# wb-search-miner

Браузер-как-транспорт для WB-поиска. Долгоживущий сайдкар: держит прогретые
дорожки (headful Chromium через Xvfb, patchright) и отдаёт выдачу u-search
in-page fetch'ем из доверенного контекста.

## Зачем

С **23-09-2026** это единственный путь к данным WB: публичные хосты
(`card`/`u-card`/`search`/`u-search`.wb.ru) отдают 403 всем, включая домашний
RU-IP, а фронт ушёл на `__internal` за тем же доменом. Обычным HTTP-клиентом
туда не попасть даже с валидной кукой и верным JA3 (curl и curl_cffi → 498),
поэтому и выдача, и цены идут через прогретый браузер.

Ключ к `__internal` — заголовок **`deviceid`** (`site_<32 hex>`, значение
произвольное): без него даже прогретая страница получает 403. Сайдкар выдаёт
свой id каждой дорожке и меняет его при пересоздании браузера.

Раньше сайдкар был фолбэком на 403 горячих запросов (диагноз 05-07: дело в
транспорте, не в IP). Это по-прежнему верно, просто теперь через него идёт всё.

Диагноз и общий план — `docs/WB-SEARCH-STATUS.md`.

## API

- `GET /search?query=<q>&sort=<popular|pricedown|…>&page=<n>` → сырой JSON
  u-search (форма `wbSearchResponse`), статус зеркалит upstream (403 при стене).
  Пагинация работает: страницы тянутся in-page fetch'ем, а не навигацией.
- `GET /card?nm=id1;id2;…` → живые цены пачкой (до `WB_CARD_BATCH_MAX`, по
  умолчанию 10 — столько же кладёт в запрос сам фронт). Форма ответа та же,
  что отдавал закрытый `u-card.wb.ru`.

  **Одиночный `nm` идёт через батчер:** запросы копятся окно
  `WB_CARD_BATCH_WINDOW_MS` (250 мс) и уходят к WB одной пачкой, каждому
  вернётся свой товар. Без этого поток «по одному» выжигал доверие дорожки за
  2–4 минуты (498 → перепрогрев → цены в архив, живых оставалась пятая часть).
  Несколько `nm` в запросе — ручная проверка, идёт напрямую, без окна.
- `GET /healthz` → `{healthy, total, lanes}`; 200 если жива хоть одна дорожка.
- `GET /metrics` → `wb_search_miner_healthy_lanes` и пр. (Prometheus text).

Зовёт его Go `WildberriesSearchScraper` как 403-фолбэк (`WB_SEARCH_BROWSER_URL`):
direct-first (холодные запросы дёшевы), на 403 — в сайдкар, с залипанием на
остальные страницы запроса.

## Ключевой конфиг (env)

| env | дефолт | что |
|-----|--------|-----|
| `WB_SEARCH_MINER_PORT` | `8081` | порт сервиса |
| `WB_SEARCH_POOL_SIZE` | `1` | число дорожек |
| `WB_WARM_QUERY` | `телефон` | запрос прогрева (проходит стену) |
| `WB_SEARCH_PROXY_URL` / `WB_LANE_<i>_PROXY` | — | опц. прокси (обычно НЕ нужен) |
| `WB_WARM_KEEPALIVE_MINUTES` | `30` | периодический re-warm живой дорожки |
| `HEADLESS` | `false` | headful в Xvfb (обязателен для обхода) |

## Прогрев

Навигация на страницу поиска `WB_WARM_QUERY` (проходим wbaas-стену) → ждём, что
in-page fetch к u-search отдаёт валидный 200 → дорожка healthy. Нездоровые
перепрогреваются в maintenance-цикле с экспоненциальным backoff (не долбим стену).
