# price-insight — ревью, первый запуск и что осталось

Дата: 13.08.2026. Автор проверки — сессия, которая сервис НЕ проектировала.
Предмет: `price-insight/`, миграция `032_price_insight.sql`, правки compose.
Канон замысла — [`docs/PRICE-INSIGHT-JAVA.md`](PRICE-INSIGHT-JAVA.md).

**Короткий вывод.** Доменная логика оказалась верной по существу — на сверке с
SQL-портом Go совпала полностью. Но до продакшена сервис не доехал бы: в том
виде, в каком код лежал, он **не обработал бы ни одного события на нашей
Kafka** и **отдавал бы в Postgres замороженный вердикт**. Оба дефекта нашлись
только при реальном запуске, юнит-тесты их не видят по построению. Сейчас
этапы 1–3 закрыты, этапы 4–5 (прод и сверка на живых данных) НЕ выполнены.

## 2. Найденные дефекты

Порядок — по тяжести. Все, кроме отмеченных, починены и закрыты тестом.

### D1. Сервис не работал бы на нашей Kafka вообще (блокер)

`exactly_once_v2` требует координатора транзакций. Служебный топик
`__transaction_state` создаётся с дефолтами `replication.factor=3`,
`min.insync.replicas=2`, а брокер у нас **один** — топик не создаётся никогда,
клиент вечно висит на `InitProducerId`:

```
TimeoutException: Timeout expired after 60000ms while awaiting InitProducerId
```

Поток перезапускается обработчиком `REPLACE_THREAD` и упирается в то же самое.
При этом **healthcheck зелёный, логи почти чистые, сервис молча не делает
ничего**. Ровно этот сценарий воспроизвёлся локально.

Починка — в `docker-compose.yml`, сервис `kafka`:

```yaml
KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
```

⚠️ **Это правка ЧУЖОГО сервиса, и она требует рестарта брокера на проде.** По
условию задачи price-insight не должен трогать существующее — формально это
нарушение, поэтому выношу отдельно и без решения не катаю. На Go-сервисы
настройка не влияет: транзакции использует только price-insight, топика
`__transaction_state` до него в кластере не существовало.

### D2. Проекция в Postgres замораживала строку навсегда (блокер)

В `VerdictProjector` стояло:

```sql
ON CONFLICT (product_id) DO UPDATE SET ...
WHERE price_insight.computed_at <= EXCLUDED.computed_at
```

`computed_at` — **не версия строки**. У вердикта из события это время события,
у вердикта из пунктуатора — stream-time, и второе легко больше первого.
Наблюдалось живьём в топике по товару 777:

```
computed_at=2026-08-13T09:21 verdict=1 min_all=1000   ← тик пунктуатора
computed_at=2026-08-03T09:17 verdict=5 min_all=1000   ← событие
computed_at=2026-08-12T09:17 verdict=1 min_all=700    ← событие: цена упала
```

Guard отбросил два последних. В таблице осталось `min_all = 1000` вместо `700`
— то есть сервис утверждал бы «обычная цена» там, где рекордный минимум. Это
ровно то враньё, ради борьбы с которым он написан.

Починка: guard убран. Порядок обеспечивает Kafka — ключ `product_id`, товар
живёт в одной партиции, вердикты приходят строго по порядку, последний
выигрывает. Перечитывание топика проигрывает ту же последовательность и
сходится к тому же значению; расхождение при этом временное, а не вечное.
Регрессионный тест: `IntegrationTest.laterRecordWinsEvenWithEarlierComputedAt`.

### D3. Стейт рос по числу СКРЕЙПОВ, а не по числу смен цены

Ключевое расхождение моделей, которое не видно, если не сопоставить два
источника:

- `price_history` — **change-only**: строка пишется только при смене цены
  (`cmd/scraper/main.go`, `pricesEqual`);
- `price-events` — публикуется на **каждом** скрейпе (там же, комментарий про
  строгую per-plan модель).

`ProductState.apply` резал новый сегмент на каждое событие. На стабильном
товаре при минутном кадансе reseller это ~130 000 сегментов за 90 дней
retention **на один товар**, и каждое событие переписывало бы весь снимок в
RocksDB и в changelog-топик. На агрегаты это не влияет (соседние сегменты с
одинаковой ценой эквивалентны одному), но по ресурсам это мина.

Починка: событие с той же ценой **продолжает** открытый сегмент. Критерий
равенства — до копейки, `Math.round(a*100)`, тот же, по которому Go решает,
писать ли строку. Теперь размер стейта равен числу строк `price_history`.
Тесты: `repeatedPriceIsCoalesced`, `subKopeckDifferenceIsSamePrice`.

### D4. Медиана брала не ту половину на равенстве

Go: `cum >= tot / 2.0` — нижняя взвешенная медиана. Было: `acc > total / 2`.
Разница видна ровно на равенстве половин: 10 дней по 1000 и 10 дней по 2000
дают у Go `1000`, а у Java давали `2000` — вердикт переворачивался с «обычная
цена» на «выше обычной». Починено на `acc * 2 >= total`.
Тест: `medianTakesLowerHalfOnTie`.

### D5. RocksDB съел бы лимит контейнера мимо heap

Streams заводит отдельный экземпляр RocksDB на каждую партицию: block cache
50 МБ + memtable 3 × 16 МБ. На десяти партициях `price-events` это ~1 ГБ вне
heap при `mem_limit: 1g` — контейнер убил бы OOM-killer, причём heap о внешней
памяти ничего не знает. Добавлен `BoundedMemoryRocksDBConfig`: общий на процесс
`LRUCache` 128 МБ + `WriteBufferManager` 32 МБ. `MaxRAMPercentage` снижен
45 → 40. Замер после починки — §4.

### D6. Битое сообщение вешало поток в вечный цикл

Дефолт Streams — `LogAndFailExceptionHandler`: ошибка десериализации роняет
поток, `REPLACE_THREAD` поднимает его, он читает ту же запись, падает снова.
Поставлен `LogAndContinueExceptionHandler` — пропуск безопасен, источник правды
в `price_history`, вердикт догонит следующее событие.

### D7. Readiness врал

`/actuator/health/readiness` отвечал UP по факту поднятого Spring-контекста:
топология могла быть мертва, а compose считал бы контейнер здоровым (и именно
это происходило при D1). Добавлен `KafkaStreamsHealthIndicator`, группа
readiness расширена. Проверено живьём: `{"status":"UP"}` при работающем потоке.

### D8. Мои собственные грабли по дороге

Бин health-индикатора был назван `kafkaStreams` и столкнулся с бином самого
потока — контекст не поднялся. Поймано первым же запуском `IntegrationTest`,
починено (имя выводится из имени класса).

### D9. Тест был устроен так, что зеленел бы на второй раз ложно

`IntegrationTest` держал стейт в общем `/tmp/price-insight-it`: каталог
переживал прогон, и следующий запуск поднимался на чекпоинтах от ДРУГОГО
брокера. Теперь каталог уникален на прогон. Схему тест создавал своей копией
DDL — заменено на чтение боевой миграции `032`, иначе копия разъедется молча.

### D10. Alpine и нативная часть RocksDB

Образ на musl; `rocksdbjni` подхватывает musl-сборку, но она динамически
линкуется с `libstdc++`. Добавлен `apk add --no-cache libstdc++`
превентивно. Живьём падения не было — то есть, возможно, пакет и так приезжал
с temurin; лишним не будет.

## 3. Расхождения с Go, которые НЕ являются багами (и их надо знать перед переключением)

### R1. У Java физически меньше истории, чем у Go — retention `price-events` = 72 часа

`KAFKA_LOG_RETENTION_HOURS: 72`. Отсюда:

- «пересобрать стейт проигрыванием топика с начала» (§5 PRICE-INSIGHT-JAVA.md)
  **невозможно** — назад проигрывается максимум трое суток;
- `observed_since` у всех товаров будет ≈ момент выкатки, а не момент начала
  трекинга. Значит **первые 7 дней после деплоя ВСЕ товары получат
  `insufficient`** (гейт по возрасту), а честный `min_90` появится только через
  90 дней;
- `min_all` у Go включает бэкфилл маркетплейс-истории (`PrependOlder`, WB
  `price-history.json`) — точки, которых в топике не было **никогда**. Java их
  не узнает ни при каком retention.

Это не чинится настройкой: нужен отдельный бутстрап стейта из `price_history`
(см. §6, «не закрыто»).

### R2. Время «нет в наличии» считается по-разному

Go: при OOS строка не пишется, а при возврате по той же цене — тоже не пишется
(`pricesEqual`). Значит **весь интервал отсутствия засчитывается как время по
последней известной цене** и тянет медиану. Java рвёт сегмент и время
отсутствия не учитывает.

Java здесь **правее**, но это осознанное расхождение: у товаров, уходивших из
наличия, `median_30` будет отличаться от того, что показывает бот сейчас.

### R3. `computed_at` немонотонен и не годится как признак свежести «в лоб»

Два разных источника времени (событие / stream-time), плюс дедупликация: если
вердикт не изменился, сообщение не публикуется и `computed_at` в таблице
стареет, хотя сервис здоров и вердикт актуален. Наивная проверка «протух →
откат на `Stats`» будет откатываться на стабильных товарах **всегда**. Для
notifier нужен другой признак живости (например, отдельный heartbeat сервиса
или сравнение с временем последнего события по товару).

### R4. `LAG = 1` на каждой партиции — это норма, а не залипание

С `isolation.level=read_committed` в конец каждой транзакции пишется control
record. Он входит в `LOG-END-OFFSET`, но не выдаётся консьюмеру. Постоянный
лаг 1 на партицию — ожидаемая картина, не путать с реальным отставанием при
мониторинге на проде.

## 5. Инструмент сверки: `scripts/sql/price-insight-parity.sql`

Только чтение, ничего не меняет. Считает два среза:

- **Срез А — тест логики.** Go считает по тому же окну, что и Java: строки
  `price_history` не старше `observed_since`, момент оценки = `computed_at` из
  строки. Здесь вердикты **обязаны** совпадать, расхождение = дефект.
- **Срез Б — цена переключения.** Go по всей своей истории. Показывает,
  насколько вердикт из `price_insight` сегодня отличается от того, что бот
  показывает пользователю. Расхождение тут ожидаемо (см. R1) и говорит не об
  ошибке, а о неготовности данных.

Плюс матрица переходов вердиктов и оценка, насколько история Go глубже.
Сравниваются только товары **в наличии** (при OOS Java намеренно молчит).

Запуск на проде:

```bash
docker compose exec -T postgres psql -U user -d tryberrybot -f - < scripts/sql/price-insight-parity.sql
```

⚠️ Через 7 дней после выкатки срез А по вердиктам будет тривиально совпадать
(обе стороны отдадут `insufficient` — гейт по возрасту). Осмысленный ответ он
начнёт давать не раньше, чем через неделю после старта, а по `min_90` — через
90 дней. **Смотреть на числа `min_30`/`median_30` в срезе А имеет смысл сразу.**

## 6. Что осталось незакрытым

1. **Прод (этап 4) не тронут.** Нужны: решение по рестарту Kafka (D1), ручная
   миграция, наблюдение за памятью и лагом.
2. **Сверка на реальных данных (этап 5) не проведена.** 3 синтетических товара
   — не 50 и не «несколько сотен».
3. **Бутстрап стейта из `price_history` не спроектирован.** Без него сервис
   годен к переключению не раньше чем через 90 дней после выкатки (R1). Эскиз:
   одноразовый producer, который читает `price_history` и льёт синтетические
   `PriceEvent` с историческими `recorded_at` — но применять его надо ДО живого
   потока по товару, иначе гард `lastEventAt` их отбросит.
4. **Алертов на price-insight нет.** Scrape-job в Prometheus добавлен, но имя
   `price-insight` намеренно без префикса `tryberrybot-`, чтобы штатный откат
   (`docker compose stop price-insight`) не будил дежурного по `ServiceDown`.
   Когда notifier начнёт зависеть от вердикта — префикс вернуть и завести
   алерты на лаг и на состояние потока.
5. **Панель в Grafana не сделана** (пункт 4 порядка работ в PRICE-INSIGHT-JAVA.md).
6. **Грабля деплоя:** миграция `032`, скормленная в `psql` целиком, выполняет и
   `Up`, и `Down` — таблица создаётся и тут же удаляется, **без единой ошибки**.
   На проде миграции катают руками через psql (README-deploy.md), поэтому брать
   только секцию `Up`:
   ```bash
   awk '/-- \+goose Up/{f=1} /-- \+goose Down/{f=0} f' migrations/032_price_insight.sql \
     | grep -v 'goose Statement' \
     | docker compose exec -T postgres psql -U user -d tryberrybot -v ON_ERROR_STOP=1
   ```
   Права на новую таблицу `tryberry_app` получит сам — через
   `ALTER DEFAULT PRIVILEGES FOR ROLE "user"` из `pg-create-roles.sh`
   (проверено локально: `tryberry_app=arwd/user`).
7. **Пунктуатор обходит весь store на тик** (раз в 6 ч). При текущем каталоге
   дёшево, при кратном росте — переделывать в очередь «когда пересчитать».
8. `ProductState.stats()` отдаёт `hasData=false`, если у товара были только
   OOS-события, тогда как Go отдал бы `hasData=true`. Недостижимо на практике
   (при `current <= 0` вердикт не публикуется), оставлено как есть.

## 7. Оценка: можно ли переключать notifier на `price_insight`

**Нет, пока нельзя.** Не из-за качества кода — логика после починок сходится с
Go на всех проверенных входах, — а из-за данных и незакрытых стыков.

Переключение станет безопасным, когда:

1. **Сервис отработает на проде и сверка (§5, срез А) пройдёт на сотнях
   товаров.** Сегодня подтверждение — 3 синтетических товара.
2. **Решён вопрос глубины истории (R1).** Либо бутстрап из `price_history`,
   либо осознанное согласие, что 90 дней после выкатки notifier читает вердикт
   только у товаров, которые сервис успел пронаблюдать, а остальным — старый
   путь.
3. **Придуман честный признак свежести (R3).** `computed_at` для этого не
   годится: он немонотонен и стареет на стабильных товарах.
4. **Принято решение по OOS-семантике (R2).** Значения `median_30` у товаров,
   уходивших из наличия, изменятся — это видимое пользователю изменение
   вердикта, а не рефакторинг.
5. **Заведены алерты** на лаг и состояние потока (§6.4).

Отдельно: даже после переключения fallback на `PriceHistoryRepo.Stats` снимать
нельзя — это единственное, что делает падение JVM-сервиса безопасным.

### Что до этого можно сделать прямо сейчас

Выкатить на прод в режиме наблюдения — сервис аддитивен, никто из Go-сервисов
от него не зависит, откат — `docker compose stop price-insight`. Единственное,
что мешает выкатить прямо сейчас без обсуждения — рестарт Kafka из D1.

**Шаг 1. Рестарт Kafka с настройками транзакций.** Кратковременный обрыв для
Go-сервисов, они переподключаются сами. Без этого шага price-insight не
обработает ни одного события (D1).

```bash
$C up -d kafka
$C exec kafka kafka-topics --bootstrap-server localhost:9092 --describe --topic __transaction_state | head -2
```

Ожидание: топик существует, `ReplicationFactor: 1`. Если «does not exist» —
он создаётся при первом транзакционном продюсере, проверить снова после шага 3.
Заодно убедиться, что продукт жив:

```bash
$C logs --tail 30 notifier scraper
```

**Шаг 2. Миграция 032 — ТОЛЬКО секция Up.** Целиком скормленный файл создаёт
таблицу и тут же её удаляет, молча (см. §6.6).

```bash
awk '/-- \+goose Up/{f=1} /-- \+goose Down/{f=0} f' migrations/032_price_insight.sql \
  | grep -v 'goose Statement' \
  | $C exec -T postgres psql -U user -d tryberrybot -v ON_ERROR_STOP=1

$C exec postgres psql -U user -d tryberrybot -c '\dp price_insight'
```

Ожидание: `CREATE TABLE`, `CREATE INDEX`, и в правах строка
`tryberry_app=arwd/user`. Если прав нет — сервис не сможет писать, выдать
руками: `GRANT SELECT, INSERT, UPDATE, DELETE ON price_insight TO tryberry_app;`
