# VK-клон: дизайн профиля, привязки аккаунтов и поэтапный план

> Дата: 2026-06-11. Статус: обсуждение дизайна, код не начат.
> Исходная идея: кнопка «Профиль», где видно привязанный TG и можно привязать VK
> (и наоборот), без полноценной регистрации с подтверждениями.

## TL;DR решений

| Вопрос | Решение |
|---|---|
| Модель юзера | Один `users` с nullable `telegram_id` + nullable `vk_id` (вариант A, не отдельная таблица identities) |
| Привязка | **Одноразовый код-ссылка** между ботами, а не ручной ввод id — иначе угон аккаунтов |
| Объединение двух живых аккаунтов | В v1 запрещено: поглощаем только «пустой» аккаунт, иначе отправляем в поддержку |
| Изменение привязки | В TG можно менять только VK, в VK — только TG (твоя идея, она верная) |
| Порядок работ | Фаза 0: профиль+привязка → Фаза 1: уведомления в VK → Фаза 2: полный UX в VK |

---

## 1. Главный подводный камень: привязка без подтверждения = угон аккаунта

Если в TG-боте можно просто «вписать» VK id (и наоборот), то:

- я могу указать **чужой** VK id. Когда настоящий владелец придёт в VK-бота, он
  попадёт в мой аккаунт — увидит мои подписки, я увижу его действия;
- обратное хуже: из VK можно «привязать» telegram_id **платного** юзера и получить
  его тариф и подписки. После запуска ЮKassa это прямой способ красть подписки.

Перебор id никак не детектится — это не баг реализации, а дыра в самой схеме
«ввёл число — привязал».

### Решение: одноразовый код, UX в два тапа (это НЕ «регистрация»)

1. В TG: «Привязать VK» → бот генерирует одноразовый код (8 симв., crypto/rand,
   TTL 15 мин, хранится в Redis — он уже есть для FSM) и показывает:
   «Открой нашего бота в VK и отправь ему: `link A7K2M9QX`» + кнопка-ссылка на vk.me.
2. В VK: юзер шлёт код → VK-бот находит код в Redis (атомарный `GETDEL` — код
   одноразовый даже при гонке), привязывает.

Владение **обоими** аккаунтами доказано без телефонов и почты: код получен в TG
(владеешь TG), отправлен из VK (владеешь VK). То же самое в обратную сторону.
Никаких «подтверждений» в понимании регистрации — два тапа и вставка кода.

Правило «в TG меняем только VK, в VK — только TG» — правильное и естественно
ложится на код-флоу: ты никогда не редактируешь ту identity, через которую сейчас
авторизован (иначе можно выпилить сам себя или угнать сессию).

## 2. Модель данных

### Вариант A (рекомендую): расширить users

```sql
ALTER TABLE users ALTER COLUMN telegram_id DROP NOT NULL;
ALTER TABLE users ADD COLUMN vk_id BIGINT UNIQUE;
ALTER TABLE users ADD CONSTRAINT chk_user_has_identity
    CHECK (telegram_id IS NOT NULL OR vk_id IS NOT NULL);
-- + notify_channel TEXT NOT NULL DEFAULT 'auto'  -- 'auto'|'tg'|'vk'|'both'
```

Плюсы: минимальная миграция; все текущие запросы по `telegram_id` продолжают
работать; `vk_id` юзера — это и есть peer_id для отправки в VK (ЛС).

### Вариант B (отвергнут для v1): таблица user_identities(platform, external_id)

Красивее и расширяемо на третью платформу, но `telegram_id` сейчас используется
в ~20 файлах (notifier, reconciler, поиск-уведомления, admin, FSM) — переезд на
JOIN-ы везде это и есть те «2–4 недели», причём без пользовательской ценности.
Если когда-нибудь появится третья платформа — мигрировать из A в B механически.

### Ripple-эффект nullable telegram_id

Все места, где «юзер = telegram_id», должны уметь жить с NULL:
- notifier/reconciler: выборки `SELECT telegram_id ...` → выбирать оба id + канал
  и роутить (фаза 1);
- `SetPlan(telegramID, ...)` и админка: оставить как есть (админка по tg id),
  добавить вариант по `users.id` там, где надо;
- упавший случай «VK-only юзер» до фазы 1 невозможен: пока VK-бота нет,
  vk_id появляется только привязкой к существующему TG-аккаунту.

## 3. Второй камень: объединение двух живых аккаунтов

Сценарий: полгода пользовался ботом в TG (Pro, 40 подписок), отдельно потыкал
VK-бота (free, 2 подписки, триал использован). Привязывает — а у нас **две строки
users**. Честный merge — это перенос подписок с дедупликацией, конфликт планов,
OR по trial_used, конфликты referred_by, потенциальный фарм реферальных наград
через объединения… это болото.

### Решение v1: поглощаем только пустой аккаунт

Аккаунт считается пустым: `plan='free'` AND `trial_used=false` AND нет
подписок (активных или на паузе). Тогда при привязке пустую строку просто
удаляем, id вписываем в живую.

Если оба аккаунта непустые — отказ с человеческим текстом: «Этот VK-аккаунт уже
пользуется ботом отдельно. Напиши @kosov_andrey — объединим вручную». Покроет
95% случаев: нормальный путь — зарегался на одной платформе, привязал вторую
до того, как начал ей пользоваться.

### Анти-абьюз привязок

- `trial_used` при поглощении: OR двух значений (иначе: триал в TG → привязал
  свежий VK → отвязал → триал в VK → …).
- Смена привязки VK (отвязать старый, привязать новый) — разрешить, но старый
  vk_id просто обнуляется: бывший VK-юзер при следующем сообщении создаст
  свежий пустой аккаунт. Ничего не наследует — фарма нет.
- Rate-limit на генерацию кодов (не чаще 1 в минуту на юзера) — гигиена.

## 4. Экран «Профиль» (твоя идея, расширенная)

Кнопка в главном меню (вместо или рядом с «Мой тариф» — можно объединить):

```
👤 Профиль

Тариф: Pro · до 12.07.2026
Telegram: ✅ @username
VK: ❌ не привязан
Уведомления: Telegram

[🔗 Привязать VK]
[🔔 Куда слать уведомления]   ← появляется, когда привязаны оба
[ℹ️ Тариф и лимиты] [◀️ В меню]
```

В VK-боте зеркально: «Telegram: не привязан [Привязать Telegram]».
Позже сюда же лягут история платежей и кнопка «Купить тариф».

Настройка `notify_channel`: auto (куда зарегался) / tg / vk / both.

## 5. Специфика VK (что будет отличаться от TG)

| Аспект | TG (сейчас) | VK |
|---|---|---|
| Приём апдейтов | polling → Kafka → bot-worker | Callback API (webhook на cmd/api за nginx — он уже наружу смотрит) или Bots Long Poll |
| Egress | через xray/WG (РКН) | **прокси не нужен** — vk.com доступен с RU-VM напрямую |
| Форматирование | HTML | **plain text** — нужен рендер-слой (HTML для TG / текст для VK) |
| Клавиатуры | inline + callback | есть аналог (callback-кнопки с JSON payload) |
| Правка сообщений | без ограничений | messages.edit ограничен по времени — «меню в одном сообщении» работает, но с фолбэком «отправить новое» |
| Deep-links | t.me/bot?start=ref_X | vk.me/club…?ref=X (параметр ref в кнопке «Начать») |
| Оплата | ЮKassa-ссылка | та же ЮKassa-ссылка — это просто URL, работает везде |

## 6. Поэтапный план (каждая фаза — деплоябельна и полезна сама по себе)

### Фаза 0 — Профиль и привязка (≈1–2 дня)
Миграция (vk_id, nullable telegram_id, notify_channel) + экран «Профиль» в TG +
генерация link-кодов в Redis. Привязка пока «в одну сторону» не работает без
VK-бота, поэтому фаза 0 деплоится вместе с минимальным VK-ботом из фазы 1.

### Фаза 1 — Минимальный VK-бот: привязка + уведомления (≈3–5 дней)
Сервис `cmd/vk-receiver` (Callback API → Kafka) + обработчик: /start, приём
link-кода, «Профиль». В notifier — роутинг по notify_channel: VK-отправка
(messages.send, без прокси). **Ценность: уведомления приходят в VK** — это 80%
пользы клона за 20% работы. Полные меню в VK ещё не нужны.

### Фаза 2 — Полный UX в VK (2–3 недели, после обкатки фазы 1)
Рендер-абстракция текстов (HTML/plain), портирование меню и флоу добавления
подписок, реферальные deep-links в VK. Сюда лезем, только если фаза 1 покажет
реальный спрос (метрика: сколько юзеров привязали VK и включили уведомления).

---

## 7. Что НЕ делаем (осознанно)

- Полноценную регистрацию с телефоном/почтой — не нужна, код-флоу достаточен.
- Merge двух живых аккаунтов — вручную через поддержку, пока кейсов мало.
- Таблицу identities — premature, vk_id колонкой дешевле на порядок.
- VK Pay — оплата остаётся ЮKassa-ссылкой.
