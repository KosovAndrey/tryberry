# WB: живая цена карточки вместо архива (📌 КАНОН по источнику цены WB)

Статус: **v2 не проверена на проде** (ветка `fix/wb-live-card-price`, 2026-07-16).
v1 (навигация) на проде **провалилась и откачена** — разбор в §«Провал v1».
Фиксит баг, найденный 2026-07-15 при отборе товара для промо-скриншотов.

**Включается только явно**: `WB_CARD_BROWSER_URL=http://wb-search-miner:8081` в
`.env`. По умолчанию пусто = цена из архива (поведение до фикса).

## Симптом

Станция Лайт 2 (nm 376365149, product 8288688): в базе **3 696.02 ₽** от 13.07,
на живой карточке **5 047 ₽**. Публичная `/p/` писала «Дешевле не было за всё
время наблюдения» на цену, которой уже нет.

## Диагноз

Текущая цена бралась **последней точкой архива** `price-history.json` с
basket-CDN (`parseWBHistory`). Архив обновляется с лагом в **дни** (комментарий в
коде обещал «часы»). Cond-GET 304 дополнительно замораживал цену из снимка.

Масштаб по метрике на 2026-07-15: `wb_price_source: basket=100, ucard=3` →
**97% цен WB из архива**. При этом **success rate = 100%**: скрейпер честно
качает файл с CDN, там нет антибота.

> **Успех ≠ правда.** Такой баг метриками не ловился в принципе — только сверкой
> с живой карточкой глазами. Тот же класс, что `ozon-oos-foreign-price-bug`:
> «откуда мы знаем, что эта цена принадлежит этому товару СЕЙЧАС».

## Решение: браузер, НЕ прокси

Прокси отвергнут: xray бережём под TG-egress. Образец — Ozon (браузерный
сайдкар); Я.Маркет тут НЕ образец (он ходит direct без браузера).

Сайдкар с нуля не нужен — расширен **существующий** `wb-search-miner` (уже
прогрет, проходит wbaas, на проде с 2026-07-05):

- **Python** (`wb-search-miner/server.py`): эндпоинт `GET /card?nm=<id>` рядом с
  `/search`. Навигация прогретой дорожкой на страницу товара + перехват `u-card`
  XHR, который фронт делает сам. Транспорт общий с `/search` (`_fetch_intercept`):
  интервалы, стена, re-warm — те же.
- **Go** (`internal/scraper/wildberries.go`): `SetCardBrowser(url)` →
  `fetchFromBrowserCard` — основной источник цены. Живая карточка и архив идут
  **параллельно** (навигация ~1-2с >> basket ~100мс, история почти бесплатна),
  затем живые цена/наличие кладутся поверх архивных имени/картинки/Истории.
- `price-history.json` остаётся **только бэкфиллом истории** — его настоящая роль
  (только WB отдаёт выгружаемую серию).
- Убран захардкоженный `InStock: true`: живая карточка без оффера → честный OOS.

### Точки отката и деградации

| Ситуация | Поведение |
|---|---|
| `WB_CARD_BROWSER_URL` пуст | Цена из архива — ровно как до фикса (рубильник) |
| Сайдкар 502 (нет дорожек) / 403 (стена) | Откат в архив: цена отстаёт, но не пусто |
| `products: []` в ответе | **НЕ** трактуем как OOS (иначе сбой формы разом погасил бы весь WB) → откат в архив |
| Товара нет в basket (трансгран) | Живой карточки достаточно, просто без Истории |

### Метрики

- `wb_price_source{source}` → `browser` (норма) / `basket` (архив, **цена
  отстаёт**) / `ucard`. **Рост доли `basket` = деградация правдивости цен при
  success rate 100%** — следить надо именно здесь.
- `wb_card_fetch_total{outcome}` → `ok|forbidden|no_lanes|empty|error`.

## Замер нагрузки (сделан 2026-07-16, прод)

`sum(rate(tryberrybot_wb_price_source_total[1h])) by (job) * 3600` →
**251/час у `scraper`** (~4.2/мин), `bot-worker` — 0 (реальных юзеров нет).
Это и есть спрос на сайдкар. Замер стал возможен только после фикса `dns_sd`:
до него Prometheus видел одну реплику из трёх.

## Провал v1: навигация (откачена в тот же день)

**Что сделали:** `/card` навигировал прогретую дорожку на страницу товара и
перехватывал u-card XHR — по образцу `/search`.

**Что случилось на проде:** `ok=7` против `no_lanes=89`, `browser` отъел у
`basket` всего 16/час из 400. Дорожка почти всё время была нездорова.

**Почему (по таймингам логов):** навигация на страницу товара стоит **~14с**
(страница тяжёлая), а не 1-2с, как заложили. Одна дорожка тянет **~4.3
карточки/мин** при спросе **4.2/мин** — 100% загрузки, ноль запаса. Дальше
лавина: очередь → `FETCH_TIMEOUT` 15с → таймаут гасит дорожку → перепрогрев 10с
→ всё в `no_lanes`. Запрос `card 224414413`: пришёл 12:01:51, ответ 12:02:18 —
**27с** в очереди.

**Два урока, оба архитектурные:**

1. **Дорожка общая с `/search`, а v1 гасила её на любой неудаче карточки.**
   Health дорожки означает «wbaas-стена пройдена» — это про прогрев, а не про то,
   что u-card ответил 403 на один товар. Карточки роняли поиск заодно с собой.
   Поиску повезло: трафика в тот момент не было.
2. **Рубильника не существовало.** `${WB_CARD_BROWSER_URL:-http://…}` подставляет
   дефолт и на пустое значение → выключить из `.env` было нельзя, откат пришлось
   делать кодом. Теперь дефолт пустой, включение явное.

## v2: in-page fetch (не проверена)

`/card` зовёт u-card **изнутри прогретого контекста** (`page.evaluate` + `fetch`,
`credentials:include`), **без навигации**: ~1с вместо 14 → загрузка дорожки при
4.2/мин падает с 100% до ~7%. Неудача карточки больше **не** гасит дорожку
(только смерть браузера).

**Чем рискуем:** тот же приём к `u-search` wbaas отвергает 403 — фронт кладёт в
запрос что-то своё (см. `warm`). Сработает ли он с `u-card` — **неизвестно**.
Довод за: u-card — другой хост с другой защитой, и браузеру с нашего
датацентр-IP он отвечает (те самые `ok=7` в v1 пришли именно от него). Довод
против: u-card 403-ит наш IP из Go (потому и `SetUCardProxy`), т.е. защита там
всё же есть.

Если 403 → Go штатно уходит в архив, видно по `wb_card_fetch_total{forbidden}`.
Тогда остаётся: пул дорожек (`WB_SEARCH_POOL_SIZE` 3-4, но это 3-4 браузера в
RAM) либо гибрид (браузер только активным подпискам).

**Проверять только так:** сначала деплой ОДНОГО `wb-search-miner` (Go-сторона
выключена, звать `/card` некому) → ручной запрос → и лишь потом `.env`.
