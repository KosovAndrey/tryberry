# Ozon — разбор «мобильного API» вместо браузера (исследование, 2026-06-13)

Цель: научиться получать цену/название/картинку товара Ozon по URL, как мы это делаем
для WB через basket CDN — то есть **без headless-браузера на каждый скрейп**.
Контекст видео, которое видел Андрей: «работать не через браузер, а по мобильному API».

## Что вообще есть у Ozon

Есть **три** разных «API», их постоянно путают:

1. **Seller API** (`api-seller.ozon.ru`) — официальный, по Client-Id/Api-Key.
   Отдаёт только **свои** товары продавца. Для чужих карточек/мониторинга цен — бесполезен.

2. **Statistics API** (анонс на vc.ru, «Ozon for Dev») — официальный публичный API
   по ассортименту: характеристики, **цены**, остатки, отзывы (200+ млн карточек).
   Доступ по заявке на партнёрском сайте. Это легальный путь, но: модерация заявки,
   неизвестны лимиты/цена, и почти наверняка не realtime-per-URL, а выгрузки/срез.
   → **Стоит подать заявку параллельно** — если дадут, это снимает всю возню с антиботом.

3. **Storefront / «composer» API** — то, что дёргает сам сайт и приложение:
   - web: `https://www.ozon.ru/api/entrypoint-api.bx/page/json/v2?url=/product/<slug>-<id>/`
   - app/api: `https://api.ozon.ru/composer-api.bx/page/json/v2?url=/product/<slug>-<id>/`
   Оба возвращают один и тот же JSON c `widgetStates` (внутри — JSON-строки виджетов,
   в т.ч. `webPrice`, `webSale`, заголовок, галерея). Это и есть «мобильное API»
   из видео — формат удобный, ровно то, что нам надо.

## Мобильный API — точный рецепт (из репо `Churkashh/ozon-pinneaples`)

Приложение Ozon ходит на **тот же хост**, но другой путь и набор заголовков —
и защита там заметно слабее, чем у веб-`/product/`:

- **GET** `https://api.ozon.ru/composer-api.bx/page/json/v2`
  - параметр `url=/products/{id}/?layout_container=pdppage2copy&layout_page_index=2`
    (путь `/products/` — **множественное**, не веб-`/product/`)
- Заголовки приложения:
  ```
  Accept: application/json; charset=utf-8
  User-Agent: ozonapp_android/17.48.0+2528
  x-o3-app-name: ozonapp_android
  x-o3-app-version: 17.48.0
  x-o3-device-type: mobile
  x-o3-fp: 1.01ae145142fa31f9      # отпечаток приложения
  x-o3-sample-trace: false
  MOBILE-GAID: <uuid>
  MOBILE-LAT: 0
  ```
- Авторизация (`__Secure-access-token`, `getUserV2`) нужна **только** для залогиненных
  фич; для публичной цены товара НЕ требуется.
- Цена и инфа лежат в `widgetStates` ответа (как и в вебе).

⚠️ С немецкого датацентрового IP мобильный рецепт ведёт себя иначе, чем веб: сначала
`307` (cookie-челлендж), и только потом FAB-403 — т.е. блок срабатывает **по IP**,
не по заголовкам. На RU-резидентском IP, по словам Андрея и по логике видео, мобильный
путь проходит. Это и проверяем.

## Эмпирическая проверка (сделана сегодня)

Дёргал оба эндпоинта напрямую curl'ом:

| Запрос | Результат |
|---|---|
| `entrypoint-api.bx` (browser UA) | `307` → ставит cookie `__Secure-ETC`, редирект `&__rr=1` |
| `composer-api.bx` (browser UA) | то же `307`, затем после cookie → **403 FAB** (incident) |
| `composer-api.bx` + заголовки приложения (`ozonapp_android`, `x-o3-app-name/-version/-device-type`) | **403 FAB**, сразу |
| `ozonapp_ios` вариант | **403 FAB**, сразу |

Вывод по антиботу: у Ozon стоит собственный антибот (в ответе `incidentId: fab_...`,
`blockURL=.../block.html`). Он **режет на первом контакте**, ещё до прохождения
cookie-челленджа, и **мобильные заголовки не помогают** — значит детект не по
User-Agent/заголовкам, а по **TLS/JA3-отпечатку + IP**. curl и стандартный Go
`net/http` имеют «не-браузерный» TLS-отпечаток и палятся мгновенно.

⚠️ **Важная оговорка про чистоту теста:** egress в этой dev-среде — немецкий
датацентровый IP (`AS63150 BAGE CLOUD, DE`). Ozon заведомо враждебен к зарубежным
и датацентровым IP, так что часть 403 — из-за IP, а не только TLS. На проде у нас
RU egress (wg-proxy/tinyproxy), но он тоже **датацентровый** — для Ozon это, скорее
всего, тоже красная тряпка. Нужен **RU-резидентский/мобильный** IP.

## Что реально требуется, чтобы «composer API без браузера» заработал

Три условия, и нужны все три одновременно:

1. **Браузерный TLS-отпечаток.** Go `net/http` не подойдёт. Варианты:
   - `utls` (github.com/refraction-networking/utls) — низкоуровнево, мимикрия ClientHello;
   - `tls-client` (github.com/bogdanfinn/tls-client) — обёртка над utls с готовыми
     профилями Chrome/Safari, удобнее всего для нашего Go-кода.
2. **RU-резидентский/мобильный IP.** Датацентровые (в т.ч. наш wg) — под подозрением.
   Нужен пул резидентских/мобильных прокси РФ, либо смириться с высоким % блоков.
3. **Антибот-cookie.** Первый запрос ставит `__Secure-ETC` + редирект `__rr=1`; дальше
   нужна валидная сессия. Иногда хватает «прогреть» cookie через настоящий клиент.

Доп.риск: у мобильного API может быть **подпись запроса** (HMAC-заголовок типа
`x-o3-...`), вычисляемая в приложении. Если так — нужен реверс подписи (mitmproxy +
декомпиляция apk). Это подтверждается только перехватом трафика реального приложения.

## Результаты замеров мобильного рецепта (2026-06-13/14) — статический рецепт МЁРТВ

Прогнали мобильный рецепт из `ozon-pinneaples` во всех комбинациях:

| Откуда | TLS-клиент | Результат |
|---|---|---|
| RU ПК (резидентский) | curl | **FAB 403** |
| Москва-VPS | curl | **FAB 403** |
| DE-датацентр | curl | FAB 403 |
| DE-датацентр | okhttp-impersonation (Go `bogdanfinn/tls-client`, профиль Okhttp4Android13) | **FAB 403** |

→ Дело **не в IP** (RU-резидентский тоже режется) и **не только в TLS**.
Статический рецепт протух: в репо `x-o3-fp` захардкожен (отпечаток чужого устройства),
`abt_data` генерится **просто случайной строкой** (`"7."+рандом 475–520 симв.`), а работает
там всё лишь потому, что в конфиг кладут **реальные `__Secure-access-token` залогиненного
аккаунта** + прошедшую FAB сессию. Для анонимного запроса цены — не проходит.
Публичного алгоритма генерации `x-o3-fp`/`abt_data` в открытых репо нет.

**Единственный путь дальше: снять ОДИН живой запрос приложения** (ground truth) →
узнать реальный `x-o3-fp`, нужен ли cookie/`abt_data`, есть ли подпись запроса, какой TLS.
Перехват приложения через HTTP Toolkit на планшете Android 14 без root НЕ работает
(нет доверия user-CA + cert-pinning). Доступный путь — `apk-mitm` (пропатчить APK:
доверие user-CA + снятие pinning) → поставить на планшет → перехват HTTP Toolkit.

## Прорыв через apk-mitm + что такое FAB-челлендж (2026-06-14)

Снят живой 200-запрос пропатченного приложения (apk-mitm снял pinning, HTTP Toolkit
показал трафик), **без логина**. Выводы:
- `x-o3-fp: 1.01ae145142fa31f9` — **статическая константа приложения** (совпала с GitHub-репо),
  не уникальный отпечаток устройства. Вычислять не надо.
- Логин не нужен (`__Secure-user-id=0`).
- Антибот-токен — cookie **`__Secure-ETC`** (32 hex). Приложение получает его один раз
  и переиспользует для многих API-запросов (первый же 200 шёл с готовым ETC).
- ETC **привязан к IP**: захваченный ETC не работает с другого IP (получаешь новый challenge).

Серия замеров «TLS vs IP» (товарный/поисковый эндпоинт):
| Клиент | IP | ETC | Итог |
|---|---|---|---|
| приложение (okhttp) | RU домашний | свежий | **200** ✅ |
| curl | RU домашний (тот же!) | свежий | **403** ← только TLS отличается |
| curl | Москва-VPS | свежий чужой | 307 |
| Go okhttp-TLS (`tls-client` Okhttp4Android13) | RU домашний | — (с нуля) | **`fab_chlg_`** (выдан челлендж!) |
| Go okhttp-TLS | DE-датацентр | — | **`fab_nmk_`** (мгновенный блок) |

→ FAB различает: (1) **TLS-отпечаток** (curl=403, okhttp=челлендж при идентичных IP/ETC),
(2) **репутацию IP** (RU-резидент → `fab_chlg_` решаемо; датацентр → `fab_nmk_` без шанса).

### Сам челлендж (`challenge.html`, 94 КБ)
Коммерческий антибот: 88 КБ обфусцированного JS с **собственной VM** (байткод
`LOAD_NUM/MUL/ADD/JUMP_COND_NEG/FUNC_CALL`, `panic: caught bigint`), встроенный
**CryptoJS** (AES/HmacMD5), **анти-дебаг** (`debugger`, `while(true){}`), **снятие
отпечатка окружения** (перебор шрифтов, `outerWidth/outerHeight`, navigator). Считает
токен, шлёт `POST` с решением → в ответ валидный `__Secure-ETC`. В 200-ответе
`"isWebView": true` — **приложение решает челлендж в WebView**.

**Вердикт:** пройти FAB без исполнения этого JS нельзя; чистый Go не решит (нет
браузерного окружения + VM + анти-дебаг). Но модель «решить раз → переиспользовать ETC»
= паттерн WB token-miner: WebView/headless изредка добывает ETC, Go (okhttp-TLS
`tls-client`) переиспользует его для частых дешёвых запросов товаров. Браузер НЕ на каждый
скрейп. Открытый риск: прод-egress (RU, но датацентровый wg) может ловить `fab_nmk_` —
тогда solver'у нужен RU-резидентский/мобильный выход.

## Возможные архитектуры (сопоставление с тем, что уже есть)

### Вариант A — чистый Go + tls-client + резидентский RU-прокси
- `OzonScraper.Scrape()`: tls-client с профилем Chrome → `composer-api.bx`, парсим `widgetStates`.
- Плюсы: нет браузера, дёшево в рантайме, ложится в текущий интерфейс `MarketplaceScraper`.
- Минусы: нужен резидентский прокси РФ ($), хрупко к смене JA3/антибота, возможна подпись.

### Вариант B — гибрид: браузер-«майнер» cookie + Go-скрейп (по аналогии с WB token-miner)
- Сайдкар на Patchright (он у нас уже есть для WB) раз в N минут проходит FAB-челлендж,
  складывает антибот-cookie + UA в Redis; Go берёт их и ходит в composer-api сам.
- Плюсы: переиспользуем готовую инфраструктуру `token-miner`; браузер не на каждый скрейп.
- Минусы: cookie Ozon короткоживущие и часто привязаны к IP/JA3 → cookie из браузера
  может не подойти к Go-клиенту (другой TLS). Требует проверки жизнеспособности.

### Вариант C — браузер на каждый скрейп (Patchright рендерит PDP)
- Самый надёжный (так советуют все парсеры Ozon), но самый тяжёлый: это ровно то,
  чего видео призывало избегать. Для нашего объёма мониторинга — дорого по ресурсам.

### Вариант D — официальный Statistics API (Ozon for Dev)
- Подать заявку. Если одобрят — снимает антибот целиком, легально и стабильно.
- Минусы: модерация, неизвестные лимиты, возможно не per-URL realtime.

## ПРОРЫВ 2026-06-14: мобильный прокси пробивает FAB + реализация

Андрей купил **приватный мобильный прокси** (Мегафон Москва, 1790₽/мес, безлимит,
регулируемая ротация по ссылке/вручную, 10-15 Мбит/с, sticky-IP). Тест `oztest-linux`
через него (egress `31.173.87.173`, Мегафон РФ):

| Выход | Вердикт FAB |
|---|---|
| датацентр (DE/RU wg) | `fab_nmk_` — мгновенный блок |
| **мобильный РФ (приватный)** | **`fab_chlg_` — выдан челлендж (решаемо)** |

IP стабилен между запросами (приватный держит до ручной/таймерной ротации) → solver и
скрейпер сидят на ОДНОМ IP, ETC не протухает на ротации. Формат прокси от продавца
`host:port:user:pass` → URL `http://user:pass@host:port`.

### Реализованная архитектура (= паттерн WB token-miner)
1. **`ozon-miner/`** (сайдкар, Patchright + Xvfb, как `token-miner/`): headful Chromium
   через мобильный прокси заходит на `www.ozon.ru`, FAB решается в браузере, харвестим
   cookie `__Secure-ETC` + всю cookie-строку `.ozon.ru` + UA + egress-IP →
   Redis `ozon:etc:pool:0` HASH `{cookie,ua,etc,ip,mined_at,status}`. Пул = **1 слот**
   (один sticky-IP; пул из N на одном IP ничего не разносит — Ozon лимитит по IP).
   Обновляет по возрасту (`MINE_MAX_AGE_HOURS=6`) и когда Go пометил слот `broken`.
2. **`internal/scraper/ozon.go`** (`OzonScraper`): `bogdanfinn/tls-client` с профилем
   `Chrome_124` (под Chromium майнера) + **тот же прокси** (`OZON_PROXY_URL`) + cookie
   из Redis → `GET www.ozon.ru/api/entrypoint-api.bx/page/json/v2?url=/product/<id>/` →
   парсим `widgetStates` (`webPrice*`/`webProductHeading*`/`webGallery*`). На 403/FAB
   помечает слот `broken` (майнер перевыдаст). Браузер — НЕ на каждый скрейп.
   `NewOzonScraper(OzonOptions{})` без Redis = режим только `Matches` (бот/api).

### Деплой/проверка на проде
1. В `.env` на VM: `OZON_PROXY_URL=http://user:pass@host:port` (см. `.env.prod.example`).
   Опц. `OZON_VALIDATE_PRODUCT=<id>` — майнер залогирует, что entrypoint-api отдаёт
   `widgetStates` (sanity-check сессии).
2. `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build ozon-miner scraper`
3. Логи майнера: `docker logs -f pt_ozon_miner` → ждём «слот 0 обновлён: etc=…».
   Проверить Redis: `docker exec pt_redis redis-cli HGETALL ozon:etc:pool:0`.
4. Затрекать в боте товар `ozon.ru/product/...` → в логах `pt_scraper` должен быть
   `scraped marketplace=ozon price=…`.

### Открытый РИСК (проверить на проде)
ETC минтит **Chromium** (Chrome-TLS), реплеит **tls-client** (профиль `Chrome_124`).
Если FAB биндит ETC к точному TLS-хэшу минтившего клиента — Chromium≠tls-client может
не пройти (получим 403 на скрейпе при живом ETC). Фолбэки если так:
(а) подобрать профиль tls-client ближе к ревизии Chromium Patchright;
(б) точные поля `widgetStates` (`price`/`coverImage`) свериться по первому живому 200 и
подправить парсер (`parseOzonWidgets`).
