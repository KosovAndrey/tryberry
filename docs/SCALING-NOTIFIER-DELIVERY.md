# Масштабирование доставки уведомлений (notifier → 1000+ юзеров)

> Статус: **дизайн, код не тронут** (2026-06-23). Согласовать до реализации.
> Триггер разбора: алерт `HighKafkaConsumerLag` за 22.06 (см. ROADMAP-журнал)
> — ранний симптом структурной узости. Решили проектировать под цель 1000+
> пользователей заранее, т.к. первый пользовательский опыт — самый важный.

## 1. Проблема

Товарный путь уведомлений сейчас:

```
scheduler ─(scrape-tasks)→ scraper ─(price-events, key=product_id)→ notifier
                                                                       │
                                              decode → DB(subs) → решить → Telegram-send
```

`notifier` консьюмит `price-events` **одним последовательным циклом**
(`internal/kafka/consumer.go`: `FetchMessage → handler → CommitMessages`, по
одному сообщению на инстанс) и **внутри хендлера синхронно шлёт в Telegram**
через медленный egress-прокси. Плюс `notifier` — синглтон (`container_name:
pt_notifier`) и держит ещё `runPlanReconciler`, `runDigest`, search-consumer →
**горизонтально не масштабируется как есть**.

Факты из кода, влияющие на нагрузку:

- **`price-event` эмитится на КАЖДОМ скрейпе**, не только при изменении цены
  (`cmd/scraper/main.go`: строгая per-plan модель требует оценки подписки на её
  чек-поинте). Значит объём `price-events` = объём всех скрейпов.
- Интервал скрейпа товара = MIN по планам подписчиков
  (`internal/domain/plan.go`): free 60м / lite 30м / pro·trial 15м /
  **reseller 1м**.
- `scheduler` тикает раз в минуту и эмитит **все «дозревшие» товары разом**
  (`productSchedulerTick`, батч-цикл) → price-events идут **поминутными
  всплесками**, не ровным потоком.
- Хендлер на каждое событие делает ≥1 Postgres-запрос
  (`GetActiveByProductIDWithTelegramID`), а на реальном срабатывании — сетевую
  Telegram-отправку (секунды; на плохом плече egress до ~25с).

## 2. Свидетельство (что уже наблюдали)

22.06 сработал `HighKafkaConsumerLag` на партиции 2 (пик 449), при этом:

- объём — **3939 событий/сут** (~2.7/мин), средний хендлер **53мс**;
- утилизация консьюмера ~0.2% (209с работы за сутки);
- лагнула **только** партиция 2 (ключ=`product_id`, `kafka.Hash`) — пачка
  уведомлений по «горячим» товарам упёрлась в медленный Telegram-send и
  блокировала цикл; за минуты слилась сама.

То есть даже при копеечном объёме **медленная доставка сериализует консьюмер**.
Это не throughput-проблема сегодня, но прямой предвестник того, что будет при
росте.

## 3. Модель нагрузки при 1000 пользователях

Смешанный реализм: ~1000 юзеров, ~15 товаров в среднем, дедуп популярных →
**~10 000 уникальных товаров**, эффективный интервал ~15–20 мин (почти у каждого
товара найдётся pro/trial-подписчик на 15м).

- **Средний поток:** ~10 000 / ~1100с ≈ **8–10 событий/сек**.
- **Пики:** шедулер эмитит дозревшие товары поминутным батчем → пики
  **50–100/сек** на несколько секунд каждую минуту.
- **Ёмкость одного последовательного консьюмера:** 53мс/событие →
  **~19/сек потолок**. Пики переполняют мгновенно; при 1000 юзеров lag не
  успевает слиться до следующего тика → **перманентное отставание** →
  уведомления опаздывают на минуты-часы. Это и убивает UX.

### Жёсткая стенка выше консьюмера — Telegram

- Лимиты Telegram Bot API: **~30 сообщений/сек на бота** (глобально), **~1/сек
  на чат**, всплески ~20.
- Падение цены на популярном товаре, который трекают K юзеров = **K сообщений**.
  K=200 → ≥7с только на него; несколько падений разом → очередь + HTTP 429.
- **Это не лечится скоростью консьюмера.** Даже бесконечно быстрый консьюмер
  упрётся в 30/сек на отправке. Делать вывод: доставка обязана быть
  **отдельной, глобально rate-limited очередью**, а не частью горячего пути.

## 4. Три независимых рычага (в порядке влияния на UX)

| # | Рычаг | Что чинит | Сложность |
|---|-------|-----------|-----------|
| 1 | Outbox `pending_alerts` (расцепить «решить» и «доставить») | корень lagّа; консьюмер сливает поток на скорости вставки в БД | средняя |
| 2 | Rate-limited флашер с бандлингом | Telegram-throttle (30/с), мультипликатор сообщений (1 на юзера вместо N) | средняя |
| 3 | Горизонтальное масштабирование event-consumer | consume-throughput (линейно репликами) | низкая (после сплита кода) |

Параллелить **сам** консьюмер (worker-pool с порядком по ключу) — **сознательно
НЕ делаем**: при наличии #1 и #3 это лишний риск с трекингом оффсетов и
коммит-дырками ради нуля выгоды (порядок по `product_id` уже даёт партиция).

## 5. Целевая архитектура

```
scraper ─(price-events)→  event-consumer (N реплик, consumer-group)
                              │  decode → DB(subs) → решить (throttle+триггер)
                              │  если сработало → INSERT pending_alerts
                              ▼  commit offset (быстро, без сети)
                          ┌─────────────┐
                          │ pending_alerts (Postgres, durable)
                          └─────────────┘
                              ▲
          delivery-flusher (singleton, rate-limited, бандлинг)
              читает pending → группирует по user → 1 сообщение/юзер
              → Telegram/VK с глобальным лимитом 30/с + per-chat 1/с, ретраи
```

### 5.1 Схема `pending_alerts` (эскиз)

```sql
CREATE TABLE pending_alerts (
    id              BIGSERIAL PRIMARY KEY,
    user_id         BIGINT      NOT NULL,
    subscription_id BIGINT      NOT NULL,
    product_id      BIGINT      NOT NULL,
    channel         TEXT        NOT NULL,          -- telegram|vk (из users.notify_channel)
    payload         JSONB       NOT NULL,          -- что показать: имя/url/old/new/honest-line/триггер
    idem_key        TEXT        NOT NULL,          -- = текущий ключ идемпотентности (sub:price:recordedAt)
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    deliver_after   TIMESTAMPTZ NOT NULL DEFAULT now(), -- окно бандлинга/дебаунс
    sent_at         TIMESTAMPTZ,                   -- NULL = не отправлено
    attempts        INT         NOT NULL DEFAULT 0,
    last_error      TEXT
);
CREATE UNIQUE INDEX ON pending_alerts (idem_key);   -- дедуп при at-least-once
CREATE INDEX ON pending_alerts (sent_at, deliver_after) WHERE sent_at IS NULL;
CREATE INDEX ON pending_alerts (user_id) WHERE sent_at IS NULL;
```

Семантика at-least-once сохраняется: консьюмер коммитит оффсет только после
успешного `INSERT ... ON CONFLICT (idem_key) DO NOTHING`. Идемпотентность —
по `idem_key` (уже формируется в текущем хендлере).

### 5.2 Контракт флашера

- Тикает с коротким периодом (напр. 1–2с) ИЛИ слушает LISTEN/NOTIFY.
- Выбирает «созревшие» (`sent_at IS NULL AND deliver_after <= now()`),
  **группирует по `user_id`** → одно бандл-сообщение (≤N товаров; >N — «и ещё M»).
- Глобальный rate-limit (token bucket ~25–28/с, запас под лимит 30) + per-chat
  троттл (≥1с между сообщениями одному юзеру).
- Помечает `sent_at`/инкрементит `attempts`/пишет `last_error`; ретраи с backoff.
- Идемпотентность доставки — `idem_key` (повторная выборка не задвоит сообщение).
- Чистка отправленных: периодически удаляем `sent_at < now() - 7d`.

### 5.3 Сплит `notifier`

Разнести на два деплоя:

- **event-consumer** — stateless, **N реплик**, consumer-group делит 10
  партиций `price-events` (+ `search-events`). Снять `container_name`,
  `--scale event-consumer=N`. Только: decode → решить → outbox.
- **jobs-singleton** — 1 реплика: `runPlanReconciler` + `runDigest` +
  **delivery-flusher**. Держатель egress (HTTPS_PROXY). Не масштабируется (и не
  надо: лимит Telegram глобальный).

Тот же приём (снять `container_name`, масштабировать consumer-group) применим к
`scraper` — он реальный верхний боттлнек (один HTTP-скрейп на товар на интервал).
Вне скоупа этого дока, но отметить: быстрый notifier бессмыслен без поспевающего
scraper.

## 6. Фазирование

- **Phase 0 (дёшево, низкий риск, можно сейчас):** в коде вынести
  event-consume-петлю в отдельный entrypoint, отделив от синглтонов. Деплоим
  ещё 1 репликой — но будущее масштабирование становится конфигом, не рефактором.
- **Phase 1a — СДЕЛАНО (2026-06-23, ветка `feat/notifier-outbox-flusher`):**
  outbox `pending_alerts` + флашер с глобальным rate-limit, **поведение
  эквивалентное** (по одному сообщению на алерт). Консьюмер пишет в outbox и
  двигает стейт подписки на решении; `runFlusher` (singleton) доставляет с
  лимитом ~25/с и бэкоффом, потолок 10 попыток (исчерпанные оседают в таблице,
  видны в `tryberrybot_pending_alerts_depth`). Миграция `021_pending_alerts.sql`.
  ⚠️ Деплой: **сперва `make migrate` (021), потом выкат notifier** — иначе
  `Insert` падает и консьюмер встаёт на ретраях.
- **Phase 1b — СДЕЛАНО (2026-06-23):** бандлинг. Окно коалесинга — **по тарифу**
  (`Plan.BundleWindow`: free 15м / lite 10м / pro·trial 5м / reseller·unlimited 0),
  задаётся консьюмером через `deliver_after = now + окно`. Формат — **гибрид**:
  флашер группирует due-строки по юзеру, 1 алерт → богатый `SendPriceAlert` (фото),
  ≥2 → одно текстовое `SendBundledAlert` (список ≤15 позиций, «и ещё N», TG+VK).
  Лимитер тратит 1 токен на юзера = 1 сообщение (вот где экономия квоты 30/с).
- **Phase 2 (по сигналу нагрузки):** event-consumer и scraper на N реплик.
  Чисто ops, раз код уже разделён.

## 7. Решения и оставшиеся вопросы

Решено и реализовано (Phase 1a/1b):

1. ~~**Окно бандлинга.**~~ → по тарифу (`Plan.BundleWindow`), см. §6.
2. ~~**Бандл-формат.**~~ → гибрид (1→фото, ≥2→список ≤15), см. §6.

Ещё открыто:

3. **Per-chat троттл (1/с на чат).** Пока не делаем: бандлинг даёт ≤1 сообщение
   на юзера за окно, у reseller окно 0 — но если у одного reseller-юзера часто
   срабатывает много разных товаров, проверить, не упираемся ли в per-chat лимит.
4. **LISTEN/NOTIFY vs поллинг** для пробуждения флашера (сейчас поллинг 1с —
   простой и достаточный; NOTIFY уберёт до-1с латентность, если понадобится).
5. **Search-events** (`search-notifier`) — пока отдельным путём; завести в тот же
   outbox при необходимости.
6. **Метрики/алерты:** добавить алерт на рост `tryberrybot_pending_alerts_depth`
   (флашер не успевает / egress лёг) и на возраст старейшей недоставленной;
   `HighKafkaConsumerLag` уже загрублен — после Phase 1 lag по price-events расти
   не должен (консьюмер пишет в БД и не ждёт сети).

## 8. Что НЕ делаем

- Worker-pool параллельный консьюмер с ручным трекингом оффсетов — лишний риск
  при наличии outbox + горизонтального масштабирования.
- Преждевременный перевод на N реплик до Phase 0/1 — сначала код, потом ops.

## 9. Замер под нагрузкой (2026-07-05): что реально узкое место

Нагрузочный тест **5000 синтетиков / ~30k подписок / 26k товаров** (YM+Ozon+WB)
на сервере 16 ГБ. Замеры (`docker stats`, `kafka-consumer-groups`):

- **RAM — не лимит:** занято ~9 из 15.6 ГБ, свободно ~7. Хоги: `ozon-miner`
  **4 ГБ**, `wb-search-miner` ~1 ГБ, `kafka` ~1.35 ГБ. Все Go-сервисы 15–30 МБ.
- **CPU — почти весь простаивает** даже под нагрузкой: scraper-реплики 4–9%,
  прочее <1%. Всплески (kafka 230%, wb-miner 236%) — транзиентные (ребаланс /
  бурст collect), в покое 4% / 1%.
- **Единственное узкое место — продуктовый `scraper`:** топик `scrape-tasks`
  (10 партиций), консюмер **последовательный** (`Consumer.Run`, 1 сообщение за
  раз) → 1 инстанс держал lag ~9500 при CPU 15% (**latency-bound**, ждёт МП).

**Масштабирование scraper (Phase 0 сделан — снят `container_name`):**
`docker compose -f … -f … up -d --scale scraper=N` (в prod ports сброшены
оверлеем; consumer-group делит 10 партиций; `partition.Manager` идемпотентен
под advisory-lock — реплики безопасны).

Замер при N=4: ёмкость **~240 задач/мин** (≈1 скрейп/с на реплику) против
продукции **~107/мин** → чистый дренаж ~130/мин, бэклог 9.5k добивается за ~1 ч.

**Вывод по оптимуму под 5000/30k:**
- **3 реплики scraper** — устойчивый оптимум (~180/мин против ~107 = 1.7× запас).
- 4 — чтобы быстрее разгрести бэклог, потом можно вернуть 3. 2 — впритык.
- **Сервер сильно недогружен**: и CPU, и RAM с огромным запасом. «Занять» его
  этой нагрузкой нельзя — потолок **внешний** (латентность МП, антибот-лимиты,
  одна дорожка `ozon-miner`), не локальные ресурсы.

**Следующие пороги (не текущий):**
- **Ozon-товары** скрейпятся через дорожки `ozon-miner` — scraper-реплики их не
  ускорят. Рычаг — `OZON_POOL_SIZE`. ЗАМЕР 2026-07-20 (прод, 4 дорожки):
  `pt_ozon_miner` = 5.435 ГиБ, т.е. **~1.36 ГиБ на дорожку**, а не 4 ГБ, как
  тут стояло раньше (оценка была завышена втрое и отпугивала от расширения).
  Ограничение всё равно по RAM: на VPS 15.62 ГиБ выше ~8 дорожек считать вместе
  с Postgres/Kafka/воркерами. Прокси для расширения НЕ нужны — 4+ дорожки
  прогреваются с одного IP сервера и проходят FAB (см. memory proxy-strategy).
- **Доставка:** `pending_alerts_depth` держался ~130–150 из-за концентрации
  синтетик-алертов на паре тест-чатов (throttle), НЕ реальный потолок прода
  (реальные алерты расходятся по тысячам чатов). Реальный сигнал к Phase 2 —
  рост depth при РАЗМАЗАННОЙ по чатам доставке.
