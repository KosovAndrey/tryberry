# Промокод в платёжном флоу — модель, флоу, подводные камни

**Ветка:** `feat/checkout-promo` · **Дата:** 2026-06-23

## Когда промокод считается использованным (lifecycle)

Два типа кодов гасятся по-разному — это ключ ко всему:

| Тип | Что делает | Когда «использован» |
|-----|-----------|---------------------|
| **grant** (дни тарифа) | выдаёт N дней плана бесплатно | **сразу при вводе** (`RedeemGrant`: `used_count++`, UNIQUE `promo_redemptions(code,user)`, `promo_claims`). Один раз на юзера, навсегда. |
| **discount** (% на оплату) | скидка на оплату тарифа | **только после успешной оплаты** (`RedeemDiscount` в консьюмере `payment/apply.go`). До оплаты — НЕ потрачен. |

**Сколько «закреплён» discount за юзером:** код кладётся в Redis как «ожидающая
скидка» (`promo:discount:<userID>`) с TTL **24 часа** (`domain.PromoDiscountTTL`).
Снимается при оплате (`discounts.Del`) или по TTL. Перезапись новым кодом —
бесплатна (см. ниже).

**Смена 20% → 50%:** `discounts.Put` просто перезаписывает прежний код. Так как
discount гасится только при оплате, ни один из введённых кодов не «сгорает» до
оплаты — расходуется лишь тот, по которому реально заплатили. Значит последний
введённый код побеждает, менять можно сколько угодно, утечки нет.

## Что было сломано (репорт юзера)

1. **Ввод кода «в меню» не реагировал.** Кнопка `menu:promo` показывала статичный
   текст «отправь `/promo КОД`» — без FSM. Юзер жал кнопку, вводил голый код →
   ноль реакции (некому было его поймать).
2. **Скидка из меню не вела к оплате.** Даже через `/promo КОД` discount только
   молча клался в Redis с текстом «открой Тарифы» — без перехода.
3. **Нельзя было сменить код перед оплатой.** Кнопка промокода на карточке
   пряталась при уже применённой скидке (`pct == 0` в условии).
4. **Leak повторного использования (нашёл по ходу).** Гейт скидки на checkout
   (`discountUsable → Redeemable`) проверял только ГЛОБАЛЬНЫЙ лимит
   (`used_count < max_uses`), но не «этот юзер уже гасил». Так как discount
   гасится после оплаты, уже оплативший по коду юзер мог ввести его снова и
   заплатить со скидкой повторно: `RedeemDiscount` потом откатывался по UNIQUE
   (бухгалтерия чистая), но деньги уже списались со скидкой.

## Решение

**Единый ввод кода через один FSM** (`checkout_promo`, Redis, TTL 10 мин), три
точки входа сводятся в `applyPromoCode`:

- кнопка «🎟 Промокод» в меню (`menu:promo`) → ввод, возврат в список тарифов;
- кнопка на карточке тарифа (`plan:promo:<name>`) → ввод, возврат на карточку;
- `/promo` без аргумента → ввод; `/promo КОД` и deep-link — сразу применяют.

`applyPromoCode(code, returnPlan)`:
- **grant** → `applyGrantPromo` (дни сразу, как раньше);
- **discount** → пред-проверка `Redeemable(code, user)` (свободные активации **и**
  юзер ещё не гасил) → `discounts.Put` → **переход к оплате**: на карточку плана
  (`returnPlan != ""`) или в список тарифов (`""`) — уже со скидкой в цене;
- **не найден / уже использован** → просим другой код, FSM держим;
- распознан → FSM сбрасываем.

**Смена кода:** кнопка на карточке больше не прячется — при активной скидке
становится «🎟 Сменить промокод». Перезапись бесплатна (discount не потрачен).

**Закрытие leak:** `PromoRepo.Redeemable` теперь принимает `userID` и добавляет
`AND NOT EXISTS(SELECT 1 FROM promo_redemptions WHERE code_id=? AND user_id=?)`.
Этот гейт стоит и на checkout (`discountUsable`, путь денег — общий для TG и VK),
и при вводе кода (обратная связь сразу). Money-path защищён для обеих платформ
независимо от UX ввода.

## Подводные камни и как обошли

- **Голый текст во время FSM.** Пока ждём код, любой текст трактуется как промокод
  («такого нет, введи другой»). Выход — как у email-FSM: /menu или /plans сбрасывают
  (в `handleCommand` чистим `checkout_promo` FSM), плюс TTL 10 мин.
- **best-effort проверок.** Сбой БД в пред-проверке `Redeemable` НЕ блокирует ввод
  (показываем скидку), но финальный гейт на checkout всё равно отсечёт негодный код —
  тогда оплата пройдёт по полной цене (источник правды — экран оплаты, не карточка).
- **Карточка vs checkout по цене.** Карточка показывает скидку из Redis без
  проверки лимита (один лишний запрос на каждый показ — не нужен); реальную скидку
  подтверждает экран оплаты (`checkout.DiscountPct`). Пред-проверка на вводе
  делает рассинхрон редким.
- **grant + висящая скидка.** Если ввести grant (выдаст план), pending-скидка
  останется в Redis 24ч и применится к будущей оплате другого плана — это в пользу
  юзера, оставили как есть.
- **VK.** Ввод промокода в VK (`internal/vk/promo.go`) пока без пред-проверки
  «уже использовал» — но money-path (checkout) защищён общим гейтом. UX-паритет VK —
  отдельной задачей, если понадобится.

## Проверка на проде

```
/promo_create SALE20 discount 20 100        # создать код
```
1. **Меню:** 🎟 Промокод → ввести `SALE20` → должно прийти «скидка 20% применена» +
   список тарифов; карточка любого тарифа — цена со скидкой.
2. **Карточка:** тариф → «🎟 У меня есть промокод» → `SALE20` → карточка со скидкой.
3. **Смена:** на карточке «🎟 Сменить промокод» → ввести код на другой % → цена
   обновилась.
4. **Повтор:** оплатить со скидкой, затем снова ввести тот же код → «уже использован».
5. **Grant:** `/promo_create GIFT7 grant lite 7 100` → ввод в любом флоу → выдаёт дни.
