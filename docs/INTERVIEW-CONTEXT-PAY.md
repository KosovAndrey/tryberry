БИЛЛИНГ — ГЛАВНАЯ ТЕМА ДЛЯ ЭТОЙ КОМАНДЫ (отвечать этими фактами)
Провайдеры: ЮKassa и Робокасса за общим интерфейсом Provider (Checkout,
ChargeRecurring), переключаются конфигом. Переезд с ЮKassa на Робокассу уже
сделан — ради чеков НПД (я самозанятый).
Путь платежа: строка payments в статусе pending со своим ключом идемпотентности
→ ссылка на форму провайдера → вебхук → публикация события в Kafka (топик
payments, ключ user_id) → консьюмер применяет.
Применение оплаты — одна транзакция: условный переход
UPDATE payments SET status='succeeded' WHERE id=$1 AND status='pending'
RETURNING …, плюс SELECT … FROM users FOR UPDATE и продление плана.
Идемпотентность двухуровневая: наружу — заголовок Idempotence-Key при создании
платежа в ЮKassa (защищает деньги клиента от второго списания); внутрь —
условный переход статуса (защищает услугу от второй выдачи).
Best-effort после коммита: уведомление, активация/продление подписки, погашение
промокода, реферальная награда. Их сбой логируется и не откатывает оплату.
Подлинность вебхука: Робокасса подписывает ResultURL (MD5 от OutSum:InvId:
Password2) — подпись и есть источник доверия; ЮKassa не подписывает, поэтому из
тела берётся только id и статус перечитывается через API провайдера. Сверх
подписи проверяется существование платежа и совпадение суммы.
Подписки: активация только после явного согласия; шедулер Charger; отбор задач —
атомарный UPDATE billing_subscriptions SET next_charge_at = retryAt WHERE
next_charge_at <= now RETURNING …, то есть клейм и таймаут аренды одной
операцией; предупреждение о списании отдельным проходом с отметкой.
Dunning: интервал ретрая 24 ч, fail_count, active → past_due → expired.
Доступ не снимается при отказе карты — доживает до конца оплаченного периода.
Рекуррент без хранения карты: ключ рекуррента — InvId первого платежа
(recurring_invoice_id), карту не вижу, PCI DSS-область сужена.
Деньги — amount_kopecks int64, никакого float. Цены товаров — NUMERIC(12,2).
Чеки: у ЮKassa receipt в теле создания платежа (54-ФЗ), у Робокассы чек НПД;
у Робокассы подпись считается от СЫРОГО JSON чека — переупаковка её ломает.
Возврат и отмена разведены: отмена — доступ доживает до конца оплаченного
периода; возврат (админский revoke) — деньги назад и доступ снимается сразу.
Платежи не удаляются: каскад users → payments убрал бы записи, нужные для
отчётности по НПД.
Метрики: payments_created_total, payments_succeeded_total,
payment_revenue_kopecks_total — отсюда конверсия воронки.
Тесты: TestApply_IdempotentSkip, TestApply_SubRenewal, TestVerifyResult,
TestBuildPaymentURL_* — биллинг тестируется подменой провайдера, без сети.

ОСТАЛЬНЫЕ АРХИТЕКТУРНЫЕ ФАКТЫ
Гарантии: at-least-once во всех Go-сервисах, идемпотентность на уникальных
индексах — ключ уведомления sub:price:recordedAt. Exactly-once (EXACTLY_ONCE_V2)
включён только в price-insight; запись оттуда в Postgres идёт идемпотентным
апсертом, потому что транзакция Kafka на базу не распространяется.
Kafka: 1 брокер, RF=1, 10 партиций, retention 72 ч, ключ product_id.
Оффсеты в пуле коммитятся вотермарком непрерывного префикса.
Ошибки обработки: 3 попытки в последовательном консьюмере, дальше явный коммит
с логом, метрикой и алертом; в пуле ретраев нет, задача приедет на следующем
тике планировщика.
Доставка: durable outbox pending_alerts, отдельный флашер с бэкоффом и
бандлингом; лимитер 25 msg/s, токен тратится на пользователя.
Postgres: price_history партиционирована по месяцам, хранение change-only,
медиана считается взвешенной по длительности оконными функциями. Изоляция
везде Read Committed. Пул соединений на дефолте драйвера: 18 соединений в
покое при max_connections 100.
Graceful shutdown: SIGTERM отменяет корневой контекст, in-flight работа
обрывается, оффсеты сбрасываются фоновым контекстом. Это безопасно, потому что
задачи периодические и идемпотентные.
Проверки качества: линтер и тесты на pre-push хуке локально.
Тесты: домен и Kafka-консьюмер покрыты, SQL покрыт слабо; Testcontainers
используются на Java-стороне.
Бэкапы: pg_dump раз в сутки, хранение 7 дней.

ТЕМЫ, КОТОРЫЕ ВЫНОСИТЬ (по приоритету для этой команды)
1. Денежный путь и гарантии: два уровня идемпотентности, условный UPDATE как
   compare-and-set, что в транзакции и что best-effort после неё, две модели
   доверия к вебхукам, клейм в шедулере автосписаний, dunning.
2. At-least-once и идемпотентный приёмник: exactly-once доставки нет, есть
   effectively-once эффект — гарантия живёт в приёмнике, а не в транспорте.
   Дубликат возможен на любой стрелке провайдер → вебхук → Kafka → консьюмер,
   и каждый заканчивается повторным вызовом одного и того же условного апдейта.
3. Границы транзакции: почему внешний вызов нельзя завернуть в транзакцию БД,
   почему 2PC с провайдером не работает, что вместо атомарности — идемпотентность,
   фиксация намерения до внешнего вызова и сверка.
4. Данные врут при зелёных метриках: цена бралась из архивного файла и врала в
   97% при success rate 100%. Сторожем стала метрика происхождения данных.
   Для платежей это тот же принцип: метрика успеха не доказывает корректность.
5. Kafka-консьюмер: пул с семафором, вотермарк непрерывного префикса, инцидент
   с замёрзшей партицией после ребаланса и первый неверный диагноз.
6. Свежесть против нагрузки на источник (если зайдёт разговор про внешние
   интеграции вообще): частота считается — минимум по подписчикам плюс бэкофф
   по волатильности; три уровня троттлинга.

СЛАБЫЕ МЕСТА (называть самому)
В биллинге:
— Нет сверки платежей в статусе pending с провайдером. Потерянное подтверждение
  оставит человека без доступа, и узнаю я об этом от него, а не от мониторинга.
  Знаю, как чинить: проход по старым pending → GetPayment у провайдера → тот же
  идемпотентный путь применения.
— Нет метрики «возраст самого старого pending» — именно она поймала бы это.
— Подпись Робокассы сравнивается через strings.EqualFold, а не за постоянное
  время, хотя для телеграмного вебхука используется subtle.ConstantTimeCompare.
  Несогласованность на одну строку кода.
— Kafka стоит в денежном пути: событие публикуется до ответа 200, значит вебхук
  завязан на доступность брокера. Просился transactional outbox.
Общие:
— Единые точки отказа: один брокер Kafka и один Postgres без реплики, RPO сутки.
— SQL слабо покрыт тестами, самая сложная транзакция — слияние аккаунтов — не
  покрыта.
— В api оффсет Telegram двигается до публикации в Kafka, поэтому апдейты
  теряются при её сбое; задача заведена.
— N+1 в поиск-воркере: два запроса на каждый товар выдачи на каждую подписку,
  не замерено.
— pg_stat_statements не подключён, таймауты БД и размер пула не настроены.
