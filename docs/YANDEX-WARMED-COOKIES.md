# Я.Маркет: прогретые куки через прокси (спайк)

Задача из трекера: «проверить, можно ли для Я.Маркета тоже сначала через прокси
получать прогретые куки и потом делать запросы». «Тоже» = как сделали для
AliExpress (`internal/scraper/aliexpress.go`).

## Где мы сейчас

`YandexMarketScraper.Scrape` (`internal/scraper/yandex_market.go`) делает **один
холодный GET сразу по карточке** с пустым cookie-jar, всегда **через RU-прокси**:

- холодный старт (нет сессионных/антибот-кук) — самый «капчегенный» момент;
- **каждый** запрос карточки идёт через прокси → дорого по трафику прокси и по
  репутации одного IP (RPS держим низким именно поэтому).

Куки jar создаётся один раз в `newYandexTLSClient` и переиспользуется между
запросами в рамках процесса, но осознанного **прогрева** (зайти на безобидную
страницу за антибот-куками до карточки) нет.

## Гипотеза (паттерн AliExpress)

Ali закрыт антиботом X5SEC. Решение: два tls-client с **общим cookie-jar** —
`direct` (без прокси, датацентр-IP) основной + `proxy` (RU) только для разового
рефреша cookie при блоке. Один проход через прокси добывает сессионную cookie,
дальше API отдаётся напрямую с датацентра, пока cookie живы.

Для Я.Маркета антибот другой (SmartCaptcha / `spravka`), и проверить нужно две
вещи:

1. **Помогает ли прогрев вообще** — снижает ли GET homepage через прокси
   (получить `yandexuid`/`spravka`/`_yasc`/`i`) частоту капчи на последующем
   запросе карточки (`D warm→proxy` против `B proxy-cold`).
2. **Можно ли после прогрева ходить direct** — пройдёт ли карточка с
   датацентр-IP, если cookie добыты через прокси (`C warm→direct`). Если да —
   это и есть экономия прокси, как у Ali.

Открытый риск: у Яндекса `spravka`/SmartCaptcha-токен часто **привязан к IP**, на
котором выдан. Тогда `C` не пройдёт (cookie с IP прокси невалидны с датацентра), и
выигрыш сведётся к «прогрев на том же proxy-IP» (`D`) — всё равно полезно, если он
заметно режет капчу.

## Probe (`cmd/yandex-probe`)

Разовый эксперимент, **не часть прод-флоу**. На каждый URL прогоняет 4 сценария и
печатает таблицу: `status`, `blocked` (распознана SmartCaptcha), `product` (есть
JSON-LD Product), `price`, число cookie, для C/D — статус прогрева.

| код | прогрев | прокси на карточке | смысл |
|-----|---------|--------------------|-------|
| A cold-direct | нет | нет | baseline, ожидаем капчу с датацентра |
| B proxy-cold | нет | да | текущее поведение прода |
| C warm→direct | да (прокси) | **нет** | гипотеза экономии: прокси только за прогрев |
| D warm→proxy | да (прокси) | да | снижает ли прогрев капчу на proxy-пути |

Детекция капчи — те же маркеры, что в боевом `isYandexCaptcha` (сперва отсекаем
живую страницу приложения `@marketfront`/`data-baobab-name="$page"`).

### Запуск на VPS (там, где есть прокси)

```bash
docker build --build-arg SERVICE=yandex-probe -t yandex-probe .
docker run --rm -e YANDEX_PROXY_URL="$YANDEX_PROXY_URL" yandex-probe \
    "https://market.yandex.ru/card/<slug>/<sku>" \
    "https://market.yandex.ru/product--<slug>/<id>"
```

URL можно передать аргументами или через `-e YANDEX_TEST_URLS=url1,url2`.

## Как читать результат

- **C: blocked=no, product=yes, price есть** → гипотеза подтверждена, делаем
  схему direct+proxy с общим jar как у Ali (прокси экономим).
- **C блокируется, но D лучше B** (реже капча / стабильнее) → прогрев привязан к
  IP; внедряем прогрев на proxy-пути (без direct-экономии).
- **D не лучше B** → прогрев не помогает, гипотезу закрываем, оставляем как есть.

Прогнать желательно несколько раз и на 2–3 разных товарах (числа капчи шумные).

## Результат эксперимента (прод-IP, 2026-06-23)

Прогон probe на VPS (датацентр-IP `185.x`, прокси `185.189.132.213`):

- **4 сценария, 2 товара:** `A cold-direct`, `B proxy-cold`, `C warm→direct`,
  `D warm→proxy` — все `status=200`, `blocked=no`, `product=yes`, цена достаётся.
  То есть карточка отдаётся **direct с датацентр-IP без прокси и без прогрева**.
- **Нагрузка `PROBE_LOAD=100` direct (без прокси/прогрева):**
  `ok=100 blocked=0 priced=100`, **капчи ноль** — датацентр-IP держит поток.

Вывод: для Я.Маркета прокси на каждый запрос НЕ нужен; прогрев тоже не нужен
(холодный direct работает). Прокси осмыслен лишь как **fallback**, если IP однажды
начнёт ловить SmartCaptcha. (Колонка `price` в probe шумит — грубый «первый
сниппет» из стейта; боевой `parseYandexMarketHTML` берёт offers/SKU-якорь.)

## Что внедрено

Зеркало схемы AliExpress в `yandex_market.go` (+ `yandex_market_search.go`):

- два tls-client с ОБЩИМ cookie-jar: `direct` (основной, без прокси) и `proxy`
  (fallback, nil без `YANDEX_PROXY_URL`);
- `getWithFallback`: direct → при SmartCaptcha и наличии прокси один запрос через
  прокси (обновляет cookie в общем jar) → дальше снова direct;
- метрика `tg_price_bot_yandex_price_source_total{source=direct|proxy}` — рост доли
  `proxy` = датацентр-IP начал капчиться (сигнал, что пора менять IP/прокси);
- боевой парсер карточки/выдачи не тронут; прогрев не добавляли (не нужен).

Прокси-переменные (`YANDEX_PROXY_URL`→`OZON_PROXY_URL`) оставлены: теперь это
страховка, а не основной путь. `cmd/yandex-probe` остаётся для перепроверки, если
IP начнёт ловить капчу.
