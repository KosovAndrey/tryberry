# INTERVIEW-RAG — заметки для подсказки на собеседовании

Файл собран под вставку в RAG-подсказку (sobes.tech и подобные). Формат подчинён
поиску, а не чтению подряд.

**Правила формата — соблюдать при дописывании:**

1. **Одна карточка = один вопрос.** Заголовок содержит несколько живых
   формулировок, как это спросит человек, — по ним и найдётся.
2. **Карточка самодостаточна.** Никаких «как сказано выше»: в чат попадёт только
   она одна, без соседей.
3. **Ответ начинается с сути.** Первая строка — то, что можно произнести сразу.
   Дальше детали, ссылки на файлы, цифры.
4. **Числа с пометкой.** `[замер]`, `[счёт]`, `[оценка]` — чтобы не выдать
   догадку за измерение.
5. **Коротко.** Карточка длиннее 15 строк не читается взглядом во время
   разговора.

> **Про сам приём.** Держать здесь числа, названия файлов и неудобные вопросы —
> полезно. Держать готовый текст рассказа о проекте — вредно: пауза на чтение и
> ровная интонация слышны, и это ровно та ошибка, что была на прошлых собесах.
> Рассказ надо знать, подсказка — для точности.

## Путь одного изменения цены: от тика планировщика до сообщения

*«Расскажи путь данных», «что происходит, когда цена меняется», «как устроен основной поток»*

Четыре звена, и у каждого свои часы только у первого.

1. **scheduler**, тик 20 с: читает `products × subscriptions × users`, интервал
   товара = минимум по подписчикам + волатильностный бэкофф, отбирает созревшие
   по `last_enqueued_at`, помечает `ClaimEnqueued` **до** отправки, шлёт в
   `scrape-tasks` (Ozon — в отдельный топик). Ключ = `product_id`.
2. **scraper** ×3 реплики: `RunConcurrent` с семафором 8 (Ozon 6), скрейпит,
   пишет цену в Postgres change-only и в Redis, публикует `PriceEvent`
   **на каждом скрейпе**.
3. **notifier** (последовательный): по товару достаёт всех подписчиков одним
   запросом, для каждого throttle по тарифу → `Decide` → идемпотентность →
   `Insert` в outbox `pending_alerts` с `deliver_after = now + BundleWindow`.
4. **flusher**, тик 1 с: `FetchDue` → группировка по юзеру → один токен
   лимитера (25 rps) на юзера → один алерт богато с фото, ≥2 — бандлом.

## Почему PriceEvent публикуется на КАЖДОМ скрейпе, а не только при смене цены

*«190 тысяч событий в сутки, зачем?», «почти все события впустую», «публикуйте только на изменение»*

Потому что событие здесь — не только данные, но и **тик расписания**.

У notifier нет своих часов: подписка оценивается только когда пришло сообщение
по её товару. Тарифная частота — фильтр поверх потока (`shouldEvaluate`,
`cmd/notifier/main.go:599`). Фактическая частота оценки = **минимум** из «что
разрешает тариф» и «как часто приходят события». Публикуй только на смене — у
стабильного товара событий нет неделями, минимум станет недельным, и тариф
перестанет ограничивать вообще.

**Честная цена решения:** топик перестал быть архивом. При retention 72 ч назад
проигрывается трое суток, поэтому стейт price-insight нельзя пересобрать
проигрыванием топика.

**Альтернатива, которую я не замерял:** pull — `next_eval_at` на подписке +
`FOR UPDATE SKIP LOCKED`. Дизайн: `docs/NOTIFIER-PULL-MODEL.md`.

## Redis умер. Что перестало работать

*«что если упадёт Redis», «отказ кэша», «насколько критичен Redis»*

**Умерло совсем:**
- **WB-поиск** — пул `x-search-token` живёт только в Redis, токен выдаёт браузер,
  восстановить на лету нечем (`token_pool.go:83` возвращает `redis unavailable`);
- **диалоги** — FSM (`search_fsm:`, `vk_track_fsm:`, `vk_email_fsm:`,
  `vk_promo_fsm:`, `vk_merge_fsm:`): ввод порога, поисковый запрос, email для
  чека, промокод, слияние аккаунтов;
- **привязка аккаунтов** (`link:`) и **отложенная скидка** (`promo:discount:`).

**Просело, но работает:** цена (`price:` → фолбэк на `price_history`), шарды
basket WB (перебор 25 шардов ≈ 10 с), conditional GET WB (каждый скрейп полный).

**Не заметило:** весь основной конвейер. Слежение за ценой и доставка алертов
работают — ломается вход, а не наблюдение.

**Что сказать в конце:** деградация продумана — сервисы стартуют без Redis
(`log.Warn("redis unavailable")`), ни одна потеря не является потерей данных.
Одно исключение назвать самому: пул токенов — не кэш, а единственная копия,
восстановление до 48 ч. Ему место в Postgres, задача заведена.

## Kafka упала. Что происходит

*«что если брокер умрёт», «один брокер — не страшно?», «сколько проживёте без Kafka»*

**Первым ломается вход, и это худшее.** Прод на long-polling. В
`internal/telegram/receiver.go:147-151` оффсет сдвигается **до** публикации, а
`publish` при ошибке только логирует (`cmd/api/main.go:127-129`). Значит каждое
сообщение пользователя теряется безвозвратно — Telegram не пришлёт повторно.
Дыра известна, задача заведена, фикс — двигать оффсет после успешного `Send`.

**Контраст, где сделано правильно:** платёжный вебхук отдаёт `500` и Робокасса
повторяет (`cmd/api/main.go:421-425`), VK так же. Разница в том, что у поллинга
нет отправителя, который повторит, — курсором управляем мы.

**Дальше:** флашер дренирует `pending_alerts` за минуты и замолкает; цены не
обновляются; оплата зависает в `pending`.

**Восстановление ступенчатое:** планировщик всё падение продолжал ставить
`last_enqueued_at = NOW()`, а `Send` падал. Товары помечены как поставленные в
очередь, поэтому после возврата брокера ждут полный интервал — до 6 часов у free.

**Данные целы:** все записи идемпотентны, оффсеты некоммитнутые перечитаются.

## Postgres недоступен. Что теряется

*«что если база ляжет», «нет реплики?», «какой у вас RPO»*

Останавливается всё: планировщик не может выбрать созревшие, скрейпер не может
записать цену, notifier не может достать подписки, флашер не может забрать
outbox. Kafka при этом копит задачи — конвейер не теряет их, а откладывает.

Потери при коротком сбое: события, у которых хендлер вернул ошибку 3 раза
(`handlerRetryBackoff`, 3 попытки по 500 мс) — они коммитятся явно с метрикой
`kafka_messages_consumed_total{status="dropped"}`. Восстановление даёт следующий
плановый скрейп.

**Честно про надёжность:** один Postgres без реплики, RPO = сутки (дамп) плюс до
6 часов до S3, restore проверен 04.07.2026 [замер]. Целевых RTO/RPO нет — это
записано как незакрытый вопрос.

## Как коммитятся оффсеты. Вотермарк непрерывного префикса

*«как вы коммитите», «что если обработка не по порядку», «как не потерять сообщение при параллельной обработке»*

**Вотермарк непрерывного префикса** на партицию (`internal/kafka/consumer.go:236`):
коммитим наибольший оффсет, ниже которого все обработаны без дырок. Обработали
10, 11, 13 → коммитим 11; закончился 12 → вотермарк прыгает на 13.

Батч-коммит раз в 500 мс (`commitFlushInterval`) — чтобы не делать RPC на каждое
сообщение; окно потери ≤500 мс.

По-английски: *offset watermark* / *low-water mark*, паттерн — *out-of-order
acknowledgement with gap tracking*.

**История:** трекер дважды ломался. Второй раз причина была в ребалансе — после
него партиция приходит заново, оффсета `cursor` прошлой генерации больше не
будет никогда, и `complete` навсегда упирался в отсутствующий `done[cursor]`.
Фикс: `register` детектит разрыв и пересинхронизирует курсор. Плюс метрика
`kafka_partition_stuck_seconds` и алерт.

## Где у вас конкурентный консьюмер и почему не везде

*«обрабатываете параллельно?», «почему notifier последовательный», «worker pool»*

`RunConcurrent` — **только в скрейпере** (`cmd/scraper/main.go:254-255`, семафор
8 и 6 для Ozon). Все остальные консьюмеры последовательные: notifier,
bot-worker, search-worker, reseller-worker.

**Почему пул нужен скрейперу:** обработка = поход в маркетплейс, от полусекунды
у WB до 3–5 секунд у Ozon через браузер. Работа latency-bound, без пула реплика
простаивала бы на ожидании сети.

**Почему notifier без пула, и это не про синглтонность:**
1. не нужно — обработка это запрос в Postgres, миллисекунды, при 2,2 события/с
   загрузка в процентах;
2. **опасно** — у notifier read-modify-write: читает `baseline_price`, решает,
   перезаписывает. Два события одного товара параллельно дают lost update и
   двойной алерт (ключ идемпотентности не спасёт — в него входит `recorded_at`,
   а он разный).

Синглтон notifier — отдельная причина: внутри четыре фоновые петли (реконсилер,
дайджест, флашер, win-back), не рассчитанные на несколько инстансов.

## Ретраи в консьюмере и почему нет DLQ

*«что если обработка упала», «dead letter queue есть?», «сколько раз повторяете»*

В последовательном `Run` — 3 попытки с паузой 500 мс, потом **явный commit** с
громким логом, метрикой `dropped` и алертом `KafkaMessagesDropped`. В
`RunConcurrent` ретраев намеренно нет: в пуле ретрай держал бы слот и морозил
вотермарк.

**Почему не бесконечный ретрай:** консьюмер последовательный, вечный ретрай
останавливает партицию, а событие не уникально — следующий скрейп даст новое.

**DLQ нет нигде**, и ценность его разная по топикам:
- `scrape-tasks`, `price-events` — низкая, событие регенерируется;
- `telegram-updates` — средняя, сообщение пользователя уникально;
- `payments` — **высокая**: платёж применяется bot-worker'ом, при трёх неудачах
  сообщение выбрасывается, строка остаётся `pending`, деньги списаны, а
  реконсилера зависших платежей нет. Правильнее DLQ здесь периодическая сверка
  `pending`-платежей с провайдером.

DLQ неприменим к планировщику — он чистый продюсер, ничего не потребляет.

## Идемпотентность: где и чем обеспечена

*«как не задваиваете», «повторный вебхук», «at-least-once и дубликаты»*

**Принцип: на констрейнтах базы, а не в коде.**

- `payments.idempotence_key` + условный `UPDATE ... WHERE status='pending'
  RETURNING` — проходит только первый, это и есть идемпотентность вебхука
  (`internal/repository/postgres/payment.go:112`);
- `notifications.idempotency_key` = `subID:price:recordedAt`;
- `pending_alerts.idem_key` + `ON CONFLICT DO NOTHING`;
- `promo_redemptions(code_id,user_id)`, `referral_rewards(referee_id,event)`,
  `trial_claims(platform,external_id)`.

**Правило, которое стоит произнести:** при at-least-once побочный эффект должен
случаться **до** изменения состояния. В notifier так и есть: алерт кладётся в
outbox раньше, чем двигается baseline, поэтому повтор безопасен в обе стороны.

## Три уровня троттлинга

*«как ограничиваете частоту», «тарифы как реализованы», «почему не спамит»*

Развести обязательно, спрашивают именно про смешение:

1. **Каданс скрейпа** — минимум по подписчикам товара, плюс волатильностный
   бэкофф ×1/×1.5/×2/×3 по возрасту последней смены цены (границы 5/10/20 дней),
   кап ×2 при ≥5 подписчиках, к reseller не применяется.
2. **Каданс оценки подписки** — `last_evaluated_at` + интервал тарифа
   (`shouldEvaluate`): доставка строго по плану подписчика, даже если товар
   скрейпится чаще из-за соседа с дорогим тарифом.
3. **`Plan.SearchCooldown`** — анти-спам `below_target`: 6 ч free, 2 ч lite, 1 ч
   pro, **выключен** у reseller через `CooldownOff = -1s` (ноль уже значил
   «фолбэк на env-ручку», нужно было отличать «выключено» от «не задано»).

## Бандлинг и порядок доставки. Не голодают ли дешёвые тарифы

*«в каком порядке шлёте», «что если алертов больше лимита», «приоритеты у платных?»*

**Приоритет реализован не в порядке выборки, а в `deliver_after`.**
`Plan.BundleWindow()` (`internal/domain/plan.go:152`): reseller и unlimited — 0,
pro и trial — 5 мин, lite — 10, free — 15. `FetchDue` берёт
`ORDER BY deliver_after, id` — FIFO **поверх** приоритета.

**Голодания нет по построению:** алерт free всё равно созреет через 15 минут и
встанет в очередь по своему времени, а не по тарифу. Классический приоритет
(«сначала все reseller») уморил бы дешёвые тарифы, здесь так не выйдет.

**Смысл окна — склейка, не приоритет:** у пользователя подешевело 20 товаров —
уходит одно сообщение со списком вместо двадцати, и один токен лимитера вместо
двадцати. Лимитер тратит **токен на пользователя, а не на алерт**
(`cmd/notifier/flusher.go:84`), то есть потолок — 25 получателей в секунду.

**При перегрузе окна надо увеличивать**, а не уменьшать: больше склейки, меньше
сообщений, информация не теряется. Backpressure схлопыванием.

## Зачем outbox, почему не слать из консьюмера напрямую

*«что за pending_alerts», «transactional outbox», «что если доставка не удалась»*

Решение и доставка разведены. Notifier решает и кладёт строку в
`pending_alerts`; флашер тиком раз в секунду забирает созревшие и отправляет.

**Зачем:** мессенджер медленный и ненадёжный, а консьюмер последовательный —
отправка из хендлера держала бы партицию на время сетевого вызова к Telegram.

**Ретраи:** экспонента от 5 с до потолка 30 мин, до 10 попыток
(`cmd/notifier/flusher.go:58-67`), `attempts` и `last_error` в строке.

**Известный размен:** доставили, а `MarkSentBatch` упал → на ретрае дубль.
Принято осознанно, в коде записано прямо (`flusher.go:204-206`).

## Что если событий станет в 1000 раз больше

*«как масштабировать», «200 миллионов событий», «где узкое место»*

**Сначала правильный вопрос: выросли данные или шум?** Шум схлопывать ближе к
источнику, данные шардировать.

**Аргумент, который решает половину:** выход ограничен лимитом мессенджеров и не
масштабируется вообще. Значит при росте входа в 1000 раз работа обязана
схлопнуться где-то по пути.

**Первым упрётся не Kafka, а notifier** — последовательный, запрос в Postgres на
событие; потолок одного инстанса порядка 1000/с [оценка, не замер].

Варианты по возрастанию радикальности: реплики (партиций 10) → убрать запрос с
горячего пути (подписки в co-partitioned KTable через CDC/Debezium) → батч с
дедупликацией по `product_id` → развернуть на pull → шардирование.

## Как схлопнуть N запросов к БД в один

*«батчинг», «слишком много запросов», «оптимизация обращений к базе»*

Копим сообщения 200 мс, схлопываем в `map[product_id]Event` (повтор перетирает
предыдущий), делаем **один** `WHERE product_id = ANY($1)` вместо N.

**Два независимых выигрыша:**
- **А:** N round-trip'ов → 1. Работает даже когда все товары разные — у запроса
  есть фиксированная цена (сеть, разбор, планирование) ~0,3–1 мс.
- **Б:** дедупликация. Работает, только если товар попал в окно дважды.

**Честно: сейчас не даёт ничего** — при 2,2 события/с в окне 200 мс меньше
одного события. Инструмент под рост.

**Цена:** шире окно потери оффсетов, битое сообщение отравляет батч, +200 мс
латентности.

## Как убрать запрос к БД с горячего пути

*«слишком часто ходите в базу», «кэшировать подписки?», «CDC»*

Подписки должны лежать рядом с обработчиком: **Debezium** читает WAL Postgres →
топик с ключом `product_id` → **KTable** (физически RocksDB + changelog-топик для
восстановления) → co-partitioned join с потоком цен. Запросов на горячем пути
ноль.

**Почему WAL, а не опрос таблицы:** поток изменений без гонок — подписка,
созданная секунду назад, приезжает в стейт сама.

**Цена:** ещё один сервис, eventual consistency, схема таблицы становится
публичным контрактом.

**Честный финал:** «делал в другом проекте, здесь не нужно — 2,2 события в
секунду не оправдывают Debezium».

## Почему price-insight на Java и почему его результат не читают

*«зачем второй язык», «что делает JVM-сервис», «зачем сервис, если он не используется»*

**Говорить первым, не дожидаясь вопроса:** результат пока не читает никто,
сервис на проде в режиме наблюдения.

Держит по товару сегментное состояние цены в Kafka Streams, инкрементально
считает `min30/median30/min90/minAll` и те же правила вердикта, что Go.

**Замеры:** 13.08 — 99,3% совпадений вердикта на 4933 товарах [замер]; 21.08 —
98,8% на 4711 [замер]. Логика портирована верно.

**Почему не переключаю:** 21.08 переключение соврало бы 1583 товарам, из них 937
получили бы ложный `lowest_ever`. Причина не в коде, а в глубине истории — у Go
в среднем на 42,5 дня больше плюс бэкфилл архива WB, которого в топике не было
никогда.

**Неожиданное:** ожидание не помогло, а навредило — за неделю ≈1796 товаров
перешагнули 7-дневный гейт достаточности и заговорили, не став информированнее.
Гейт поднят до 14 дней в обеих реализациях.

## Почему Processor API, а не Kafka Streams DSL

*«почему низкоуровневый API», «DSL бы не подошёл?»*

**Из-за пунктуатора.** У DSL нет хука на излучение по таймеру, а он нужен
принципиально: окно едет само, и вердикт стабильного товара протухает молча.
`context.schedule(6h, STREAM_TIME, ...)`.

**STREAM_TIME, а не WALL_CLOCK:** при переигрывании топика с начала настенное
время дало бы один тик на всю историю.

**Важно сказать самому:** раньше я объяснял это иначе — что time-weighted медиана
не выражается через DSL, — и это было **неверно**: `groupByKey().aggregate()` с
собственным `Aggregator` удержит какое угодно состояние. Аргумент исправлен.

## Контейнер убивают по OOM, а heap не переполнен. Как

*«heap vs off-heap», «почему JVM в контейнере падает», «зачем BoundedMemoryRocksDBConfig»*

Kafka Streams заводит **отдельный экземпляр RocksDB на каждую партицию** входного
топика, у каждого свой block cache 50 МБ и три memtable по 16 МБ. На десяти
партициях это ≈1 ГБ **вне heap** — весь лимит контейнера.

Heap живёт по `MaxRAMPercentage` и о внешней памяти не знает, поэтому процесс
молча упирается в cgroup-лимит и его убивает OOM-killer, а heap при этом
полупустой.

**Решение:** один `static LRUCache` и один `WriteBufferManager` на процесс
(Streams создаёт по объекту config-setter'а на каждый store, общий потолок иначе
не выразить), memtable учитываются в том же кэше. Потолок 128 МБ.

**Факт на проде:** 460 МБ после бэклога → 309 МБ после GC, три замера подряд
[замер 13.08], лимит контейнера 1 ГБ.

## Что в проекте самое слабое

*«что бы улучшил», «что не нравится», «какие технические долги»*

Называть самому, не дожидаясь, пока найдут:

1. **Один брокер Kafka, RF=1, один Postgres без реплики.** Падение = остановка
   конвейера. Целевых RTO/RPO нет.
2. **SQL почти не покрыт тестами** — 1 файл на 20 в `repository/postgres`, 0 из 5
   в `repository/redis`. Самая сложная транзакция проекта (`MergeAccounts`, ~15
   операций) не покрыта; покрыта только чистая функция выбора тарифа. При этом на
   Java-стороне Testcontainers есть — асимметрия, которую заметят.
3. **CI невозможен** — раннеры GitLab требуют верифицированный аккаунт, из РФ не
   проходит. Гейт `make check` на pre-push, обходится `--no-verify`.
4. **Апдейты Telegram теряются при сбое Kafka** — оффсет двигается до публикации.
   Нашёл сам, задача заведена.
5. **N+1 в поиск-воркере** — `evaluateSubscription` делает 2 запроса на каждый
   товар выдачи на каждую подписку; при 300 позициях и 3 подписчиках 1800
   round-trip'ов. Не замерено.
6. **`ttlCache` в api не вытесняется** — TTL проверяется только на чтении,
   удаления нет; краулер по sitemap (до 5000 URL) заполнит его целиком.

## Самый сложный баг

*«расскажи про сложный баг», «как искал проблему», «что было трудно»*

**Цена WB бралась из архива и врала в 97% при success rate 100%.**

Скрейпер брал последнюю точку из `price-history.json` на basket-CDN. Метрики
идеальные: файл скачивается, антибота нет, `status="success"` — 100%. Но
последняя точка архива отстаёт на дни.

**Почему не ловилось метриками:** ошибки нет — есть неправильный ответ. Нашёл
глазами, сверкой с сайтом.

**Что делал:** браузерный путь провалился дважды — навигация ~14 с при спросе
4,2/мин = 100% загрузки одной дорожки, а молотилка попыток забанила наш IP у
wbaas и уронила заодно WB-поиск. Выбрал `u-card` через xray — он уже работал на
трансграничных товарах (646 успехов в проде), то есть расширял работающий путь,
а не проверял гипотезу.

**Результат:** 90% живых цен вместо 3%. Сторож — метрика **происхождения** цены
`wb_price_source_total{source}`, не success rate.

**Мораль:** success rate не ловит неправильный ответ. Нужна метрика того, откуда
взялись данные.
