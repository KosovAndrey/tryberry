# Ozon — статус интеграции (журнал + точка возобновления)

Ветка: **`feat/ozon-scraper`** (всё запушено в origin/GitLab).
Дата последней работы: **2026-06-15**.

## Цель
Получать цену/название/картинку товара Ozon по URL (как WB), для трекинга в боте.
Ограничение пользователя: **без браузера на каждый скрейп**, дёшево, масштабируемо.

## ИТОГ ОДНОЙ СТРОКОЙ
**РАБОТАЕТ end-to-end в проде (2026-06-15).** Путь B: аккаунт-cookie + `composer-api.bx`
+ okhttp (`Okhttp4Android13`) + RU-мобильный прокси. Боевые `/track` и регулярный
мониторинг (`pt_scraper`) отдают цену+имя+картинку — проверено на нескольких товарах,
включая 18+ (после подтверждения возраста на аккаунте). Осталась эксплуатационная
обвязка (постоянный прокси, авто-рефреш токена, отдельный аккаунт, метрика) — см. ниже.

## Что пробовали и что получилось (хронология)

| Подход | Результат | Почему |
|---|---|---|
| Чистый Go (`net/http`/curl) + composer/entrypoint API | ❌ 403 FAB | палится по TLS-отпечатку |
| Go `tls-client` (okhttp/Chrome профиль), аноним | ❌ `fab_nmk_` на датацентре, `fab_chlg_` на мобильном | FAB бьёт по TLS + репутации IP |
| Браузер-майнер (Patchright+Xvfb) добывает `__Secure-ETC` с главной → Go реюзает | ❌ | анонимный ETC с главной FAB не принимает для API товара |
| web-эндпоинт (`entrypoint-api.bx`, Chrome-TLS) + анонимный ETC | ❌ `fab_cp_` (даже при стабильном IP) | токен признан, но запрос режут |
| in-page `fetch` из прошедшей FAB главной | ❌ 403 | FAB валидирует каждую навигацию, не сессию |
| Реальная навигация браузера на `/product/<id>` | ❌ «Antibot Captcha» (и на свежем IP) | фингерпринт Chromium-в-Xvfb + пул палятся |
| **Аккаунт-cookie (путь B): `OZON_COOKIE` из приложения + composer-api + okhttp + RU-мобильный прокси** | ✅ **FAB ПРОЙДЕН** (ошибка стала «price not found», т.е. 200 widgetStates) | доверенная сессия залогиненного аккаунта + хороший IP |
| Тот же аккаунт-cookie, но датацентровый IP сервера (без прокси) | ❌ `fab_chlg_` | **аккаунта мало — FAB также гейтит по IP** |
| xray/wireguard как RU-выход | ❌ (не пробовали до конца) | наш wg/xray — **немецкий**, для Ozon бесполезен |

## Что РАБОТАЕТ и почему
- **Путь B**: cookie-строка из **приложения** (HTTP Toolkit) в `OZON_COOKIE` (содержит
  `__Secure-access-token`/`refresh-token`/`__Secure-user-id`/`abt_data`) +
  эндпоинт `https://api.ozon.ru/composer-api.bx/page/json/v2?url=/products/<id>/?layout_container=pdppage2copy&layout_page_index=1`
  + TLS-профиль `Okhttp4Android13` + заголовки приложения (`x-o3-*`, `MOBILE-GAID`) +
  **RU-мобильный прокси** → FAB пропускает, отдаёт `widgetStates`.
- Эталон — репо `Churkashh/ozon-pinneaples` (тоже под залогиненным аккаунтом).

## Что НЕ работает и почему (ключевые выводы)
- **Анонимно — никак**: FAB упирает в `fab_chlg_`/капчу даже на свежем мобильном IP.
- **Аккаунт-cookie сам по себе недостаточен**: FAB проверяет И сессию, И **IP**.
  Нужен **RU-мобильный/резидентский** IP. Датацентр (в т.ч. IP сервера, наш немецкий wg) — режется.
- **`layout_page_index=2`** грузит вторичный контент (характеристики/описание/рекомендации) —
  **цены там нет**. Цена на `layout_page_index=1`.
- **18+ товары** (нож, алкоголь и т.п.) Ozon прячет за возрастным гейтом: в `widgetStates`
  цены нет → `price not found`. Лечится **подтверждением 18+ в настройках аккаунта**
  (мы ходим под его сессией) — код менять не нужно.
- **Маркеры 18+/login (подстроено по реальному ответу 20.06):** на живом аккаунте 18+
  подтверждён → даже табак/нож отдают цену (`has ₽: True`). Снятый ответ вскрыл МИНУ:
  глобальный «хром» страницы есть на ЛЮБОЙ карточке и несёт слова-ловушки — `catalogMenu`
  всегда содержит ссылку «Товары для взрослых» (`adult`), `horizontalMenu` — «Ozon Банк»
  (`/fintech/signin`). Старый `isOzonAgeGated` матчил `«для взрослых»` → при любом
  `price==0` (OOS/промах парсера) товар ложно получал `ErrAgeRestricted`. Фикс:
  (1) `hasOzonProductCard` — если виджеты карточки на месте, это НЕ гейт; (2) маркеры
  гейтов пропускают «хром» (`isOzonChromeWidget`) и не матчат широкое `«для взрослых»`.
  Настоящую сигнатуру гейтов вживую так и не сняли (аккаунт здоров) — снять при первом
  реальном логин-/age-инциденте (диагностика `price not found` дампит имена виджетов).
  Снять ответ повторно: `scripts/ozdump.sh '<url>'` на ВПС.

## Реальная структура данных (как парсим, проверено 2026-06-15)
- **Цена**: виджет `price-*` → объект `price` → массив `price.price[]` из
  `{"text":"202 ₽","textStyle":"PRICE|ORIGINAL_PRICE|CARD_PRICE"}`. Берём по `textStyle`:
  `PRICE` (текущая) → `CARD_PRICE` → `ORIGINAL_PRICE`. (Старый плоский поиск — фолбэк.)
- **Имя**: мобильный API кладёт заголовок в `navTitle-*` (web — `webProductHeading-*`).
  Выбор заголовка **стабилизирован** (20.06): виджеты перебираем по фикс. приоритету
  имени (`navtitle`→`productheading`→`heading`→`title`) с сортировкой ключей, а title
  внутри ищем shallowest-first — выделенный заголовочный виджет всегда побеждает
  посторонние (секции/табы/хлебные крошки), и один и тот же ответ всегда даёт один и
  тот же заголовок (убран рандом range-по-map). Остаточная A/B-разница текста между
  РАЗНЫМИ запросами Ozon — не критично.
- **Картинка**: продуктовые фото на `ir.ozone.ru/.../multimedia-…`; ищем URL с `multimedia`
  (отсекает иконки банков `payments-cdn` из ценового виджета), приоритет `coverImage`.

## Состояние кода (готово, собрано, тесты зелёные)
- `internal/scraper/ozon.go` — `OzonScraper`:
  - account-режим (`OzonOptions.Cookie` или `AccessToken`/`RefreshToken`) — без Redis/майнера;
  - ETC-режим (через Redis + `ozon-miner`) — запасной;
  - mobile (`composer-api.bx`+okhttp) по умолчанию, web — за флагом;
  - **устойчивый парсер** `widgetStates`: рекурсивный поиск полей `price`/`cardPrice`/
    `originalPrice`, `title`/`text`, `coverImage`/`src` — не завязан на точные имена виджетов;
  - на FAB/неудаче логирует диагностику (`incident`, `minted_ip`/`current_ip`, `priceKey`/`priceRaw`),
    токены/cookie в логи НЕ пишет (только `cookie_len`).
- `ozon-miner/` — сайдкар Patchright+Xvfb (для ETC-пути; для пути B не нужен).
- ENV (в `.env`, секреты вне git): `OZON_COOKIE`, `OZON_PROXY_URL`, `OZON_API_MODE` (mobile),
  опц. `OZON_ACCESS_TOKEN`/`OZON_REFRESH_TOKEN`. Проброшены в `cmd/scraper` и `cmd/bot-worker`,
  в `docker-compose.yml`.
- `/track` в боте скрейпит синхронно через `bot-worker`; регулярный мониторинг — через
  `scheduler` → `scrape-tasks` → `pt_scraper` (ВАЖНО: при смене кода/прокси пересоздавать
  **оба** сервиса + `scheduler`, иначе крутят старый образ/старый env).
- **Пол интервала Ozon**: `OZON_MIN_INTERVAL_MINUTES` (дефолт 20) в `scheduler` —
  Ozon-товары не скрейпим чаще даже у `reseller_pro` (1 мин). WB — на тарифном кадансе.

## ИНЦИДЕНТ 15–16.06: FAB-челлендж на каждом скрейпе (не токен!)

Алерт `HighScrapeErrorRate` по ozon каждые ~20 мин (= пол интервала скрейпа). В логах
`pt_scraper` КАЖДЫЙ запрос = `403 + incident fab_chlg_*`. Диагностика:
- **Не протухший токен**: 401/логин-гейт дали бы статус `auth` + критикал `ScrapeAuthExpired`
  (чувствит., `increase>0` за 10м) — его НЕ было. Токен аутентифицирует.
- **Не (только) IP**: сменили мобильный IP по ссылке-switch (`31.173.84.24 → 178.176.74.157`) —
  первый же запрос на свежем IP опять `fab_chlg_`.
- **Вывод**: протух **FAB-доверие самой cookie-сессии**. В `OZON_COOKIE`, снятой из приложения
  14–15.06, был «решённый FAB»-стейт (свежий `abt_data`/challenge-pass куки); у него TTL
  (~сутки-двое) → истёк → FAB челленджит каждый запрос независимо от IP.
- Почему звенел только мягкий `HighScrapeErrorRate`, а не `MarketplaceBlocked`: за цикл падает
  ~4 запроса (по числу Ozon-товаров), а порог `MarketplaceBlocked` = `increase{blocked}[5m]>5`.

**Лечение (на сейчас, выключили):** `OZON_MIN_INTERVAL_MINUTES=100000` в `.env` + recreate
scheduler — Ozon-товары не enqueue’ятся, алерт гаснет за 5–7 мин. Вернуть = убрать строку.

**Стратегическое решение (16.06):** Ozon нужен к запуску → ручной рефреш cookie не годится.
Строим **браузер-как-транспорт с пулом дорожек** (фаза 2). Авто-рефреш по `refresh-token`
(п.2 выше) проблему НЕ закрывает — он про access-token, а протухает FAB-стейт; его освежает
только живой браузер/приложение, решая `challenge.html`.

### КОНСТРАЙНТ ПРОКСИ (узнал 16.06): только ОДИН IP в один момент

Текущий мобильный прокси отдаёт **один IP за раз** (sticky), смена — по ссылке-ротации.
Следствия для масштабирования:
- **Два браузера на одном IP** — НЕ масштаб: FAB видит один IP, общий rate выше → быстрее
  выгорает. Смысла нет.
- **Throughput-масштаб = больше одновременных IP = больше прокси-подписок** (по SIM на дорожку).
  Внутри дорожки — flat; стоимость линейна по прокси.
- **Идея Андрея (тайм-мультиплекс + ротация):** один IP за раз — браузер/аккаунт A скрейпит
  батч на IP1 → ротация ссылкой → IP2 → браузер/аккаунт B скрейпит батч → … «1 IP на 1 сессию
  скрейпа». Это НЕ повышает throughput (один IP-канал, серийно), но: (а) размазывает нагрузку
  по аккаунтам → меньше per-account бан-риск; (б) каждый IP делает короткий бурст и сменяется →
  меньше выгорание IP (как было 15.06 на долгом sticky + дележе с WB-майнерами). Хороший рычаг
  ЖИВУЧЕСТИ на одном прокси.
- Смена IP под живым браузером для account-cookie пути OK (auth не привязан к IP), НО FAB-пропуск
  привязан к IP → после ротации браузер надо **перепрогреть** (заново пройти FAB на новом IP).
  Если залогиненный браузер решает молча — проблем нет (реальная мобильная сессия тоже меняет IP).
  Ротировать НЕ во время запроса в полёте.

**Правка скелета под это (TODO):** текущий `server.py` запускает дорожки ПАРАЛЛЕЛЬНО (по прокси
на дорожку) — это режим «много прокси». Для одного прокси нужен режим **rotation**: серийный
планировщик дорожек + вызов switch-link между дорожками + перепрогрев. Заложить флагом
(`OZON_LANE_MODE=parallel|rotation`, `OZON_PROXY_ROTATE_URL`). На сейчас (≈6 товаров) хватит и
N=1 без ротации — если не делить IP с WB-майнерами и не сидеть вечно на одном sticky.

## Инцидент 2026-07-29: дедлок дорожки (11ч простоя Ozon)

**Симптом:** warning-алерты «медленный скрейпинг ozon» (p95 30с) с 22:50 28-07 и
«>50% ошибок» (100%) с 00:20 29-07. Critical `OzonMinerNoHealthyLanes` НЕ сработал.

**Что было:** контейнер `pt_ozon_miner` жив (8 дней аптайма, `/metrics` отдаёт),
`healthy_lanes 4/6`. Дорожки 4 и 5 отвалились в 00:14 и 01:01 с `status=0` за
34-38с (попыток 2) и **больше ни разу не перепрогрелись** — при потолке backoff
600с их должно было чинить каждые 10 минут. В логах после 01:01 — ни одной
строки прогрева.

**Причина:** `fetch_path` в ретрай-ветке звал драйвер без дедлайна —
`_nudge()` (`page.mouse.wheel`) и `page.wait_for_timeout(RETRY_PAUSE_MS)`. На
подвисшем драйвере эти await не возвращаются никогда, а вызывались они **под
локом дорожки**. Дальше цепочка: лок держится вечно → запросы Go копятся на входе
в лок (p95 30с → таймауты → 100% ошибок) → `maintenance_loop` пропускает
залоченные дорожки (`if lane.lock.locked(): continue`) и, идя последовательно,
замирает на `await lane.warm()` → пул не чинится вообще → `healthy` остаётся
`True` навсегда → алерт на `healthy_lanes == 0` слепой.

**Почему 11 часов:** единственный critical-алерт по сайдкару смотрел на
`healthy_lanes`, который при залипании **врёт**. Приходили только warning'и.

**Фикс** (ветка `fix/ozon-miner-lane-deadlock`):
- ни один await к драйверу не бывает без дедлайна: `LANE_OP_TIMEOUT_S` на всю
  операцию под локом (таймаут → 504, дорожка на пересоздание), `DRIVER_CALL_TIMEOUT_S`
  на нудж/egress-IP/закрытие браузера, `MAINT_OP_TIMEOUT_S` на прогрев и старт camoufox;
- паузы больше НЕ идут через браузер — свой `asyncio.sleep` вместо `page.wait_for_timeout`;
- обслуживание каждой дорожки — отдельная задача: зависшая соседка не морозит ремонт пула;
- вотчдог: лок держат дольше `LANE_STUCK_S` → снять `healthy` (пул обойдёт) + пересоздать браузер;
- метрики `ozon_miner_last_success_age_seconds` и `ozon_miner_stuck_lanes` +
  алерты `OzonMinerStale` (critical, >15м без успеха) и `OzonMinerStuckLanes`;
- регрессия `ozon-miner/test_lane_deadlock.py` (без браузера, драйвер-заглушка виснет).

**Осталось наблюдать:** 1220 PIDs и 4.3ГБ RSS при 8 днях аптайма — утечка процессов
camoufox на пересозданиях. Дедлайн в `close()` часть проблемы снимает, но счётчик
PIDs после деплоя проверить отдельно.

## Инцидент 02-09-2026: пул тихо деградировал до одной дорожки

**Симптом:** всю ночь пилой падали алерты `HighScrapeLatency` по Ozon (p95 26–29с
при пороге 10с) и всплесками `HighScrapeErrorRate` (50–67%). Внешне похоже на
«Ozon стал медленным» или на блокировки — ни то, ни другое.

**Что было на самом деле.** Живых дорожек **1 из 6**, и выжившая — та самая
`authed`, которая по замыслу резервируется под 18+. Пять анонимных по кругу
пытались прогреться и падали с `прогрев не дал 200`: зажившийся camoufox
(контейнер стоял 5 суток) перестаёт проходить FAB. Дальше механика:
`pick()` при отсутствии живых анонимных фолбэчит на любую живую → **весь
массовый поток пошёл под аккаунтом**, сериализованный на одном локе со
спейсингом 1.5с ± 40%. Ёмкость одной дорожки ≈ 0.34 rps, спрос был ≈ 0.5 rps →
очередь на входе в лок росла, пока не упиралась в 60-секундный таймаут Go.
Именно эта очередь и есть p95 26–29с: сам сайдкар отвечал за 1–2 секунды
(в логе видно отставание метки запроса Go на 25–28с).

Всплески «ошибок» — это `not_found`, а не блокировки: за 8ч success 11219,
not_found 2778, blocked 6, error 0. Порог алерта (`status != success` > 50%)
ловил перекос `not_found` в отдельных пятиминутках.

**Диагностика — что смотреть в следующий раз:**
- `ozon_miner_healthy_lanes` против `ozon_miner_total_lanes` (а не только на ноль);
- `avg_over_time(ozon_miner_lane_healthy[7d])` — здесь вскрылось, что анонимные
  дорожки были здоровы лишь **16% времени за неделю**, то есть деградация шла
  давно и постепенно, а ночью схлопнулась в ноль;
- в логах `pt_ozon_miner`: `прогрев не дал 200 (попыток подряд N)` — счётчик N
  датирует начало (11 минут на попытку = потолок backoff);
- расхождение времени в логе сайдкара и метки запроса Go = длина очереди.

**Две ложные версии, отброшенные фактами:** OOM-алерт той же ночи оказался
`pt_ali_miner` (chrome, rss 2.87 ГиБ, упор в свои 3g) — у ozon-miner было
3.9 из 6 ГиБ и camoufox это Firefox, а не chrome. И «Ozon закрыл анонимный
проход с датацентр-IP» — опровергнуто: пересоздание вернуло **6/6 дорожек**
с того же адреса.

**Атрибуция фикса (важно — уборка синтетики шла в тот же час).** По
`ozon_miner_healthy_lanes` с шагом 2 минуты: 08:39:15 ещё `1`, ~08:40
`--force-recreate`, 08:41:15 замер пропущен (контейнер поднимался), 08:43:15 уже
`6`. Уборка синтетиков — 08:51–08:52, то есть на девять минут ПОЗЖЕ. Дорожки
подняло пересоздание браузеров, а не снятие нагрузки; спрос отвечал лишь за то,
что деградация пула превращалась в очередь и алерты. До этого пул два часа
держал ровную единицу без флапа — порог `< 50% за 15м` сработал бы на этом плато.

**Что сделано:**
1. **Плановый recycle браузера по возрасту** (`OZON_LANE_MAX_AGE_SECONDS`, деф.
   6ч, джиттер 0.2) — раньше его тут не было сознательно («пере-прохождение FAB
   дороже пользы»). Обоснование опровергнуто: FAB мы теряем всё равно, только не
   осознанно раз в N часов, а исподволь и без предупреждения. У `ali-miner` и
   `wb-search-miner` recycle был давно, у `ozon-miner` — нет.
2. **Алерт `OzonMinerDegradedPool`**: живых дорожек < 50% пула дольше 15 минут.
   Строгий ноль (`OzonMinerNoHealthyLanes`) этот сценарий не ловил — узнали
   кружным путём, по латентности, через неделю.
3. **Регрессия** — случай E в `ozon-miner/test_lane_deadlock.py`.

**Спрос убран отдельно:** в тот же день удалены синтетики нагрузочного теста
(5000 юзеров, 17116 подписок) — из 1954 Ozon-товаров в скрейпе 1940 держала
синтетика. После уборки p95 Ozon = 1.15с. Аварийный троттл
(`OZON_INTERVAL_MULTIPLIER`) не понадобился. См. `docs/LOAD-TEST-SYNTHETIC.md`.

**ПОДТВЕРЖДЕНО ЧЕРЕЗ СУТКИ (03-09-2026).** Не «стало лучше», а измеренное:
`прогрев не дал 200` за 24 часа — **ноль раз** (до фикса шло непрерывно, пять
дорожек из шести не могли прогреться). `avg_over_time(ozon_miner_healthy_lanes[24h])`
= 5.997 из 6 (было 1.0), у каждой дорожки healthy 99.95% времени, минимум за
сутки 4 — это короткие провалы в моменты пересозданий, разведённые джиттером.
Recycle отработал 18 раз, по три на дорожку — сходится с порогом 6ч ± 20%.
Скрейп за сутки: 3437 успехов, 352 not_found, блокировок 0; p95 = 0.85с против
26-29с в инциденте. Гипотеза «браузер теряет FAB с возрастом» подтверждена.
