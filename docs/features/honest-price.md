# Фича: «Честная цена» по истории (анти-фейк-скидка)

Статус: **спека** (2026-06-21). Автор: Андрей + Claude. Журнал: ROADMAP.md.

## Зачем
На РФ-маркетплейсах массовы фейковые скидки: цену задирают перед «распродажей»,
и «−40%» считается от завышенной планки. Недоверие к скидкам — боль №1 покупателя.
У нас уже копится `price_history` на каждый трекаемый товар → можем показывать
**правду**: «это реально минимум за 90 дней» или «эта „скидка“ выше вашей обычной
цены — не торопись».

Ценность:
- **Повод платить**: target-price алерт («дай знать при ≤ X»), вердикт «покупать/ждать».
- **Виральность**: скриншотами «маркетплейс врёт про скидку» делятся → органический рост.
- **Почти бесплатно по инфре**: данные уже есть, добавляем агрегацию + рендер.

## Что есть сейчас (точки опоры в коде)
- Таблица `price_history(product_id, price NUMERIC(12,2), recorded_at TIMESTAMPTZ)`,
  помесячные партиции, индекс `idx_price_history_product` (`001_init.up.sql`).
- Пишется на каждом скрейпе: `cmd/scraper/main.go:192` → `PriceHistoryRepo.Insert`.
- Читается только `GetLatest` (фолбэк к Redis). **Агрегатов (min/median по окну) нет — добавляем.**
- `domain.PriceEvent` несёт `OldPrice` — витринную «старую цену» маркетплейса (для детекта фейка).
- Алерт снижения: `internal/telegram/notifier.go:41 SendPriceAlert` («📉 Было X → Стало Y…»),
  зеркало в VK (`internal/vk/...`). Карточка при `/track` — `internal/telegram/track.go`.

## Модель данных и расчёт

### Что считаем (на товар, по окнам)
Окна: **30 дней** (основное), **90 дней** (глубина), **всё наблюдаемое** (since first-seen).
Метрики на окно: `min`, `median` (percentile_cont 0.5), `count` (точек), `since` (первая запись).

> Важно: история есть только с момента, как **мы** начали трекать товар (не вся история
> маркетплейса). Это надо честно отражать (см. «достаточность данных»).

### Новый метод репозитория
`internal/repository/postgres/price_history.go`:

```go
type PriceStats struct {
    Min30, Median30   float64
    Min90             float64
    MinAll            float64
    Count30, CountAll int
    Since             time.Time // первая запись по товару
}

// Stats — агрегаты цены по товару одним запросом (окна 30/90д + всё время).
func (r *PriceHistoryRepo) Stats(ctx context.Context, productID int64, now time.Time) (PriceStats, error)
```

SQL (один проход, фильтр-агрегаты по окнам):
```sql
SELECT
  min(price) FILTER (WHERE recorded_at >= $2 - interval '30 days')                AS min30,
  percentile_cont(0.5) WITHIN GROUP (ORDER BY price)
        FILTER (WHERE recorded_at >= $2 - interval '30 days')                     AS median30,
  min(price) FILTER (WHERE recorded_at >= $2 - interval '90 days')                AS min90,
  min(price)                                                                       AS min_all,
  count(*) FILTER (WHERE recorded_at >= $2 - interval '30 days')                  AS count30,
  count(*)                                                                         AS count_all,
  min(recorded_at)                                                                 AS since
FROM price_history
WHERE product_id = $1;
```

Перф: композитный индекс `(product_id, recorded_at DESC)` **уже есть** (`idx_price_history_product`
в `001_init`) — миграция НЕ нужна, запрос сразу эффективен.
При росте — кэшировать `PriceStats` в Redis с TTL ~ интервал скрейпа (цена меняется не чаще).
Медиана по партициям ок на текущих объёмах; следить через метрику времени запроса.

## Доменная логика — вердикт

`internal/domain/honest_price.go` (чистая функция, легко тестируется):

```go
type PriceVerdict int
const (
    VerdictInsufficient PriceVerdict = iota // мало данных — наблюдаем
    VerdictLowestEver                        // ≤ минимума за всё наблюдение
    VerdictLowest90                          // ≤ минимума за 90д
    VerdictLowest30                          // ≤ минимума за 30д
    VerdictTypical                           // в районе медианы (≤ median30)
    VerdictAboveTypical                      // > median30 — «скидка» завышена
)

type HonestPrice struct {
    Verdict        PriceVerdict
    Min30, Median30, Min90, MinAll float64
    FakeDiscount   bool    // витринная скидка есть, но цена ≥ median30
    DropFromMedian float64 // % ниже медианы (для «реально дешевле на N%»)
}

func AssessHonestPrice(current, showcaseOld float64, s PriceStats, now time.Time) HonestPrice
```

Пороги (по убыванию строгости):
1. `count30 < MinSamples` (напр. 5) **или** `since` моложе ~3 дней → `VerdictInsufficient`
   («наблюдаем N дней, выводы рано») — честность важнее красивого бейджа.
2. `current <= MinAll` → `VerdictLowestEver` 🟢 «минимум за всё время наблюдения».
3. `current <= Min90` → `VerdictLowest90` 🟢 «минимум за 90 дней».
4. `current <= Min30` → `VerdictLowest30` 🟢 «минимум за 30 дней».
5. `current <= Median30` → `VerdictTypical` 🟡 «в рамках обычной цены».
6. иначе → `VerdictAboveTypical` 🔴 «выше обычной».

**Детект фейк-скидки.** Важная поправка по факту кода: `PriceEvent.OldPrice = prevPrice`
(прошлая цена нашего скрейпа), а **витринную зачёркнутую цену маркетплейса скрейперы НЕ
возвращают** (`scraper.Result` несёт только `Price`). Поэтому явное «маркетплейс рисует было
N₽, а это выше медианы» в MVP невозможно — это фаза 2 (добавить strikethrough в `Result`).
В MVP сигнал фейк-скидки даёт сам вердикт `VerdictAboveTypical` (текущая > медианы за 30д из
НАШЕЙ истории) — это и есть «скидка завышена» по нашим данным, без опоры на витрину.
Поэтому `AssessHonestPrice(current, stats, now)` — без `showcaseOld`.

Допущение против манипуляции нашей же историей: один аномальный скачок не должен ломать
медиану — медиана устойчива к выбросам (в отличие от среднего), потому и берём её.

## Где показываем

1. **Алерт снижения** (`SendPriceAlert`, TG + зеркало VK) — главное место.
   К текущему «📉 Было X → Стало Y, Скидка %» добавляем строку вердикта:
   - 🟢 `VerdictLowest*`: «🟢 Это минимум за 90 дней — хорошая цена».
   - 🟡 `VerdictTypical`: «🟡 Обычная цена для этого товара».
   - 🔴 `VerdictAboveTypical` + `FakeDiscount`: «🔴 «Скидка» завышена: дешевле было N ₽
     (медиана за 30д M ₽). Не настоящая распродажа».
2. **Карточка при `/track`** (track.go) и в списке `/list` — вердикт + «мин за 30/90д».
3. **Поиск-подписки** (фаза 2) — бейдж честной цены в выдаче «подешевело».
4. **Веб/график** (фаза 3) — спарклайн истории с отметкой медианы/минимума.

# Реализация MVP (2026-06-21, ветка feat/honest-price-spec)

## Что сделано
- `domain.PriceStats` + `domain.AssessHonestPrice(current, stats, now)` + `HonestPrice.Line()`
  (`internal/domain/honest_price.go`) — чистая логика, 12 тест-кейсов.
- `PriceHistoryRepo.Stats` — агрегаты одним запросом (`internal/repository/postgres/price_history.go`).
- `PriceAlert.HonestLine` + рендер в TG (`telegram/notifier.go`) и зеркало VK
  (`cmd/notifier/delivery.go vkPriceText`).
- notifier считает вердикт раз на событие (`cmd/notifier/main.go`).
- Деплой MVP: пересобрать **только `notifier`** (миграций/env нет).

## Принятые решения (и почему)
1. **Медиана, а не среднее.** Среднее ломается одним выбросом и легко «накручивается»
   нашей же историей; медиана устойчива → вердикт честнее.
2. **`AssessHonestPrice` без витринной цены.** По факту кода `PriceEvent.OldPrice` =
   прошлый скрейп, strikethrough маркетплейса не доступен. Сигнал фейк-скидки даёт сам
   `VerdictAboveTypical` (текущая > медианы по НАШИМ данным). Явное «маркетплейс врёт про
   N₽» — фаза 2 (добавить strikethrough в `scraper.Result`).
3. **Порог достаточности (5 точек / 3 дня) → пустая строка.** История у нас только с
   момента трекинга; на тонкой выборке молчим, а не вводим в заблуждение зелёным бейджем.
4. **Вердикт раз на событие, не на подписку.** Stats зависит от товара, не от подписчика →
   один запрос на событие, а не N (по числу подписчиков товара).
5. **Логика в `domain`, формат строки тоже (`Line()`).** TG и VK берут одну строку — не
   разъедутся формулировки (та же причина, что и для прочих рендеров в domain).

## Подводные камни, которые продумал и обошёл
- **OOS засорил бы медиану.** Проверено: `Insert` под `if result.InStock` (`scraper/main.go:191`),
  нулевые/OOS-точки в историю не идут → медиана/мин не искажаются.
- **`current` уже в истории к моменту оценки** (записан этим же скрейпом до публикации
  события) → семантика `current <= MinAll` = «минимум за всё время» корректна (равенство —
  это и есть «текущая = историческому минимуму»).
- **Пустое окно/нет истории** → `percentile_cont`/`min` дают NULL: скан в `*float64`,
  `HasData=countAll>0`, иначе `Insufficient`.
- **Лишний шум в уведомлении** → для `back_in_stock` и `Insufficient` строка пустая, ничего
  не добавляем.
- **Миграции не понадобилось** — нужный индекс `(product_id, recorded_at DESC)` уже есть в `001`.
- **Деградация median-запроса при росте** вынесена в раздел хранения ниже (главный риск «через время»).

# Хранение истории: анализ и оптимальное решение

Вопрос Андрея: цена месяцами не меняется — хранить каждый скрейп расточительно; на графике
это прямая, точки можно проставить самим. Верно. Но у наивного «хранить только изменения»
есть НЕочевидный подвох с медианой. Разбор.

## Ключевой подвох: корректность медианы зависит от схемы хранения
При **хранении каждого скрейпа** интервалы между точками равные → простой `percentile_cont`
автоматически = **взвешенной по времени** медиане. Это и есть «обычная цена» (где товар
провёл половину времени). Корректность даётся бесплатно — ценой объёма.

При **хранении только изменений** точки неравномерны: 1 запись «1000₽» (28 дней) + 1 запись
«800₽» (2 дня) дадут `percentile_cont = 900`, а по времени медиана = **1000** (товар почти
всё время стоил 1000). Пример, где это **переворачивает вердикт**: текущая 950 →
по change-only-медиане (900) → 🔴 «выше обычной»; по time-weighted (1000) → 🟡 «обычная».
То есть наивный change-only **врёт в вердикте**. Значит «только изменения» требует
**взвешивания по длительности сегмента** (duration = `lead(recorded_at) - recorded_at`).

## Варианты

| Подход | Объём (товар/год при 20-мин кадансе) | Корректность медианы | Сложность запроса | График |
|---|---|---|---|---|
| **A. Каждый скрейп** (сейчас) | ~26 000 строк | ✅ бесплатно (равномерная выборка) | простой | по точкам |
| **B. Только изменения (RLE)** | ~12–60 строк | ⚠️ нужна **взвешка по длительности** + якорь на границе окна | сложнее (window-функции) | идеально (ступени, концы синтезируем) |
| **C. Дневной агрегат** (upsert min/last/day) | ~365 строк | ✅ ~time-weighted (равномерно по дням) | простой | по дням |
| **D. Горячий raw + ретеншн + дневной rollup** | raw ограничен ретеншном + ~365/год | ✅ | средняя (2 таблицы, джоб) | raw для деталей, rollup для длинных окон |

Доп. подводные для B (если выбираем его):
- **Якорь границы окна**: товар сменил цену 40 дней назад и стоит так же — внутри 30-дн.
  окна точек нет, но активная цена ровно эта. `min30`/`median30` обязаны подтянуть
  «последнюю запись до начала окна». Иначе окно «пустое» → ложный Insufficient.
- **Открытый последний сегмент**: длительность последней цены = `now - recorded_at`.
- **OOS-разрывы**: сегмент «не в наличии» исключаем из ценовой взвески (он уже не пишется).
- Это ровно «точки проставим сами» из интуиции Андрея — синтез концов сегментов на чтении.

## Что НЕ так «прямо сейчас» и «через время»
- **Сейчас объём ничтожен**: по факту десятки скрейпов/сутки суммарно (видели ~58 Ozon/24ч).
  Даже 1000 скрейпов/сут ≈ 365k строк/год ≈ ~20–30 МБ/год с индексом. Партиции помесячные.
  Оптимизировать сейчас — преждевременно, а замена схемы внесёт риск в корректность вердикта.
- **Через время масштаб бьёт по числу ТОВАРОВ**: 10k товаров × 20-мин = ~263 млн строк/год
  (~15 ГБ/год) + дорожает `percentile_cont` (сорт по партициям). Вот тогда A становится больно.

## Рекомендация (оптимум по балансу)
**Фаза текущая — оставить A (каждый скрейп).** Корректно, просто, объём пренебрежим;
менять схему ради 20 МБ/год и рисковать вердиктом — не стоит.
**Триггер перехода** (любой): raw `price_history` > ~50 млн строк / > ~5 ГБ, ИЛИ онбординг
многих платных юзеров (рост числа товаров), ИЛИ время `Stats`-запроса (метрика) деградирует.
**Куда переходить:**
- Хочется минимум места и точный график → **B (RLE + взвешка по длительности + якорь окна)**.
  Это ровно идея Андрея, плюс закрытый подвох медианы.
- Хочется проще и почти бесплатно по месту → **C (дневной upsert `min/last`)**: ~70× меньше,
  корректная (дневная) взвеска, простые запросы, без window-математики. Лучший «средний» путь.
- Совсем большой масштаб → **D** (ретеншн горячего raw через drop старых партиций + дневной
  rollup для длинных окон/all-time).

Промежуточно (дёшево, снижает рост уже сейчас, безопасно для A): **прорежать запись на
неизменной цене** — писать не каждый скрейп, а «изменение ИЛИ раз в день» (дневной
heartbeat). Даёт ~равномерную дневную выборку (медиана остаётся ~корректной, как в C) и
режет объём в десятки раз, не ломая текущие запросы. Это самый дешёвый шаг, если объём
начнёт беспокоить раньше полноценного C/D.

Метрика для решения: гистограмма времени `Stats` + счётчик строк `price_history` на дашборд.
