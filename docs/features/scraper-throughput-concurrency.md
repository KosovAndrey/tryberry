# Консьюмеры price-tracker: разбор лага + заметка про последовательность

Статус: **инцидент закрыт** (2026-06-22). Этот файл сначала был написан на
ОШИБОЧНОМ диагнозе (думали — пропускная скрейпера); ниже — что было на самом деле.

## Что произошло (пост-мортем)

Алерт: лаг группы `price-tracker` в топике `price-events` рос без предела
(112 → ~260). Долго копали как «скрейпер не успевает» — **неверно**.

Топология (важно): группа `price-tracker` консьюмит ДВА топика:
- `scrape-tasks` — воркер `pt_scraper` (скрейпит цену → produces `price-events`);
- `price-events` — воркер `pt_notifier` (шлёт Telegram/VK-алерты).

Факты при разборе:
- лаг `scrape-tasks` = **0 на всех 10 партициях** → скрейпер успевал, проблемы не было;
- лаг `price-events` = ~260 на ОДНОЙ партиции → залип `pt_notifier`;
- логи notifier'а: `handler error (will retry): ... Bad Request: wrong type of the
  web page content` — по кругу.

**Корень:** notifier застрял в ретрай-петле на одном price-event — алерт по
трансграничному товару (`nm=1114323146`), у которого image-URL строится из basket,
а в basket трансграничных нет → ссылка ведёт не на картинку → Telegram отвергает
`sendPhoto` (4xx) → handler возвращает err → kafka не коммитит → бесконечный ретрай
→ партиция не двигается, лаг растёт.

## Фикс (сделано)

`fix(notifier): не зацикливать кафку на перманентной ошибке Telegram` (в main):
- `call`: различает перманентную 4xx (≠429) → sentinel `ErrTelegramPermanent`;
- `SendPriceAlert`: битую картинку (перманентная ошибка `sendPhoto`) → шлём
  **текстом**, алерт всё равно доходит;
- `deliver`: перманентную ошибку TG (битая картинка, бан, чат не найден) НЕ
  ретраим — `return nil` + skip-метрика.

После деплоя лаг ушёл в 0, петля исчезла.

## Заметка на будущее: консьюмеры последовательны

И `pt_scraper`, и `pt_notifier` гоняют `Consumer.Run` — **по одному сообщению**
(FetchMessage → handler → commit). Это НЕ было причиной инцидента (петля была), и
на текущем объёме оба успевают. Но это потолок: если поток вырастет настолько, что
один последовательный консьюмер перестанет успевать (а не залипнет), тогда —
**и только тогда** — понадобится:
- параллельная обработка (`Consumer.RunConcurrent`, батч-конкурентность с
  безопасным коммитом непрерывного успешного префикса на партиции; хендлеры
  идемпотентны), ИЛИ
- масштабирование воркера репликами по партициям (как `reseller-worker`,
  `--scale`; у топиков `KAFKA_NUM_PARTITIONS=10`, есть куда).

Сейчас это **не нужно** — заводить, если реально упрёмся в throughput (по метрикам
лага + длительности обработки), а не по подозрению.

## Побочное (мелочь)

Картинка трансграничных товаров 404-ит (строится из basket, которого у них нет).
Сейчас обходим текст-фолбэком. Если захочется картинку — брать её из ответа u-card
(там есть `pics`) и строить URL под трансгран отдельно. Не срочно.
