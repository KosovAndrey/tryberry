# WB: отслеживание магазина/продавца — ресёрч

Статус: **ресёрч завершён, реализация не начата** (2026-06-22).
Триггер-задача в трекере: «🟡 WB: отслеживание страницы продавца (купибара)».

Цель: дать юзеру подключить к отслеживанию не отдельный товар, а всю витрину
продавца WB — ловить снижения цен по магазину (и, опционально, новинки).

---

## TL;DR

- **Источник данных есть и он открытый.** `catalog.wb.ru/sellers/v4/catalog?...&supplier={id}`
  отдаёт `200` **без wbaas-токена и без прокси** (в отличие от поиска!). Форма
  ответа — `{products, total}`, товары с `id/name/brand/sizes[].price.{basic,product,total}`
  — **ровно то, что уже парсит `wbProductToItem`**.
- **API принимает фильтры WB как есть** (`xsubject`, `fbrand`, `f5023`, …): тот же
  набор query-параметров, что на HTML-странице продавца, прокидывается в catalog-API
  и сужает выдачу. Это решает проблему гигантских магазинов.
- **HTML-страница продавца за антиботом** (`www.wildberries.ru/seller/{id}` → `498`
  wbaas-challenge), но она нам и не нужна: `supplier_id` + фильтры достаём из ссылки.
- **Фича структурно = поиск-подписка с другим «запросом».** Вся обвязка
  (`SearchScraper` + `searchsub` engine: diff, baseline, Decide, батч-уведомления,
  лимиты, дедуп по `normalized_url`) переиспользуется почти 1-в-1.
- **Дешевле AliExpress-кейса**: там `card.wb.ru` = 403 и данных нет; здесь источник
  открыт и парсер готов.

## Ключевая UX-проблема и решение: размер выдачи

Магазин может быть огромным (МВИДЕО `supplier=250000206` → **42033 товара** — парсить
всё каждый цикл недопустимо дорого). Решение трёхуровневое:

1. **Фильтры WB в ссылке** прокидываем в API → юзер сам сужает до адекватного.
   Проверено на МВИДЕО (2026-06-22):
   | Ссылка | `total` |
   |---|---|
   | `?supplier=250000206` (без фильтров) | **42033** |
   | `&xsubject=515&fbrand=6049` (смартфоны Apple) | **304** |
   | `&f5023=…` (конкретные модели iPhone 17) | **17** |
2. **Потолок на размер выдачи** (CAP, напр. ~300 товаров / 3 страницы). При
   подключении скрейпим `page=1`, читаем `total`. Если `total > CAP` — **не заводим
   подписку**, а отвечаем «в выдаче N товаров, лимит M — сузь фильтры (категория /
   бренд / модель) и пришли ссылку снова». Юзер сам понимает, укладывается ли он.
3. **Опциональный клиентский текстовый фильтр** (на нашей стороне): иногда у магазина
   нет хороших фильтров WB. Юзер может добавить текст (напр. «iphone 17») → мы тянем
   WB-выдачу (в пределах CAP) и **трекаем только карточки, чьё name/brand матчит
   текст**. CAP считается по WB-`total` (стоимость скрейпа), текст лишь сужает, что
   показываем/трекаем.

   Сценарий-пример (из обсуждения): юзер хочет iPhone в конкретном магазине, где
   иногда дропают ниже рынка → ставит ссылку на селлера с фильтром «смартфоны Apple»
   (304, в пределах CAP) + клиентский текст «iphone 17» → трекается ~17 нужных.

## Что проверено эмпирически (2026-06-22)

| Эндпоинт | Результат |
|---|---|
| `catalog.wb.ru/sellers/v4/catalog?...&supplier=1000` | `200`, 12 товаров (бренд ELSY), цены есть |
| `catalog.wb.ru/sellers/v2/catalog?...&supplier=` | `404` (старая версия мертва) |
| `catalog.wb.ru/sellers/catalog` (без версии) | `404` |
| `static-basket-01.../supplier-by-id/{id}.json` | `404` |
| `www.wildberries.ru/seller/1000` (HTML) | `498` (wbaas-challenge) |
| `supplier=1234` / большинство мелких id | `200`, `total=0` (продавец пуст/деактивирован) |

Пример позиции из ответа (`supplier=1000`):
`id=1439945 brand='ELSY' name='Тренчкот' price.product=237500` (= 2375 ₽, копейки).

Важно: цена в seller-catalog — это **live-ish цена выдачи** (как у поиска), что
**свежее**, чем basket `price-history.json` для одиночных товаров (тот отстаёт на
часы). Т.е. подписка на магазин получает более актуальную цену, чем трекинг
одного товара.

## Как ложится на существующий код

Поиск-подписки уже устроены так (см. `internal/scraper/wildberries_search.go`,
`internal/searchsub/engine.go`):

- `SearchScraper` интерфейс: `MatchesSearch` / `NormalizeSearchURL` / `ScrapeSearch`.
- `wbProductToItem` парсит `{id,name,brand,sizes[].price,feedbackPoints}` → `SearchItem`.
- `searchsub.Decide/Evaluate` — чистые функции: baseline (first_seen), типы триггеров
  `below_target / any_drop / discount_pct`, анти-спам (повтор только если цена ниже
  прошлого уведомления).

Подписка на магазин — это тот же контур, где «запрос» = `supplier_id`, а скрейп
идёт в seller-catalog v4 вместо u-search. **Парсер ответа переиспользуется как
есть** (одинаковая форма `{products[], total}`).

### Развилка реализации

**Вариант A — расширить `WildberriesSearchScraper`:**
`MatchesSearch` дополнительно матчит `/seller/{id}`, `ScrapeSearch` ветвится: seller
→ v4-catalog (без токена/прокси), text → u-search (токен). Минус: смешиваем два
разных пути аутентификации в одном типе.

**Вариант B — отдельный `WildberriesSellerScraper` (рекомендую):**
Свой тип, реализует тот же `SearchScraper`. `MatchesSearch` ловит `/seller/{id}`,
`ScrapeSearch` ходит в v4-catalog простым клиентом (без wbaas, без прокси — он не
нужен). Переиспользует `wbProductToItem` и структуры ответа. Чище по
ответственности; реестр сам разрулит через `FindSearchByURL` (он перебирает
скрейперы и матчит по URL).

## Дизайн MVP (решено в обсуждении 2026-06-22)

- **Событие:** только снижения цен (переиспользуем `searchsub.Decide`:
  below/any_drop/discount). Новинки — возможный шаг 2.
- **Подключение:** юзер кидает ссылку селлера **со своими фильтрами WB**
  `wildberries.ru/seller/{id}?xsubject=…&fbrand=…&f5023=…`. Парсим `supplier_id` из
  пути + прокидываем фильтры в catalog-API.
- **CAP на размер выдачи:** при подключении читаем `total`; `total > CAP` → отказ с
  подсказкой сузить фильтры. CAP — env-константа (старт ~300).
- **Клиентский текстовый фильтр:** опциональный текст, матчим по name/brand карточек
  (на нашей стороне), CAP — по WB-`total`.

## Открытые вопросы (на согласование)

1. **Значение CAP.** ~300 (= 3 страницы по 100) как старт? Влияет на стоимость
   цикла: CAP × кол-во seller-подписок товаров скрейпится каждый тик.
2. **Клиентский текст-фильтр — в MVP или шаг 2?** Добавляет колонку в БД и UI-шаг,
   но закрывает магазины без хороших WB-фильтров. Рекомендация: в MVP (дёшево —
   фильтрация строкой в памяти после скрейпа).
3. **Лимиты на тариф.** Сколько seller-подписок на план? Свериться с текущими
   лимитами поиск-подписок (`internal/*/plans.go`).
4. **Имя магазина.** Есть ли `supplierName`/`supplier` в ответе v4? Если нет — брать
   `brand` первого товара или «Магазин #{id}». Проверить при реализации.
5. **Нормализация для дедупа.** `NormalizeSearchURL` должен включать `supplier_id` +
   значимые фильтры + клиентский текст (одинаковый набор = общая подписка между
   юзерами; разные фильтры = разные подписки).

## Риски / зависимости

- **v4 может смениться, как сменился v2.** Источник неофициальный — заложить
  метрику исхода скрейпа (как `wb_basket_resolve_total`) и понятный фолбэк.
- **Пагинация:** размер страницы = 100 (как у поиска), `total` отдаётся. Поведение
  `page=2+` на хвосте выдачи перед реализацией добить (нужно для корректной сборки
  всех страниц в пределах CAP).
- **wbaas на HTML-странице** не мешает (id из URL), но если WB закроет и
  catalog-API — фича превращается в AliExpress-кейс. Пока открыт.
