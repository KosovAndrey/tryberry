# Я.Маркет: закрыта форма `/product/`, живая — `/card/<slug>/<oskuId>`

Дата разбора: **01-09-2026, вечер**. Ветка: `fix/ym-card-url-form`.
Канон каданса и общий статус — `SCRAPE-CADENCE.md`, `YANDEX-STATUS.md`.

## Короткий вывод

Яндекс закрыл SmartCaptcha обе формы URL, которыми пользуется наш код, и оставил
третью, которой мы нигде не строим. Дело не в IP и не в прокси: с живого
российского адреса закрытые формы капчатся так же, как с датацентрового, а живая
форма открывается даже без прокси. Скрейп Я.Маркета стоит не потому, что нас
забанили, а потому что **мы ходим по адресам, которых больше нет**.

| форма | пример | что отдаёт |
|---|---|---|
| `/product/<modelId>` — наш канон (миграции 030/031) | `/product/923133126` | 302 → `showcaptcha` |
| `/product--<slug>/<modelId>` — её строит парсер выдачи | `/product--x/923133126` | 302 → `showcaptcha` |
| `/card/<slug>/<oskuId>` — живая | `/card/kofemashina-.../5193397317` | 200, 2,2 МБ, цена парсится |

В базе на момент разбора: **14086 товаров в форме `/product/`, 15 в форме
`/card/`**. Те 15 пришли от пользователей ссылками из рекламной выдачи — и именно
они, единственные из всего Я.Маркета, скрейпились сегодня успешно.

## Чем доказано

**Форма, а не адрес.** `ym-form-probe` (добавлен этим же разбором) ходит по трём
формам одного товара без следования редиректам. Через мобильный RU-прокси
(МегаФон, Москва, проверен `ym-proxy-check` — 3 из 3 карточек с ценой):

```
/product/5193397317     302 → market.yandex.ru/showcaptcha?...&retpath=...
/product--x/5193397317  302 → market.yandex.ru/showcaptcha?...&retpath=...
/card/x/5193397317      200, 2221 КБ, в теле канонический адрес
```

Тот же результат на четырёх разных id. То есть по одному и тому же клиенту, с
одного адреса, в одном прогоне: `/product/` — капча, `/card/` — карточка.

**Прогрев кук не лечит.** `yandex-probe` прогнал четыре сценария (cold-direct,
proxy-cold, warm→direct, warm→proxy) на трёх `/product/`-адресах. Главная отдаётся
200 и кладёт 15 кук в общий jar, но карточка `blocked` во всех четырёх. Гипотеза
«прогретых cookie» (`YANDEX-WARMED-COOKIES.md`) на этот режим не распространяется.

**Слаг декоративен.** `/card/x/5193397317` с заведомо фиктивным слагом отдал
полную карточку 2221 КБ и сам назвал настоящий адрес в теле
(`/card/kofemashina-avtomaticheskaya-jura-e8-piano-black-15584/5193397317`).
Боевой скрейпер по нему — 105077 ₽, в наличии. Значит форма проверяет только id.

**Наши id в пространстве `/card/` не живут.** `ym-card-probe` на выборке 50
случайных `/product/`-id из базы: **карточка 0, скелет 50 (100%)**, капч нет.
Скелет — одинаковая страница-заглушка 1366–1367 КБ. То есть подставить наш id в
живую форму нельзя, нужен другой идентификатор.

**Прокси не нужен: живая форма открывается direct.** Проверено `ym-dump` без
прокси с прод-адреса, три карточки подряд: 2264452, 2366819 и 2027203 байта, ноль
вхождений капчи. Контроль тем же клиентом с того же адреса: `/product/5193397317`
— 14191 байт и 302 на `showcaptcha`. То есть датацентровый IP Яндекс пускает,
режется именно форма. Мобильный прокси (1800 ₽/мес) для карточек не требуется;
он остаётся разве что запасным вариантом, если IP снова нагреется.

**Прежний диагноз «прод-IP забанен целиком» неверен.** Четырнадцать из пятнадцати
`/card/`-товаров обновились сегодня между 14:05 и 15:10 UTC — то есть скрейпились
успешно с датацентрового IP, ровно в те часы, когда `/product/` уже сыпал
блокировками. Прокси всё равно понадобится (проверять и это тоже придётся заново),
но чинит он не эту поломку.

## Механика резолва: modelId → oskuId

В стейте выдачи (`market.yandex.ru/search?text=...` — 2,1 МБ, без капчи, **direct
с прод-адреса тоже**: проверено `ym-dump` без прокси, 0 вхождений капчи, `modelId`
и `oskuId` на месте) оба идентификатора лежат **в одном объекте**:

```json
{"modelId":"1016751481","cskuId":"103780259023","oskuId":"103710149199",
 "slug":"aravia-neytralnyy-konditsioner-konstruktor-dlya-vsekh-tipov-volos-neutral-hair-conditioner-350-ml"}
```

И то же самое дублируется в JSON-LD позиции выдачи, уже собранным адресом:

```json
{"sku":"103780259023","offers":{"url":"https://market.yandex.ru/card/aravia-neytralnyy-.../103710149199"}}
```

`modelId` — это ровно то, что лежит у нас в `products.url` (проверено: наш
`/product/1016751481` встречается в выдаче 22 раза как `"modelId":"1016751481"`).
`oskuId` — то, что стоит в `/card/`-ссылке. Никакой эвристики по названию и цене
не нужно, связь публикуется явно.

Ещё в стейте встречаются `marketSku` / `cskuId` / `mskuId` — это **не** id для
`/card/`, не перепутать: у ARAVIA `cskuId=103780259023`, а в адресе
`oskuId=103710149199`.

## Что придётся менять в коде

1. `internal/scraper/yandex_market_search.go:444` — парсер выдачи строит
   `/product--<slug>/<id>` из `modelId`. Должен строить `/card/<slug>/<oskuId>`.
   Значит `ymSearchModel` надо расширить полями `oskuId`/`slug` того объекта, где
   они лежат вместе (сейчас парсится только объект-модель `entity:"product"`).
2. `internal/scraper/canonical_url.go:55` — канон `/product/<id>`. Должен стать
   каноном по `oskuId`. Дедупликация по id, слаг в ключ не входит (он декоративен
   — доказано выше, как и у витрин продавца `/business--<slug>/<id>`).
3. `internal/scraper/yandex_market.go:484` — `ymProductPathRe` сознательно не
   принимает `/card/`. Комментарий рядом фиксировал причину: «у `/card/` id другой
   размерности, похоже на id ОФФЕРА, а не товара... Проверить не удалось: YM
   закрыл пробника SmartCaptcha». Теперь проверено — это `oskuId`, и форму надо
   принимать.
4. `ymExtractSKU` уже берёт последний числовой сегмент, то есть на `/card/`
   работает без правок. Но парсер цены ищет по этому id в стейте — надо
   убедиться на OOS-карточках, что `oskuId` там якорь не хуже, чем `modelId` был
   на старой форме.

## Риски миграции

**Один modelId даёт несколько карточек.** У ARAVIA в выдаче три разных `oskuId`
на один и тот же кондиционер (103710149199 за 326 ₽, 6161223426 за 3104 ₽,
6185775750 за 3055 ₽) — это разные офферы и разные объёмы. Выбор не того
`oskuId` = ровно тот класс бага, что уже был с чужой ценой у Ozon-OOS и у
YM `/cc/`: цена приедет от другого товара, а пользователь получит алерт о
«снижении». Резолвер обязан брать `oskuId` **из объекта с нашим modelId**, а не
первый попавшийся в выдаче, и отказываться, когда однозначного объекта нет.

**Резолвится не всё.** В пробе на трёх случайных товарах один (подгузники MIMISO)
в выдаче по своему названию не нашёлся вообще — ноль вхождений. Долю
нерезолвимых надо померить до миграции, на выборке хотя бы в 200 товаров.

**Трафик.** Один запрос выдачи ≈ 2,1 МБ. На 14086 товаров это около 30 ГБ — но
не через прокси, а с прод-канала, где это не деньги. Резолвер всё равно обязан
ходить щадящим темпом (не греть IP), держать чекпоинт и продолжать с места обрыва.

**`products.url` — UNIQUE и ключ товара.** После переписывания два разных modelId
могут схлопнуться в один `oskuId`. Тогда нужно решать, как сливать историю цен,
подписки и `public_id` (у части товаров публичная страница `/p/<public_id>` уже
проиндексирована). Пока таких коллизий не померено — считать, что они будут.

## Сколько работы на самом деле: живых подписок ДВЕ

Прежде чем писать резолвер на 14086 товаров, посчитали, ради кого он. Активных
YM-подписок на `/product/`-товары — 8946 у 4328 пользователей, но по датам
регистрации картина такая:

| регистрация подписчика | пользователей | подписок |
|---|---|---|
| 2026-05-27 | 1 | 1 |
| 2026-06-11 | 1 | 1 |
| **2026-07-05** (нагрузочный тест) | **4326** | **8944** |

То есть на мёртвой форме **живых подписок две, на один товар**, остальные 8944 —
синтетика нагрузочного теста (см. заметку про него: 5020 юзеров в базе почти
целиком оттуда). Массовая миграция ради их истории не нужна.

ВАЖНАЯ ПОПРАВКА к этой таблице: она считает только подписки на `/product/`-товары.
Живых YM-подписок больше — **семнадцать**: две на мёртвой форме и пятнадцать на
тех самых `/card/`-товарах (одиннадцать от пользователей, пришедших 14-08, плюс
четыре майско-июньских). Пятнадцать живых подписчиков уже на рабочей форме и
оживают сразу, как только площадку перестаёт глушить синтетика — то есть цена
поломки была выше, чем показывал первый подсчёт.

## План

Приоритет сместился: срочна не миграция, а то, чтобы НОВЫЕ товары заводились в
живой форме. Пока парсер выдачи строит `/product--<slug>/<modelId>`, каждый
добавленный сегодня YM-товар — мёртвая ссылка с первой секунды.

1. **Код — главное.** Парсер выдачи строит `/card/<slug>/<oskuId>` (нужны поля
   `oskuId`/`slug` из объекта, где они лежат с `modelId`); канон переезжает на
   `oskuId`; `ymProductPathRe` принимает `/card/`. Тесты на обе формы. После
   этого всё новое живёт, независимо от старого хвоста.
2. **Один живой товар** мигрировать вручную — резолвить его `oskuId` из выдачи и
   переписать `products.url`. Двум пользователям Я.Маркет чинится в тот же день.
3. **Синтетику НЕ мигрировать.** 14085 оставшихся `/product/`-товаров — балласт
   теста. Решить отдельно: пометить, чтобы не скрейпить, или удалить вместе с
   синтетическими подписками (осторожно с каскадами — у живых пользователей
   каскад цепляет `payments`, там НПД-чеки; синтетика платежей не имеет, но
   проверить перед DELETE).
4. **Резолвер `cmd/ym-resolve`** — теперь необязательный. Нужен, только если
   решим восстанавливать историю по старым товарам, когда их кто-то тронет:
   тогда резолв делается лениво, по одному товару, а не пакетом на 30 ГБ.
5. **Прокси не покупать.** И карточки, и выдача идут direct.

свежим строкам `price_history`, а не по метрике. И смотреть узкое окно: `[10m]` и
`logs --since 15m` захватывают время ДО вмешательства и показывают эхо старых

## Хвосты

1. ~~14085 синтетических товаров~~ **СДЕЛАНО 01-09 вечером.** Оказалось не
   косметикой, а тем, что глушило починку: очередь скрейпа строится через
   `JOIN subscriptions ... active` (`GetSchedulableProducts`), поэтому мёртвые
   ссылки тянули в Яндекс именно синтетические подписки — 8944 штуки. Брейкер
   один на площадку, и они разомкнули цепь на всех трёх репликах
   (`success=0, blocked=39, suppressed=780, circuit_open=1`), заодно давя живые
   `/card/`-товары. Лечение — не миграция и не удаление ссылок, а деактивация
   синтетических подписок: `UPDATE subscriptions SET active=false` по товарам
   `yandex_market` в форме `/product/` у пользователей с `created_at::date =
   '2026-07-05'`. Обратимо, без деплоя, данные целы. Товары без подписок в
   очередь не попадают вовсе, трогать их незачем.
2. ~~Метрики на отказ по мёртвой форме нет.~~ **СДЕЛАНО.** Ссылка в закрытой форме
   теперь отвергается ДО похода в сеть (`ErrDeadURLForm`), а не идёт в Я.Маркет за
   капчей: иначе каждая такая ссылка считалась `blocked` и двигала брейкер, а он
   один на площадку — пара старых ссылок глушила живые карточки. Считать отказы:
   `tryberrybot_scrape_requests_total{marketplace="yandex_market", status="dead_url"}`.
   Пользователю во всех трёх ботах (TG/VK/MAX) говорим, что ссылка старого формата
   и просим прислать адрес вида `market.yandex.ru/card/…` — текст общий
   (`scraper.DeadURLFormMsg`), чтобы каналы не разъезжались. Если счётчик пойдёт
   вверх, значит пора делать ленивый резолв `modelId → oskuId`.
3. **Резолв `modelId` → `oskuId`** (`cmd/ym-resolve`) не написан и, судя по
   объёму живых подписок, пока не нужен.

## Инструменты, добавленные этим разбором

- `cmd/ym-form-probe` — какая форма URL живая: статус без редиректов, Location,
  капча, канонический адрес из тела.
- `cmd/ym-card-probe` — доля наших id, открывающихся формой `/card/`; классы
  card / skeleton / captcha, цена боевым скрейпером у первых N.
- `cmd/ym-dump -proxy` — сырой дамп страницы или выдачи через RU-выход.
- `cmd/ym-proxy-check` (был) — годность кандидата в прокси. Учти: он ходит на
  `/card/`-адреса, поэтому «3 из 3» говорит про прокси, но ничего не говорит про
  форму URL, которой пользуется прод.
