НАБЛЮДАЕМОСТЬ
48 правил алертов в Alertmanager с доставкой в Telegram, почти каждое выросло из
инцидента. Экспортеры Postgres, Redis, Kafka, node. Логи в Loki, трейсы через
OpenTelemetry по OTLP в Jaeger, контекст трейса едет в заголовках Kafka.
Главный принцип: ловлю тихие отказы. Процесс жив и healthcheck зелёный, а работа
не делается. Поэтому меряю возраст последнего успешного результата, а не только
up: KafkaPartitionStuck, NoNotificationsButSubscriptionsExist, пул воркеров
stale. Плюс метрики свойств данных: происхождение цены, а не только success rate.
Алерты по симптомам, но есть и по ресурсам хоста: HostOOMKill, HostMemoryLow,
HostSwapAlmostFull. Формальных SLO нет. Если бы вводил: SLI доля товаров с
актуальной ценой и доля уведомлений, доставленных за N минут после изменения.

ИНЦИДЕНТЫ (порядок всегда один: замер, потом гипотеза, после разбора метрика или
регрессионный тест)
1) Замёрзшая партиция Kafka: лаг рос на одной партиции при живой реплике.
Первая версия, что зависла горутина, не подтвердилась. Разошёлся трекер
оффсетов после ребаланса. Фикс, метрика возраста застоя, алерт.
2) Архивная цена WB: success rate 100%, а цена врала в 97% проверок. Поймала
метрика происхождения цены. После переезда на живую карточку актуальных 90%
вместо 3%. Вывод: без ошибок не значит правильно.
3) Дедлок пула сайдкара: подвисший драйвер держал лок, пул стоял при healthy>0,
Ozon не собирался 11 часов. Теперь алерт на возраст последнего успеха.
4) Сайдкар дорастал до лимита памяти контейнера. Снимал memory.current из cgroup
раз в 5 секунд и увидел, что раздувается страница выдачи, а не течёт код. Две
первые гипотезы были неверные.
5) Мой худший промах: порты Redis и Postgres торчали в интернет, потому что
задеплоил без прод-оверрайда. Вычистил последствия, закрыл файрволом, сменил
пароли, завёл алерты на признаки повторения (неожиданный суперюзер, Redis
переведён в реплику).

ЁМКОСТЬ. Нагрузочный тест: 5000 синтетических пользователей, 30 тыс. подписок,
лаг 0, CPU реплик 4–9%. Сначала упёрся в последовательный консюмер, вынес
scraper в 3 реплики одной consumer group, потом упёрся в браузерный пул площадки.
Железо простаивало, потолок во внешних лимитах источников.

ДЕПЛОЙ И DOCKER, мои грабли
Сборка вся из кэша на старой ветке молча деплоит старый код. mem_limit не
применяется к работающему контейнеру без force-recreate. OOM в cgroup контейнера
это не OOM хоста, смотреть надо разные метрики. Graceful shutdown: SIGTERM
отменяет корневой context, оффсеты досбрасываются, потом выход. pre-push гейт:
gofmt, go vet, тесты с -race, линтеры. nginx с TLS и автообновлением
сертификатов. Ночная проверка живости исходящих узлов, перезапуск только при
реальном изменении состава.

ВОПРОСЫ ПРО KUBERNETES (отвечать честно)
В: Работал с Kubernetes? О: В проде нет. На одном сервере Compose хватает, а
кластер ради кластера не заводил. Знаю модель и то, как мой прод в неё лёг бы:
scraper в 3 репликах это Deployment с HPA по лагу консьюмера, Postgres и Kafka
это StatefulSet или вообще управляемые сервисы, restart: always это
restartPolicy, mem_limit это limits, и мой OOM в cgroup это ровно OOMKilled с
кодом 137.
В: Liveness или readiness? О: Liveness проверяет только сам процесс, иначе
падение базы перезапустит все поды разом. Зависимости и прогрев в readiness. Мой
урок про дедлок пула как раз в том, что liveness по факту жизни процесса этот
случай не ловит, нужна проверка прогресса.
В: requests и limits? О: requests для планирования, limits потолок. По памяти
превышение это OOMKilled, по CPU throttling. Для JVM heap надо ставить от лимита
контейнера: у меня Kafka Streams с RocksDB набирал гигабайт вне heap и убивался
OOM-киллером, ограничил общим LRU-кэшем.
В: Как бы деплоил без простоя? О: RollingUpdate с maxUnavailable 0 и нормальной
readiness, для рискованного канарейка. SIGTERM обработать, grace period больше
времени досброса оффсетов.

СЛАБЫЕ МЕСТА (называю сам). Kubernetes в проде не было. Единые точки отказа:
один брокер Kafka, один Postgres без реплики, бэкап раз в сутки, то есть RPO
сутки. Формальных SLO и error budget нет. Terraform и Ansible не использовал,
сервер настроен руками плюс скрипты. Опыта дежурств в команде нет, только соло.
