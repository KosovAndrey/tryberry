# Тарифы v2: фри-поиск по ссылке + каданс по волатильности

Статус: **дизайн (согласовать → реализовать).** Ветка `feat/free-tier-search-link`.
Заменяет черновик от июня: главный блокер того плана — «парсер выдачи не готов» —
**снят**: Я.Маркет и Ozon включены юзерам (`docs/features/search-by-url-ozon-yandex.md`),
WB-горячие ходят через сайдкар `wb-search-miner` (`docs/WB-SEARCH-STATUS.md`),
дедуп поисковых ссылок уже есть (scheduler группирует по `normalized_url`, map
`byQuery` в `searchSchedulerTick`). Не готов только AliExpress (X5SEC → ждёт
`ali-miner`), для MVP не нужен.

## Идея одной строкой

Free получает **1 трек поисковой выдачи** на редком кадансе — как хук/воронка;
одновременно вводим **каданс по волатильности**, который в разы режет внешнюю
нагрузку на антибот-пути и делает фри-поиск дешёвым для нас.

---

## 1. Что меняем в тарифной сетке

### Сейчас (`internal/domain/plan.go`, `domain.Plans`)

| план | товары | поиски | интервал (общий) | цена ₽ (раз / подписка) |
|---|---|---|---|---|
| free | 5 | 0 | 60м | 0 |
| lite | 20 | 3 | 30м | 199 / 189 |
| pro | 100 | 10 | 15м | 499 / 479 |
| trial (3 дня) | 100 | 10 | 15м | 0 |
| reseller_start | 5 | 1 | 1м | 990 / 940 |
| reseller_pro | 15 | 3 | 1м | 1990 / 1890 |

Одна `Interval` на оба пути (товары и поиск). Поисковый скрейп при этом сильно
дороже товарного: WB-горячие = навигация браузера в сайдкаре, Ozon = дорожка
`ozon-miner` (уже присыпан полом `OZON_SEARCH_MIN_INTERVAL_MINUTES=30м`).

### Предложение

Развести интервалы: поле `Plan.SearchInterval` (0 → берётся `Interval`,
обратная совместимость). Сетка:

| план | товары | поиски | товар-каданс | **поиск-каданс** | цена |
|---|---|---|---|---|---|
| free | 5 | **1** | 60м | **6ч** | 0 |
| lite | 20 | 3 | 30м | **1ч** | 199 / 189 |
| pro | 100 | 10 | 15м | **30м** | 499 / 479 |
| trial | 100 | 10 | 15м | **30м** | 0 |
| reseller_start | 5 | 1 | 1м | 1м (как было) | 990 / 940 |
| reseller_pro | 15 | 3 | 1м | 1м (как было) | 1990 / 1890 |

Логика:

- **free 1 поиск @ 6ч** — хук: «слежу за категорией, а не за артикулом»; 1 юзер
  = максимум 4 поисковых скрейпа в сутки (ещё меньше после дедупа и
  волатильности). Апселл-лестница очевидна: больше поисков и чаще → Lite/Pro.
- **lite 1ч / pro 30м** — поиск замедляется относительно текущего (30м/15м),
  потому что это самые дорогие скрейпы. Компенсация юзеру — волатильностный
  буст (§2): «живой» поиск опрашивается чаще расписания, застывший — реже.
  Ozon-пол 30м остаётся.
- **reseller — не трогаем**: минутная поисковая дорожка = ядро ценности тарифа
  (отдельный пул `reseller-tasks`); волатильностный бэкофф на неё НЕ
  распространяется.
- **Цены не меняем**: сетка цен свежая (Робокасса, sub-цены как nudge к
  автоплатежу); менять ценник одновременно с изменением семантики лимитов —
  двойной риск. Free-поиск усиливает воронку и без передела цен.
- **Бонус-эффект free MaxSearch=1**: при истечении платного плана notifier
  паузит поиски сверх лимита нового плана (`selectSearchPauses/Restores`,
  `cmd/notifier/main.go:419-478`). Сейчас у истёкших гаснут ВСЕ поиски; с
  free=1 самый старый поиск останется жить на редком кадансе — мягче downgrade
  и постоянное напоминание о фиче.

Открытый вопрос (решить до реализации): **замедление pro-поиска 15м→30м — это
даунгрейд для действующих pro.** Варианты: (а) принять (алерты приходят по
факту изменения, каданс — внутренняя кухня; буст вернёт частоту живым
запросам); (б) оставить pro-поиск 15м и положиться только на волатильность.
Рекомендация — (а): честнее по нагрузке, буст компенсирует.

## 2. Каданс по волатильности (ось 1, самый дешёвый рычаг)

Сейчас каданс определяется только тарифом: `eff = MIN(Interval по подписчикам)`
(+ Ozon-множитель/полы). Товар, чья цена не менялась месяц, опрашивается так же
часто, как скачущий каждый день. Меняем:

```
eff = MIN(interval по подписчикам) × volatilityMult(товар/запрос)
```

### Множитель от возраста последнего изменения цены

| цена последний раз менялась | множитель |
|---|---|
| < 3 дней назад | ×1 |
| 3 – 7 дней | ×2 |
| 7 – 30 дней | ×3 |
| > 30 дней | ×4 |
| истории ещё нет (новый трек) | ×1 (даём набрать историю) |

Ограничители:

- **Потолок**: eff ≤ 24ч — всё живое проверяем минимум раз в сутки.
- **Reseller-дорожка** (eff ≤ `resellerLaneCutoff` 2м) — исключена из бэкоффа.
- **Популярность демпфирует бэкофф**: товар/запрос с ≥5 активными подписчиками —
  множитель капится ×2 (один скрейп обслуживает многих; свежесть важнее
  экономии). Число подписчиков планировщик уже видит (строки rows на товар).
- Ozon-полы (`OZON_MIN_INTERVAL_MINUTES` 20м, `OZON_SEARCH_MIN_INTERVAL_MINUTES`
  30м) применяются ПОСЛЕ множителя, как сейчас — это полы, не потолки.
- **Буст ×0.5 для скачущих (менялась <24ч)** — НЕ в MVP: пол = каданс плана
  сохраняем как продуктовое обещание; вернуться к бусту после замера эффекта
  бэкоффа (буст съедает часть сэкономленного бюджета запросов).

### Данные для множителя

`price_history` — уже change-only (строка пишется только при изменении цены),
т.е. возраст последнего изменения = `MAX(recorded_at)` по товару. Но джойнить
партиционированную историю каждый тик планировщика дорого. Дешевле —
денормализованная колонка:

- `products.last_price_change_at TIMESTAMPTZ` — проставляет scraper-worker там
  же, где инсертит строку в `price_history`. Бэкфилл одной миграцией из
  `MAX(recorded_at)`.
- `search_queries.last_change_at TIMESTAMPTZ` — аналогично search-worker при
  изменении выдачи (изменилась мин. цена топ-N / состав позиций).
- Планировщик читает колонки в уже существующих выборках
  (`GetSchedulableProducts` / `GetSchedulable`) — ни одного нового запроса.

### Что даёт по нагрузке (прикидка)

Большинство трекаемых товаров «спят» (цена меняется реже раза в неделю). Если
~70% товаров уходят в ×2..×4 — объём скрейпов падает вдвое-втрое без потери
качества алертов (алерт = изменение; у спящих изменений нет). Для антибот-путей
(Ozon-дорожки, WB-горячие через браузер) это прямой запас прочности — ровно то,
чего не хватало, чтобы открыть поиск на фри. Волатильность режет СПРОС,
`docs/THROUGHPUT-ROADMAP.md` (ветка `feat/throughput-roadmap`) растит
ПРОПУСКНУЮ — рычаги независимые, делаются в любом порядке.

### Фаза 2 (отдельно, НЕ в этом заходе)

Дешёвый change-detection перед полным скрейпом: WB basket отдаёт
`lastChangeTime`/версии — можно спрашивать «менялось ли» до полного парса.
Отдельная дорожка в скрейпере; делать по метрикам после фазы 1.

## 3. Семантика фри-поиска (MVP)

Трек поисковой ссылки уже работает как продукт (WB/Я.Маркет/Ozon: триггеры
`trigger_type` в `search_subscriptions`, движок Decide, алерты о подешевевших
позициях) — **новой продуктовой семантики не требуется**: free получает доступ
к существующей фиче с лимитом 1 и кадансом 6ч. Ali — «скоро» (ждёт `ali-miner`).

## 4. Имплементация (чек-лист)

1. `internal/domain/plan.go`: `MaxSearch: 1` для free; поле `SearchInterval` +
   `EffectiveSearchInterval(def)`; `volatilityMult()` с юнит-тестами; сетка §1.
2. Миграция 026: `products.last_price_change_at` (+бэкфилл из `price_history`),
   `search_queries.last_change_at` (бэкфиллить нечем — NULL = ×1 до первого
   изменения... точнее NULL трактуем как «новый трек», ×1).
3. scraper-worker / search-worker: проставлять колонки при изменении цены/выдачи.
4. `cmd/scheduler/main.go`: в оба тика volatilityMult + кап популярности; в
   search-тик — `EffectiveSearchInterval`. Роутинг reseller-дорожки считать ДО
   множителя (бэкофф не должен выкидывать перекупа из fast-lane).
5. Гейтинг/тексты (TG/VK/MAX паритет):
   - показ лимитов/интервалов: `internal/telegram/plans.go:44-45`,
     `internal/vk/plans.go:41-42`, `internal/max/plans.go`, `/myplan`
     (`internal/telegram/admin.go:81-82`) — добавить строку про поиск-интервал;
   - энфорс добавления: `internal/vk/track.go:114-120`,
     `internal/telegram/bulktrack.go` (товары); поиск-лимит проверяется своим
     путём — free-экраны «Поиск по ссылке» перестают гейтить, апселл-подсказка
     при попытке добавить второй поиск;
   - notifier-паузы/ресторы используют `MaxSearch` из Plans — новый free-лимит
     подхватится сам (`cmd/notifier/main.go:419-478`), проверить сценарий
     downgrade pro→free: 1 старейший поиск должен ожить.
6. Метрики: скрейпов/час по пути (товар/поиск × МП × транспорт) до/после;
   гистограмма множителей; `pt_wb_search_fetch_total{transport=browser}`;
   конверсия free→lite после раскатки.

Порядок: (2)+(3) волатильность-данные → (1)+(4) каданс → замер на проде неделю →
(5) открытие фри-поиска → (6) наблюдение. Волатильность идёт ПЕРВОЙ и страхует
открытие фри.

## 5. Риски

- **Замедление поиска платникам** (§1, открытый вопрос) — коммуникация: алерты
  приходят при изменениях; каданс в текстах тарифов показываем для товаров, для
  поиска формулировка «до N раз в час/день».
- **Бэкофф проспит резкое движение спящего товара** — потолок ×4 ограничивает
  задержку: free-товар максимум 4ч вместо 1ч, pro-товар 1ч вместо 15м, pro-поиск
  2ч. Алерт придёт позже, но придёт; «мгновенные» скачки — ценность reseller
  (он без бэкоффа).
- **Free-поиск = рост горячих WB-запросов** (фри трекает «iphone 17», не
  капибар) — митигируется кадансом 6ч + дедупом + волатильностью; следить за
  здоровьем дорожек `wb-search-miner`.
- **search_queries.last_change_at по составу выдачи может «дребезжать»**
  (позиции топ-N тасуются без смены цен) → запрос никогда не уйдёт в бэкофф.
  MVP: считать изменением только смену минимальной цены топ-N; состав — нет.
