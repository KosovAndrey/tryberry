# Тарифы: поиск по ссылке-поиска на бесплатном тарифе (примерный план)

Статус: **план (не реализовано).** Ветка `feat/free-tier-search-link`.
Черновик — перед реализацией сверить с кодом гейтинга тарифов (пометки
«ПРОВЕРИТЬ» ниже).

## Идея одной строкой

Дать **бесплатному** тарифу возможность трекать не только конкретный товар по
ссылке, но и **ссылку поисковой выдачи** («поиск по ссылке поиска»): юзер кидает
ссылку на результаты поиска МП, бот отслеживает выдачу (напр. минимальную цену
среди подходящих / появление нужного товара). Цель — усилить бесплатный тариф как
воронку и точку входа.

## Зачем / что даёт

- **Хук бесплатного тарифа.** Трек товара по ссылке уже есть у всех; трек
  поисковой выдачи — заметно более «вкусная» фича, которая цепляет нового юзера
  сразу («слежу за ценой на *категорию*, а не на один артикул»).
- **Воронка в платные.** На фри — с жёстким лимитом (напр. 1 поиск-ссылка,
  редкий каданс); хочешь больше поисков / чаще опрос — Lite/Pro. Ровно то, что
  уже висит в задаче «новые тарифы: больше поисков по ссылкам + каданс».
- **Дифференциация.** Немногие трекеры умеют следить за поисковой выдачей, а не
  за товаром.

## Текущее состояние бэкенда (что уже есть)

- Каркас `SearchScraper` существует (см. память `search-by-url-ozon-yandex`,
  `aliexpress-search-api`, `yandex-seller-storefront`):
  - **Я.Маркет** — выдача парсится (first-pass, цены), работает direct.
  - **WB** — горячие запросы через сайдкар `wb-search-miner` (только что
    захардён relaunch'ем); холодные — direct.
  - **Ozon** — заблокирован FAB, идёт через `ozon-miner`; парсер выдачи не
    доведён.
  - **AliExpress** — выдача = `POST /aer-webapi/v1/search`, но X5SEC блок
    (ждёт `ali-miner`).
- **ВАЖНО:** сейчас поиск по URL юзерам НЕ включён — парсер выдачи требует
  доводки (память: «не включать юзерам до доводки парсера»). Это главный гейт
  фичи, не биллинг.

## План (черновик, по шагам)

### 0. Готовность парсеров (блокер, делать первым)
Прежде чем открывать юзерам — довести парсер выдачи до продакшн-качества хотя бы
на **одном-двух МП** (кандидаты: Я.Маркет — самый готовый; WB — сайдкар есть).
Ozon/Ali — позже, по мере снятия антибота.
- Критерий готовности: стабильно достаём {цена, наличие, ссылка на товар,
  название} с первой страницы выдачи; устойчивость к сменам разметки; метрика
  доли успешных парсов.
- Решить: MVP = **только Я.Маркет + WB**, Ozon/Ali «скоро».

### 1. Продуктовая семантика трека выдачи
- Что именно трекаем по ссылке-поиска? Варианты (выбрать MVP):
  - (a) **минимальная цена** среди топ-N результатов выдачи;
  - (b) появление/цена конкретного товара в выдаче;
  - (c) средняя/медианная цена (индикатор рынка).
- MVP-рекомендация: **(a) минимальная цена топ-N** — просто и понятно юзеру.
- Хранение: как отдельный тип подписки (search-subscription) vs расширение
  существующей модели подписки. **ПРОВЕРИТЬ** текущую модель подписок/трека.

### 2. Гейтинг по тарифу
- Добавить фри-лимит: напр. `free: search_links = 1`, каданс поиска — самый
  редкий (напр. раз в N часов). Lite/Pro — больше ссылок + чаще.
- **ПРОВЕРИТЬ** где сейчас описаны лимиты тарифов (план-конфиг / БД / код) и
  вписать новый лимит туда же, где `products` per plan.
- Каданс поиска обязательно завязать на будущий **каданс по волатильности**
  (см. отдельную задачу) — поисковые скрейпы дороже (антибот), фри-выдачу нельзя
  опрашивать часто.

### 3. UX бота (TG/VK/MAX — паритет)
- Распознать, что пришла ссылка **выдачи**, а не товара (у `SearchScraper` уже
  есть `MatchesSearch`), и предложить «трекать этот поиск».
- Экран: показать топ-N результатов + выбрать, что трекать (мин. цена / товар).
- Сообщения об изменении — как у товарных алертов, через тот же notifier.

### 4. Нагрузка / антибот (критично)
- Поисковые скрейпы бьют по **антибот-путям** (WB-горячие, Ozon, Ali), которые и
  есть внешний потолок. Открытие фри-юзерам = рост объёма горячих поисков.
- Митигации: жёсткий фри-лимит + редкий каданс + дедуп одинаковых поисковых
  ссылок между юзерами (как дедуп товаров в scheduler по `byProduct` — сделать
  аналог `bySearch`).
- Держать поисковый трафик на sticky-сессии сайдкара; при стене — рычаг прокси
  на дорожку (см. `docs/WB-SEARCH-STATUS.md`).

### 5. Метрики / алерты
- Доля успешных парсов выдачи по МП; latency; объём поисковых скрейпов; конверсия
  фри→платный после введения фичи.

## Риски

- **Парсер выдачи хрупок** — смена разметки МП ломает фичу у всех разом (в
  отличие от товарной карточки). Нужны метрики парса + быстрый фикс.
- **Антибот** — фри-объём горячих поисков может провоцировать стены (как в
  WB-эпизоде под нагрузочным тестом). Отсюда жёсткий лимит + каданс + дедуп.
- **Ozon/Ali не готовы** — честно коммуницировать «пока Я.Маркет/WB».

## Порядок

1. Довести парсер выдачи (Я.Маркет + WB) до прод-качества + метрика парса.
2. Дедуп поисковых ссылок в scheduler (`bySearch`) — до открытия юзерам.
3. Модель search-subscription + гейтинг фри-лимита.
4. UX бота (TG→VK→MAX).
5. Каданс по волатильности для поисковых скрейпов (связка с отдельной задачей).
6. Раскатка на фри с жёстким лимитом, наблюдение за антибот-метриками.
