# price-insight — материализация «честной цены» на Kafka Streams (JVM)

Статус: принято к реализации, 11.08.2026
Связано: `docs/features/honest-price.md`, `internal/domain/honest_price.go`,
`internal/repository/postgres/price_history.go`, `docs/SCALING-NOTIFIER-DELIVERY.md`

---

## 1. Проблема

`PriceHistoryRepo.Stats` считает time-weighted минимум и медиану за 30/90 дней
**SQL-запросом на каждое обращение** — на каждое решение о триггере в notifier и
на каждый дайджест. Запрос идёт по партиционированной `price_history` с
change-only сегментами: чтобы получить медиану по времени, нужно поднять все
сегменты, пересекающие окно, и взвесить их по длительности.

Стоимость линейно растёт с числом отслеживаемых товаров и с частотой проверок
(на тарифе Reseller Start — раз в минуту). Это горячий путь: он стоит между
событием об изменении цены и отправкой уведомления.

Агрегаты при этом **пересчитываются с нуля каждый раз**, хотя меняются
инкрементально — приходит одна новая точка, а пересчитывается всё окно.

## 2. Решение

Отдельный сервис, который держит агрегаты по каждому товару в стейте, обновляет
их инкрементально по потоку `price-events` и материализует готовый вердикт.
Notifier читает готовое значение вместо агрегации.

```
scraper → price-events → ┌─ notifier (Go)      — триггеры, outbox, доставка
                         └─ price-insight (JVM) — агрегаты + вердикт
                                    │
                                    ├→ price-verdict (compacted topic)
                                    └→ price_insight (таблица в Postgres)
```

## 3. Почему JVM, а не Go

Задача — **stateful-обработка потока с временными окнами и гарантией
exactly-once**. В Go есть только клиенты Kafka: `segmentio/kafka-go` (используем),
`confluent-kafka-go`. Это библиотеки чтения и записи, не процессоры потока.

Своими руками пришлось бы написать:
- хранилище состояния с персистентностью и вычиткой хвоста,
- восстановление стейта после падения инстанса,
- корректное поведение при ребалансе consumer group,
- транзакционную запись результата вместе с коммитом оффсета.

Kafka Streams даёт всё это как часть библиотеки: state store на RocksDB,
changelog-топик для восстановления, `exactly_once_v2`, управление назначением
партиций при ребалансе.

**Отвергнутые альтернативы:**

| Вариант | Почему нет |
|---|---|
| Написать на Go руками | Перечисленное выше — месяцы работы и собственные баги в том, что уже решено библиотекой |
| Apache Flink | Требует кластер (JobManager + TaskManager). Для одного инстанса и одного потока избыточен по эксплуатации |
| Материализованные представления ClickHouse | Не выражает логику вердиктов (пороги, гейт по возрасту наблюдения). Плюс ещё один тяжёлый компонент в инфраструктуре |
| Кэшировать `Stats` в Redis | Лечит симптом. Инвалидация при каждом изменении цены возвращает нас к полному пересчёту |

Отдельно: это **не переписывание работающего кода на другой язык**. Меняется
модель вычисления — с «пересчитать по запросу» на «поддерживать инкрементально».
Логика вердиктов переезжает вместе с агрегацией, чтобы не размазывать один
домен по двум сервисам.

## 4. Почему Processor API, а не Streams DSL

DSL умеет `count`, `sum`, `reduce`, `aggregate` по tumbling / hopping / session
окнам. **Time-weighted медиана по change-only сегментам через них не
выражается**: у нас хранятся точки изменения, а «обычная цена» — это медиана по
времени, где товар провёл половину окна, а не по числу записей. Стабильный товар
может иметь одну запись за сорок дней; для DSL это одно значение, для нас —
сегмент длиной сорок дней с максимальным весом.

Поэтому:
- собственный `KeyValueStore<Long, PriceSegments>` — список сегментов на товар;
- `Processor` вместо DSL-оператора;
- `Punctuator` по stream-time — вычистка сегментов старше 90 дней и пересчёт
  вердиктов у товаров, которые давно не обновлялись (окно едет, даже когда
  событий нет).

## 5. Границы и деградация

- **Источник правды остаётся в Go.** `price_history` в Postgres пишет scraper,
  как и сейчас. price-insight — производное представление, его можно в любой
  момент пересобрать проигрыванием топика с начала.
- **Notifier читает вердикт, но не зависит от него жёстко.** Нет свежего
  вердикта в `price_insight` — откат на текущий путь через `Stats`. Java-сервис
  лёг → продукт работает, вердикты просто перестают обновляться.
- **Общей кодовой базы нет.** Контракт — JSON-схема события в Kafka.

## 6. Контракт входа

Топик `price-events`, ключ — `product_id` в виде строки. Поток уже
партиционирован по товару, co-partitioning для стейта получается бесплатно.

```json
{
  "product_id": 123,
  "marketplace": "wb",
  "old_price": 1990.0,
  "new_price": 1490.0,
  "recorded_at": "2026-08-11T12:00:00Z",
  "in_stock": true,
  "was_in_stock": true
}
```

**Нюансы, которые определяют логику агрегации:**

1. `new_price = 0` означает «нет в наличии» (см. `cmd/scraper/main.go`, комментарий
   про back_in_stock). Такие точки **нельзя включать в минимум и медиану** — иначе
   любой уход товара из наличия обнулит минимум. При этом они **разрывают
   сегмент**: интервал отсутствия не должен засчитываться как время по последней
   известной цене.
2. Поля аддитивны — старые сообщения без `in_stock` дают `false`. Обработчик
   обязан это переживать.
3. `recorded_at` — event-time, по нему и надо вести stream-time.

## 7. Выход

- **Топик `price-verdict`**, compacted, ключ `product_id` — актуальный вердикт по
  товару. Compaction держит ровно последнее состояние, retention не нужен.
- **Таблица `price_insight`** в Postgres — для чтения из Go без второго
  консьюмера. Пишем idempotent upsert по `product_id`.

Схема (миграция goose):

```sql
CREATE TABLE IF NOT EXISTS price_insight (
    product_id   BIGINT      PRIMARY KEY,
    verdict      SMALLINT    NOT NULL,
    min_30       NUMERIC(12,2),
    median_30    NUMERIC(12,2),
    min_90       NUMERIC(12,2),
    min_all      NUMERIC(12,2),
    observed_since TIMESTAMPTZ,
    computed_at  TIMESTAMPTZ NOT NULL
);
```

## 8. Правила вердикта

Портируются из `internal/domain/honest_price.go` без изменения семантики:

- гейт по **возрасту наблюдения** (7 дней в проде), а не по числу точек;
- медиана, а не среднее — устойчива к выбросу и к попытке накрутить нашу же
  историю одним скачком;
- порядок проверок: `LowestEver` → `Lowest90` → `Lowest30` → `Typical` →
  `AboveTypical`.

Тесты берутся с теми же кейсами, что в `honest_price_test.go`, — прямая сверка
двух реализаций на одинаковых входах.

## 9. Гарантии

`processing.guarantee = exactly_once_v2`: запись в выходной топик, обновление
changelog стейта и коммит оффсета входного топика идут одной транзакцией Kafka.
При падении между ними инстанс поднимается на согласованном состоянии, без
задвоения вердиктов и без потери.

Запись в Postgres вне транзакции Kafka, поэтому upsert обязан быть идемпотентным
(`ON CONFLICT (product_id) DO UPDATE`) — при повторной обработке результат тот же.

## 10. Ресурсы

8 CPU / 16 GB на сервере, из них Kafka со Zookeeper и контур наблюдаемости уже
занимают около половины. Kafka Streams с RocksDB — 400–600 МБ RSS, из них
существенная часть off-heap под block cache RocksDB. Приемлемо.

Настроить: `-XX:MaxRAMPercentage`, размер block cache и write buffer RocksDB,
лимит памяти контейнера (сейчас лимиты не выставлены ни у одного сервиса —
завести хотя бы у этого).

## 11. Порядок работ

1. Скелет проекта, зависимости, конфиг. Топология-заглушка.
2. Доменная модель сегментов, инкрементальная агрегация, `Punctuator`.
   Юнит-тесты на `TopologyTestDriver` — без Kafka и без Docker.
3. Порт правил вердикта, сверка с Go-тестами.
4. `exactly_once_v2`, sink в Postgres, миграция, метрики Streams через
   Micrometer в существующий Prometheus, панель в Grafana.
5. Интеграционные тесты на Testcontainers (Kafka + Postgres).
6. Деплой в compose, прогон на реальном потоке параллельно со старым путём,
   сравнение результатов.
7. Переключение notifier на чтение вердикта с fallback.

## 12. Открытые вопросы

- **Serde**: JSON (просто, схема живёт в коде) против Avro со Schema Registry
  (контракт versioned, но ещё один компонент). Пока JSON — согласовано с тем, что
  Go-сторона уже пишет JSON. Пересмотреть, если появится второй потребитель.
- **Ретеншен `price-events`**: для пересборки стейта проигрыванием с начала нужен
  достаточный retention либо compaction. Проверить текущую настройку топика.
- Нужен ли `num.standby.replicas` — актуально только при масштабировании на
  несколько инстансов, сейчас нет.
