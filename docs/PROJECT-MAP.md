# PROJECT-MAP — карта решений TryBerry для технического собеседования

Составлено 14.08.2026 чтением кода. **Опора — код**, доки использованы только
как источник замеров и потом сверены. Расхождения вынесены в §6.

По итогам первого прохода часть найденного починена в тот же день — см. **§9**.
Разделы ниже описывают состояние **после** починок; там, где было «как есть до»,
это сказано явно, потому что сама история находки ценнее итога.

Каждое число помечено:
- **[замер]** — кто-то это реально померил, указано где;
- **[счёт]** — посчитано мной из данных в репозитории;
- **[предпол.]** — предположение, на собеседовании подавать как гипотезу;
- без пометки — константа из кода (её можно открыть и показать).

## 0. Одноабзацный ответ на «расскажите о проекте»

Телеграм/VK/MAX-бот, который следит за ценами товаров на четырёх российских
маркетплейсах (Wildberries, Ozon, Яндекс.Маркет, AliExpress) и шлёт пуш, когда
цена упала по выбранному правилу. Плюс подписка не на товар, а на целую
поисковую выдачу. Плюс вердикт «честная ли это скидка» по собственной истории
наблюдений. 12 сервисов в docker compose на одной VPS (8 CPU / 16 ГБ), из них
7 на Go, 4 Python-сайдкара с браузером (антибот) и один на JVM (Kafka Streams).
Один разработчик, ~42 тыс. строк Go, 32 миграции, боевые пользователи с 14.08.2026.

**Единственная фраза, которую надо сказать первой:** узкое место системы —
не наш код и не база, а **антибот маркетплейсов**. Почти каждое нетривиальное
решение в проекте — это компромисс с чужой защитой от парсинга.

## 2. Сквозной путь данных

### 2.1. Одно изменение цены: от тикера до сообщения

**Шаг 1. Планировщик решает, что пора.** `cmd/scheduler/main.go:171`
`productSchedulerTick`, тик раз в 20 с.

1. `productRepo.GetSchedulableProducts` — **одна строка на каждую активную
   подписку** (`internal/repository/postgres/product.go:245`): join
   `products × subscriptions × users`, без LIMIT.
2. В Go группируется по `product_id`; эффективный интервал = **MIN по
   подписчикам** (`Plan.EffectiveInterval`, `internal/domain/plan.go:107`).
   Логика «кто как часто» живёт в коде (`domain.Plans`), а не в БД —
   осознанно, чтобы цифры крутились без миграции.
3. Волатильностный бэкофф: `domain.ApplyVolatility` (`internal/domain/cadence.go:67`)
   умножает интервал на ×1 / ×1.5 / ×2 / ×3 по возрасту последней смены цены
   (5 / 10 / 20 дней), капится ×2 при ≥5 подписчиках, **не применяется** к
   товарам, у которых есть reseller-подписчик.
4. Созревшие (`now - last_enqueued_at ≥ eff`) → `ClaimEnqueued` (один UPDATE
   `last_enqueued_at = NOW()`) **до** эмиссии. Claim до отправки — потому что
   планировщик синглтон, гонок нет, а провал отправки лучше потерять, чем
   задвоить.
5. Ozon по подстроке `ozon.ru` в URL уезжает в **отдельный топик**
   `ozon-scrape-tasks`, остальные — в `scrape-tasks`. Ключ = `product_id`.

**Шаг 2. Скрейпер забирает.** `cmd/scraper/main.go:247` — errgroup с двумя
консьюмерами в одном процессе: `scrape-tasks` (concurrency 8) и
`ozon-scrape-tasks` (concurrency 6). Оба используют
`Consumer.RunConcurrent` (`internal/kafka/consumer.go:168`).

**Шаг 3. Скрейп.** `registry.Scrape` выбирает скрейпер **по URL**, не по
колонке `marketplace` (`internal/scraper/registry.go:28`). На каждое сообщение
вешается `context.WithTimeout(120s)` (`cmd/scraper/main.go:268`) — без него
зависший вызов держал слот пула и морозил вотермарк партиции.

Для WB (`internal/scraper/wildberries.go:157`) параллельно двумя горутинами
идут: живой `u-card` через xray и архивный `price-history.json` с basket-CDN.
Цена берётся **с живого**, архив даёт историю/имя/картинку. Рубильник
`WB_UCARD_PRIMARY=false` возвращает старый порядок.

**Шаг 4. Запись.** `cmd/scraper/main.go:297-341`:
- `UpdateScrapedData` возвращает **предыдущее** `in_stock` (нужно для триггера
  «снова в наличии»);
- предыдущая цена — Redis `price:<id>`, фолбэк на `price_history`;
- **change-only**: строка в `price_history` пишется, только если цена
  изменилась (`pricesEqual` округляет до копеек — `cmd/scraper/main.go:453`);
- смена цены → `TouchPriceChanged` (сброс волатильностного бэкоффа);
- бэкфилл истории маркетплейса (`PrependOlder`) — под
  `pg_advisory_xact_lock(product_id)`;
- при OOS в историю и кэш **не пишем ничего**.

**Шаг 5. Событие.** `PriceEvent` публикуется **на каждом скрейпе**, а не только
при изменении цены. Причина: строгая per-plan модель — free-подписчик с
60-минутным интервалом должен иметь свою точку оценки, даже если цена
изменилась между его чек-поинтами (`cmd/scraper/main.go:344-352`). При OOS
`new_price` принудительно = 0.

**Шаг 6. Notifier решает.** `cmd/notifier/main.go:523` `makeHandler`,
последовательный `Consumer.Run`.

Для каждой активной подписки на товар:
1. **throttle**: `shouldEvaluate(last_evaluated_at, интервал_тарифа)` —
   доставку держим строго по плану подписчика, даже если товар скрейпится
   чаще из-за соседа с дорогим тарифом;
2. решение о срабатывании — **общий движок** `searchsub.Decide`
   (`internal/searchsub/engine.go:53`), тот же, что у поиск-подписок:
   первое срабатывание по типу триггера от `first_seen_price`, повторные —
   только ниже цены последнего уведомления;
3. идемпотентность: ключ `subID:price:recordedAt`, проверка в `notifications`;
4. «честная цена» считается **лениво и мемоизированно на событие**
   (`cmd/notifier/main.go:576-591`) — только когда алерт реально уходит;
5. алерт кладётся в **durable outbox** `pending_alerts` с
   `deliver_after = now + Plan.BundleWindow()` (0 у reseller, 15 мин у free);
6. **стейт подписки двигается здесь, на решении** (`UpdateBaseline`,
   `notified=true`), а доставка случится позже.

**Шаг 7. Флашер доставляет.** `cmd/notifier/flusher.go:85`, тик 1 с:
`FetchDue(limit 500)` → группировка по юзеру → **один токен глобального
`rate.Limiter` (25 rps) на юзера** → один алерт шлётся «богато» с фото,
два и больше — одним бандл-сообщением. Провал → `attempts++`, экспонента
5 с → 30 мин, потолок 10 попыток, потом строка «похоронена» и удаляется
чисткой раз в час с retention 7 дней.

**Шаг 8. Маршрутизация канала.** `deliverer.targets`
(`cmd/notifier/delivery.go:105`) читает `users.notify_channel`
(`auto|tg|vk|max|both|all`). Успех = доставлено **хотя бы в один** канал.

#### Где теряется, где дублируется

| место | что бывает | почему приемлемо |
|---|---|---|
| `producer.Send` в scraper упал | цена в БД есть, события нет → notifier не оценит эту точку | следующий скрейп даст новое событие. **Реально случилось** при рестарте Kafka на выкатке price-insight (см. §8, история 8) |
| handler notifier вернул ошибку | **сообщение не ретраится немедленно** — см. §7.1, это ключевой подводный камень | следующий скрейп даст новое событие |
| `Insert` в `pending_alerts` прошёл, `UpdateBaseline` упал | алерт уйдёт, baseline не сдвинется → возможен повтор | `notifications.idempotency_key` включает цену и `recorded_at` — точный повтор гасится |
| флашер доставил, `MarkSentBatch` упал | **дубликат сообщения** при ретрае. Осознанно принято (`flusher.go:206`) | БД-сбой в этой точке редок |
| падение scraper с in-flight сообщениями | оффсеты не закоммичены → перечитывание → повторный скрейп | все записи идемпотентны (апсерты + change-only) |
| ребаланс группы | `offsetTracker.register` сбрасывает курсор партиции, in-flight прошлой генерации бросается | at-least-once сохраняется, новый владелец перечитает |

### 2.2. Путь платежа

1. **Витрина**: юзер жмёт «Оплатить» в боте → `payment.Service.Start` /
   `StartSubscription` (`internal/payment/service.go:64`).
2. Для подписки **сначала пишется согласие** в `subscription_consents` и
   только потом создаётся платёж — «без записи оплату не начинаем»
   (защита от чарджбэка/ЗоЗПП, `service.go:87`).
3. Применяется «ожидающая скидка» из Redis; в БД заводится строка `payments`
   в статусе `pending` с UUID-`idempotence_key`.
4. Провайдер (`PAYMENT_PROVIDER`: `robokassa` — основной, `yookassa` — за
   флагом) возвращает URL оплаты, внешний id пишется в `yk_payment_id`.
5. **Вебхук** приходит в `api`:
   - Робокасса `ResultURL` **подписан** (`Password2`) → подпись и есть
     доверие; `InvId == payments.id`; дополнительно сверяется сумма
     (`cmd/api/main.go:382-427`), ответ `OK{InvId}`;
   - ЮKassa вебхуки **не подписывает** → тело не доверяем, статус
     **перечитываем по id** через API (`cmd/api/main.go:334`).
6. `api` публикует `ConfirmedEvent{payment_id, user_id}` в топик `payments`
   (ключ = `user_id`). Событие провайдеро-нейтрально: несёт только наш id,
   применяющая сторона перечитает строку.
7. **bot-worker** применяет: `PaymentRepo.MarkSucceeded`
   (`internal/repository/postgres/payment.go:98`) — одна транзакция:
   `UPDATE payments SET status='succeeded' WHERE status='pending' RETURNING …`
   (только первый переход проходит) + `SELECT … FROM users FOR UPDATE` +
   продление плана. **Это и есть идемпотентность вебхука.**
8. Дальше best-effort и вне транзакции: уведомление, активация/продление
   `billing_subscriptions`, гашение промокода, реферальная награда.
9. **Автосписания**: `payment.Charger` (`internal/payment/charger.go`) в
   bot-worker, тик раз в час. `ClaimDueForCharge` атомарно двигает
   `next_charge_at` на `retryAt` (это одновременно claim и расписание
   ретрая), затем инициирует рекуррент. Успех подтверждается **тем же
   ResultURL**. Отказ → dunning-счётчик `fail_count`, после потолка подписка
   `expired`.

## 3. Решения и их цена

### 3.1. Kafka

| решение | где | почему (если выводится) | альтернатива | цена |
|---|---|---|---|---|
| 11 топиков, ключ = сущность (`product_id`/`query_id`/`user_id`) | см. таблицу ниже | порядок в пределах сущности + co-partitioning для стейта price-insight | один топик с типом в теле | больше топиков в мониторинге |
| Ozon в **отдельный топик** `ozon-scrape-tasks` + своя группа | `cmd/scraper/main.go:183` | браузерный скрейп 3–5 с занимал бы слоты пула быстрых WB/YM | общий топик с приоритетом | дублирование конфигурации параллелизма |
| Reseller в **отдельный топик** `reseller-tasks` | `cmd/scheduler/main.go:121` | независимое масштабирование + свой пул токенов | шардирование по ключу | запрос с reseller-подписчиком целиком уезжает в fast-lane, обычные подписчики того же запроса режутся уже throttl'ом в воркере |
| at-least-once везде, **exactly-once только внутри price-insight** | `internal/kafka/consumer.go:75` | все апсерты идемпотентны | транзакции в Go | нужна дисциплина идемпотентности в каждом хендлере |
| **Вотермарк непрерывного префикса** вместо коммита каждого сообщения | `internal/kafka/consumer.go:277-399` | параллельная обработка не должна «перепрыгивать» коммитом необработанное | коммит по одному (медленно) или коммит max (потеря) | ~150 строк своего кода, который **дважды ломался** (см. §8, история 3) |
| Батч-коммит раз в 500 мс | `consumer.go:150` | не делать RPC на каждое сообщение | коммит сразу | окно потери ≤500 мс, безопасно при at-least-once |

### 3.4. Скрейпинг и антибот

| площадка | защита | как обходим | где |
|---|---|---|---|
| **Wildberries** карточка | basket-CDN открыт; `u-card` 403-ит датацентровый RU-IP | цена с живого `u-card` **через xray** (зарубежный exit), архив basket — только история/имя/фото; идут **параллельно** | `wildberries.go:157-220` |
| **WB поиск** | `wbaas` режет горячие запросы 403 — различие **в транспорте**, не в IP | пул `x-search-token` из headful-браузера + фолбэк горячих в `wb-search-miner` | `token_pool.go`, `WB_SEARCH_BROWSER_URL` |
| **Ozon** | FAB: JS-VM challenge + JA3 + репутация IP | путь A: `bogdanfinn/tls-client`, профиль `Okhttp4Android13`, заголовки мобильного приложения + cookie аккаунт-сессии. Путь B (**в проде**): браузерный пул camoufox | `ozon.ru`, `ozon-miner/server.py` |
| **Яндекс.Маркет** | SmartCaptcha | **direct без прокси** — probe доказал, что датацентровый IP держит поток | `yandex_market.go` |
| **AliExpress** | X5SEC | карточка direct; выдача — фолбэк в `ali-miner` | `aliexpress_search.go` |

Ключевые решения:
- **Два разных HTTP-стека осознанно.** «Чистые» пути (basket-CDN, витрина
  продавца, внутренние сайдкары) ходят плоским `net/http` с тюнингованным
  пулом (`MaxIdleConnsPerHost: 32` — дефолтные 2 заставляли пересоздавать TLS
  под конкурентным консьюмером, `internal/scraper/transport.go:29`). Пути с
  проверкой TLS-отпечатка — через `bogdanfinn/tls-client`. Смешивать нельзя,
  и это прямо записано в комментарии транспорта.
- **Rate limiting per-marketplace, на реплику**: `golang.org/x/time/rate`
  внутри каждого скрейпера. Значения — «потолки вежливости», не измеренные
  лимиты, и это честно написано в compose (`docker-compose.yml:229-230`).
  В проде 3 реплики → умножай на 3.
- **Прокси**: мобильный РФ-прокси отменён 03.07.2026. Сейчас `OZON_PROXY_URL`
  пуст, всё идёт direct, кроме Telegram-egress и WB `u-card` (оба через xray).
  Код при этом сохранил цепочку фолбэков `YANDEX_PROXY_URL → OZON_PROXY_URL`,
  которая сейчас разрешается в пустую строку.
- **Ozon-троттл выключен** (`OZON_MIN_INTERVAL_MINUTES=0`,
  `OZON_INTERVAL_MULTIPLIER=1`) — Ozon идёт полным тарифным кадансом. Остался
  как аварийный рычаг. **Отдельная ручка** — пол Ozon-**поиска** 30 мин с
  джиттером ±40%: выдача ротируется и тянется через одну прогретую дорожку.
- **Джиттер детерминирован** по паре (`query_id`, `last_enqueued_at`)
  (`cmd/scheduler/main.go:352`). Тонкий момент: если разыгрывать порог заново
  на каждом тике, сработает первый же тик с малым значением и всё
  распределение съедет к нижней границе. Это ровно тот вопрос, который любят
  задавать.

### 3.5. Конкурентность в Go — где именно смотреть

| приём | файл:строка |
|---|---|
| `errgroup` на два консьюмера, общий ctx | `cmd/scraper/main.go:247-250` |
| пул воркеров: `sem chan struct{}` + `sync.WaitGroup` | `internal/kafka/consumer.go:176-251` |
| фоновая горутина-коммиттер + канал `commitStopped` для упорядоченного останова | `consumer.go:180-194`, `:256-258` |
| `sync.Mutex` вокруг карты оффсетов | `consumer.go:279-292` |
| `context.WithTimeout` на одно сообщение | `cmd/scraper/main.go:268` |
| две горутины + `WaitGroup` на параллельный скрейп WB | `internal/scraper/wildberries.go:178-189` |
| `rate.Limiter` per-marketplace | `wildberries.go:78`, `ozon.go`, и т.д. |
| глобальный `rate.Limiter` доставки (25 rps) | `cmd/notifier/flusher.go:86` |
| `signal.NotifyContext(SIGTERM, SIGINT)` | в каждом `cmd/*/main.go` |
| graceful shutdown HTTP | `internal/health/server.go:25-29` |
| `sync.Mutex` в пуле токенов (счётчик 429 на слот) | `internal/scraper/token_pool.go:43` |
| мемоизация через замыкание (без локов, цикл последователен) | `cmd/notifier/main.go:576-591` |
| Python: `asyncio.Lock` на дорожку + `asyncio.wait_for` как дедлайн под локом | `ozon-miner/server.py:468-480` |

**Слабое место graceful shutdown** (спросят обязательно): при SIGTERM
`signal.NotifyContext` отменяет корневой ctx, а от него наследуются
и in-flight обработчики. То есть незавершённые скрейпы **обрываются**, их
запросы к БД падают по отменённому контексту, оффсеты не коммитятся →
перечитывание при старте. Отдельного окна дренажа («перестань фетчить, доделай
in-flight со свежим контекстом») нет. Работает только потому, что всё
идемпотентно.

### 3.7. Уведомления

- **Троттлинг двухуровневый.** Каданс скрейпа (MIN по подписчикам) и
  каданс *оценки подписки* (`last_evaluated_at` + интервал тарифа) — разные
  вещи. Плюс третий уровень для поиска: `Plan.SearchCooldown` — анти-спам
  `below_target` (6 ч у free, выключен у reseller). Ранее это была единая
  константа 6 ч, и она обнуляла минутный каданс перекупа: «11 из 12
  уведомлений выбрасывались» (`cmd/search-worker/searchloop.go:316-320`).
- **Бандлинг** — окно `Plan.BundleWindow()`: 0 / 5 / 10 / 15 мин по тарифу.
  Кладётся консьюмером в `deliver_after`, склеивает флашер.
- **Каналы**: TG / VK / MAX. Успех = хотя бы один. Полное падение канала
  ловится алертом `NotificationChannelFailing`.
- **При сбое**: 10 попыток с экспонентой 5 с → 30 мин, потом строка бросается
  (`attempts >= maxAttempts` выпадает из `FetchDue`) и чистится через 7 дней.
- **Перманентные ошибки Telegram обрабатываются, но не флашером, а слоем ниже.**
  `deliverer.deliver` (`cmd/notifier/delivery.go:221`) при `ErrTelegramPermanent`
  (4xx кроме 429: бан бота, чат не найден, битая картинка) и отсутствии других
  сработавших каналов возвращает **nil** — то есть флашер считает алерт
  доставленным и ретраев не будет вовсе. Метрика при этом честная:
  `notifications_delivered_total{channel="tg",status="skipped"}`.

  > Я сам ошибся на этом месте в первом проходе, написав, что заблокировавший
  > бота юзер съедает все 10 попыток. Проверил по коду — не съедает.
  > Стоит помнить как пример: «ретраи есть» и «ретраи применяются к этой
  > ошибке» — разные утверждения, и второе надо смотреть, а не выводить.

### 3.9. Деплой и эксплуатация

- `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d`.
  Прод-оверлей делает четыре вещи: добавляет nginx/certbot/node-exporter/бэкапы,
  **сбрасывает публикацию портов** (`ports: !reset []`), ставит
  `restart: unless-stopped`, задаёт `replicas: 3` для scraper.
- Число реплик держится **в оверлее**, а не флагом `--scale`, потому что любой
  `up -d` без флага тихо откатывал бы в одну реплику.
- `make guard-clean-shell` — падает, если в шелле экспортированы переменные,
  которые перебьют `.env` при интерполяции compose. Прямое следствие инцидента:
  граблю поймали дважды.
- `make check-ports` — наружу разрешены только 80/443 nginx.
- Секреты: только в `.env` на сервере (в git его нет), `xray/config.json` в
  `.gitignore`, роли Postgres разведены (`tryberry_app` — DML, `tryberry_monitor` —
  `pg_monitor`, суперюзер только для DDL).
- TLS: Let's Encrypt + certbot в цикле, nginx reload раз в 6 ч.
- **Лимиты ресурсов не выставлены ни у одного сервиса, кроме price-insight**
  (`mem_limit: 1g`). Обоснование там же: Kafka Streams держит block cache
  RocksDB вне heap.
- **CI нет вообще.** Ни GitLab CI, ни GitHub Actions — проверено. `make deploy`

## 4. price-insight (JVM) — разбор для Java-секции

Java 21, Spring Boot 3.5, Kafka Streams, RocksDB. **Единственный сервис не на Go.**

### 4.1. Что он делает и чем не является

Держит по каждому товару сегментное состояние цены, инкрементально считает
`min30 / median30 / min90 / minAll`, применяет те же правила вердикта, что
`internal/domain/honest_price.go`, и материализует результат в compacted-топик
`price-verdict` и в таблицу `price_insight`.

**Критично для честного рассказа:** таблицу `price_insight` **никто не читает**.
Проверено grep'ом — в Go нет ни одного упоминания. Сервис выкачен 13.08.2026 в
режиме наблюдения; переключение notifier сознательно не сделано, потому что
соврало бы ~1200 товарам (§4.6).

### 4.2. Топология

`PriceInsightTopology.build` (`price-insight/src/main/java/.../stream/PriceInsightTopology.java`)
— **низкоуровневый Processor API**, а не DSL:

```
addSource("price-events")  → addProcessor("assess", PriceInsightProcessor)
                              ├ addStateStore(persistentKeyValueStore "product-state")
                              └ addSink("price-verdict")
```

Топология собрана в отдельном классе от Spring-конфигурации специально, чтобы
гонять её на `TopologyTestDriver` без брокера и Docker.

**Почему Processor API.** Здесь важно рассказать правильную версию: в первой
редакции дока было написано «time-weighted медиана через DSL не выражается» —
и **это неверно**, `groupByKey().aggregate()` с собственным `Aggregator` и Serde
удержит какое угодно состояние. Аргумент был исправлен коммитом `c192044`.
**Настоящая причина — `Punctuator`**: у DSL нет хука на излучение по таймеру, а
он нужен принципиально, потому что окно едет само и вердикт стабильного товара
протухает молча. Кастомное состояние — довод второй.

### 4.3. Состояние: почему сегменты, а не точки

`ProductState` хранит список полуинтервалов `Segment(price, from, to)`,
`to == null` — открытый сегмент (текущая цена). Плюс отдельно то, что нельзя
восстановить после `prune`: `observedSince`, `minAll`, `lastEventAt`,
`lastEmitted`.

Четыре нетривиальных инварианта:
1. **Склейка одинаковых цен.** `price-events` публикуется на каждом скрейпе, а
   `price_history` — только на смене цены. Без склейки у reseller с минутным
   кадансом набегало бы ~130 000 сегментов на товар за 90 дней retention, и
   каждое событие переписывало бы весь снимок в RocksDB и в changelog. Со
   склейкой размер стейта = числу реальных смен цены, ровно как в Go.
2. **OOS рвёт сегмент** и не открывает новый — иначе время отсутствия
   засчиталось бы как время по последней цене.
3. **Опоздавшее событие игнорируется** по `lastEventAt` (не по открытому
   сегменту — при OOS открытого сегмента нет, и событие проехало бы мимо).
4. **Минимум в окне считается по факту пересечения, без требования ненулевой
   длительности**: только что открытый сегмент длится ноль, но выбросить его
   нельзя — при падении 1000→700 минимум за 30 дней отрапортовал бы 1000.
   Из медианы он выпадает сам (вес нулевой). Это не расхождение, а разная
   природа метрик.

Медиана — **нижняя** взвешенная: `acc * 2 >= total`. Это дословно условие
Go-запроса `cum >= tot / 2.0`. На равенстве половин Go отдаёт дешёвый сегмент,
а `acc > total/2` отдал бы дорогой, и «обычная цена» превратилась бы в
«выше обычной».

### 4.4. Пунктуатор

`context.schedule(6h, PunctuationType.STREAM_TIME, this::punctuate)`.

- **STREAM_TIME, а не WALL_CLOCK_TIME**: при переигрывании топика с начала
  настенное время дало бы один тик на всю историю, а stream-time идёт вместе с
  данными и воспроизводит ход окна.
- Тик делает **полный обход store** — O(числа товаров). Честно записано, что
  при кратном росте каталога это надо менять на очередь «когда пересчитать».
- Обратно в store пишет **только при фактическом изменении** (`pruned ||
  emitted`), потому что при `exactly_once_v2` каждый `put` уезжает в
  changelog-топик, и безусловная запись по всему каталогу раз в тик — трафик
  на ровном месте.

### 4.5. Гарантии

- `PROCESSING_GUARANTEE = exactly_once_v2` + `isolation.level=read_committed`:
  запись в выходной топик, обновление changelog и коммит входного оффсета —
  одна транзакция Kafka.
- `auto.offset.reset = earliest`: топик для нас источник пересборки стейта.
- `LogAndContinueExceptionHandler` на десериализации: по умолчанию Streams
  валит поток, а `REPLACE_THREAD` поднимает его заново — получался бесконечный
  цикл на одной битой записи.
- `setUncaughtExceptionHandler → REPLACE_THREAD`: единичный сбой потока не
  должен ронять сервис.
- **Проекция в Postgres вынесена наружу транзакции** — отдельный batch-консьюмер
  `price-verdict` (`VerdictListener` / `VerdictProjector`). Обоснование
  дословно: коммит оффсета и INSERT в Postgres — два разных ресурса,
  `exactly_once_v2` на них не распространяется. Отсюда требование
  идемпотентного `ON CONFLICT DO UPDATE` и гарантия at-least-once на этом
  участке.
- **Защиты «не затирать более свежий computed_at» намеренно НЕТ** — она там
  стояла и оказалась вредной: `computed_at` не версия строки (у события это
  время события, у пунктуатора — stream-time), и guard навсегда отбрасывал
  настоящее падение цены. Порядок обеспечивает Kafka (ключ = `product_id`),
  последний выигрывает.

### 4.6. Что подтвердилось на проде и что мешает переключению

Сверка 13.08.2026 на **4933 живых товарах** **[замер, PRICE-INSIGHT-REVIEW.md §5.1]**:

- срез А (одинаковое окно наблюдения): **99.3% вердиктов совпали**;
- остаточные 32 разобраны до механизма — **подтверждённых дефектов логики ноль**,
  во всех случаях Java **точнее** Go (Go засчитывает время OOS по последней
  известной цене и тянет медиану вниз);
- срез Б (реальное окно): **переключение сегодня соврало бы ~1200 товарам**,
  объявив «рекордно низкую цену» там, где Go по своей истории знает обратное.

Причина — **не код, а данные**: у Java физически меньше истории
(retention `price-events`), а `minAll` у Go включает бэкфилл маркетплейс-истории
(`PrependOlder`), точек которого в топике не было никогда.

Отдельная поучительная деталь: первый прогон сверки дал 1906 расхождений, из
которых ~98% оказались дефектом **измерителя**, а не сервиса — SQL-порт
`Stats` потерял «якорь» (сегмент на левой границе окна). Урок сформулирован в
доке: прежде чем объявлять расхождение дефектом, докажи, что измеритель прав.

### 4.7. Память: heap vs off-heap

| статья | значение | источник |
|---|---|---|
| лимит контейнера | 1 ГиБ | `docker-compose.yml:988` |
| heap | `MaxRAMPercentage=40` ≈ **410 МБ** | `price-insight/Dockerfile` |
| off-heap RocksDB (block cache + memtable, **общий на все партиции**) | **потолок 128 МБ**, из них 32 МБ на write buffer | `BoundedMemoryRocksDBConfig.java` |
| non-heap JVM (metaspace, code cache, стеки, буферы клиента) | ~90 МБ **[замер локально]** | REVIEW §4 |
| **конструктивный потолок** | ≈ 660 МБ из 1 ГБ **[счёт]** | — |
| факт локально (3 товара) | 228 МБ контейнер / 252 МБ RSS / heap 42 из 57 МБ / non-heap 90 МБ **[замер]** | REVIEW §4 |
| факт на проде после бэклога | **460 МБ**, после GC — **309 МБ, три замера подряд** **[замер 13.08]** | REVIEW §6.2 |

**Зачем вообще нужен `BoundedMemoryRocksDBConfig`** (это отличный вопрос для
Java-секции): Kafka Streams заводит отдельный экземпляр RocksDB **на каждую
партицию** входного топика, у каждого свой block cache 50 МБ и три memtable по
16 МБ. На десяти партициях это ≈1 ГБ **вне heap** — ровно весь лимит
контейнера. Heap живёт по `MaxRAMPercentage` и о внешней памяти не знает, так
что процесс молча упёрся бы в cgroup-лимит и был бы убит OOM-killer'ом. Решение
— один `static LRUCache` и один `WriteBufferManager` на процесс (Streams создаёт
по объекту config-setter'а на каждый store, общий потолок иначе не выразить),
memtable учитываются в том же кэше. `close()` намеренно ничего не закрывает.

## 7. Слабые места: где враждебный вопрос попадёт в пустоту

### 7.1. Семантика ошибки в последовательном консьюмере — **найдено и починено**

Это лучшая история для Go-секции: тут был не баг в редком углу, а **ложная
модель у автора в голове**, зафиксированная в комментарии.

**Как было.** `Consumer.Run`: при ошибке handler'а — лог и `continue` без
коммита, а комментарий обещал «сообщение будет перечитано».

**Почему обещание ложное.** `FetchMessage` уже сдвинул внутренний курсор
reader'а. Следующее сообщение обрабатывается и коммитится, а `kafka-go`
коммитит `offset+1` по партиции — то есть **перепрыгивает** провалившийся
оффсет. Перечитывание случалось бы только при падении процесса или ребалансе
до следующего успешного коммита. То есть секундный сбой БД = потерянный алерт,
и никакой ретрай его не спасал.

Косвенное подтверждение, что модель была именно ошибочной, а не сознательной:
в `RunConcurrent`, написанном позже, то же поведение описано **правильно** и
названо замыслом («оффсет всё равно продвигается… задача перепланируется
штатным кадансом»).

**Что сделано.** `runWithRetry`: до 3 попыток с паузой 500 мс, прерывается на
отменённом ctx (иначе shutdown растягивался бы на каждое падающее сообщение),
после исчерпания — **явный commit** с громким логом и метрикой
`kafka_messages_consumed_total{status="dropped"}`. Пропуск стал осознанным
решением, а не побочным эффектом. Гарантия по-прежнему at-least-once.
Ретраи намеренно **не** добавлены в `RunConcurrent` — там удержание слота пула
под ретрай отнимает пропускную и морозит вотермарк непрерывного префикса.
Покрыто четырьмя тестами в `internal/kafka/consumer_test.go`.

> **Вопрос интервьюера:** «У вас упала БД на секунду при обработке price-event.
> Что произойдёт с этим событием?»
> **Ответ:** три попытки на месте; если БД не вернулась — событие пропускается
> явно, с метрикой, а восстановление даёт следующий плановый скрейп товара.
> **Дальше почти наверняка спросят:** «А почему не бесконечный ретрай?» —
> потому что консьюмер последовательный, и вечный ретрай одного сообщения
> останавливает всю партицию; при этом каждое событие здесь не уникально —
> следующий скрейп породит эквивалентное.

- **Пул соединений Postgres нигде не настроен.** [счёт] 9 процессов × 8 = 72

  `statement_timeout` тоже нет — залипший запрос держит соединение до
  клиентского таймаута.
- **Один брокер Kafka, RF=1, Zookeeper.** Падение брокера = полная остановка
  конвейера. Уже случалось при выкатке price-insight — и часть событий цены
  потерялась (`price_history` записан, событие нет).
- **Один Postgres без реплики.** RPO = сутки (ежедневный дамп) + до 6 ч до S3.
- **Jaeger `SPAN_STORAGE_TYPE: memory` + `AlwaysSample`** при 2.2 событиях/с.
  [счёт] 50 000 трейсов при таком потоке — это минуты истории. Трассировка
  фактически годится только для «посмотреть прямо сейчас».
- **N+1 в поиск-воркере.** `evaluateSubscription` (`searchloop.go:275-303`)
  делает по два запроса (`GetBaseline` + `GetLastNotifiedPrice`) **на каждый
  товар выдачи на каждую подписку**. При выдаче 300 позиций и 3 подписчиках —
  1800 round-trip'ов на один скрейп. Не замерено, но это единственное место в
  проекте, где нагрузка на БД растёт мультипликативно.
- **`GetSchedulableProducts` без LIMIT** — полный join всех активных подписок
  каждые 20 с. На 30k подписок нагрузочного теста это работало, но потолок не
  измерялся.

### 7.10. Где работает по случайности, а не по замыслу

1. **Redis `volatile-lru` + пулы токенов без TTL.** Это записано как замысел —
   но если кто-то однажды поставит TTL на слоты пула, при переполнении они
   начнут вытесняться и WB-поиск встанет молча.
2. **`AllowAutoTopicCreation` + `KAFKA_AUTO_CREATE_TOPICS_ENABLE=true`.**
   Топики не объявлены нигде, кроме `price-verdict` (его создаёт Java явно,
   потому что compaction обязателен). Все остальные существуют потому, что
   брокер их создал с дефолтными 10 партициями. Смена брокерского дефолта
   изменит партиционирование бесшумно.
3. **`api` не создаёт консьюмеров, но получает `KAFKA_GROUP_ID=price-tracker`** —
   безвредно ровно до тех пор, пока в api не появится консьюмер.
4. **Идемпотентный ключ уведомления содержит `recorded_at` с точностью до
   секунды** (`cmd/notifier/main.go:647`). Два события по одной подписке с
   одинаковой ценой в одну и ту же секунду схлопнутся. Практически недостижимо,
   но это именно «работает, потому что не совпадает», а не «не может совпасть».
5. **`price_history` не имеет уникального индекса** по `(product_id, recorded_at)`.
   От дублей защищает только advisory-lock в `PrependOlder` и change-only в
   обычном пути. Ручной повторный запуск бэкфилла в обход лока задвоил бы точки.

## 8. Истории (то, что рассказывать вслух)

### 1. Цена WB бралась из архива и врала в 97% случаев при success rate 100%

**Задача.** Показать пользователю ту же цену, что он видит на сайте.
**Что было.** Скрейпер брал последнюю точку из `price-history.json` на
basket-CDN. Метрики были идеальные: файл честно скачивался, антибота там нет,
`scrape_requests_total{status="success"}` — 100%.
**Что выяснилось.** Последняя точка архива — **не текущая цена**, архив отстаёт
на дни. Врал в 97% скрейпов. Поймать это метриками невозможно в принципе —
только глазами, сверкой с сайтом.
**Варианты.** (а) браузерный сайдкар на карточку; (б) `u-card` через xray.
**Что выбрали и почему.** Браузерный путь провалился **дважды**: навигация на
карточку ~14 с при спросе 4.2/мин = 100% загрузки одной дорожки, а молотилка
попыток **забанила наш IP у wbaas и уронила заодно WB-поиск**. Выбрали `u-card`
через xray — он уже работал на трансграничных товарах (646 успехов в проде),
то есть расширяли работающий путь, а не проверяли гипотезу.
**Цена.** Цена теперь зависит от стороннего VLESS-провайдера. Поэтому в коде
есть рубильник `WB_UCARD_PRIMARY=false` (`wildberries.go:97`) — переключение в
`.env` без выкатки, цены снова отстанут, но бот переживёт падение xray.
**Что выяснилось потом.** Живых цен стало 90% вместо 3%. Сторожевая метрика —
`wb_price_source{source="basket"}`: рост её доли = цены снова врут.

### 2. Один товар — десять строк в базе

**Задача.** Понять, почему у товара «начинается история заново».
**Что было.** `products.url UNIQUE` — де-факто ключ товара. Одна карточка
приходит десятком написаний: со slug и без, с `?asb=`/utm, с www, из
мобильного шаринга. Каждое заводило **отдельный** `products` со своей историей,
подписками и `public_id`.
**Замер.** У Яндекс.Маркета — 14 524 строки на 13 460 товаров (~1 057 лишних,
у одного 12 копий). У Ozon — **ровно один дубль**. То есть настоящая проблема
всё это время сидела там, куда отчёт не смотрел.
**Решение.** `CanonicalProductURL` — канон по id. Но у Яндекс.Маркета его
нельзя было вывести из общих соображений: **он единственный реально фетчит
сохранённый URL** и достаёт из пути `sku`, которым потом вытаскивает цену.
Пришлось написать отдельный пробник `cmd/ym-canon-probe` и проверить живым
скрейпером: 8 из 8 карточек дали ту же цену и имя.
**Цена.** Две миграции-склейки (030, 031), каждая — одна транзакция с отчётом
до/после, и обе **не применимы goose'ом**.
**Грабля порядка.** На 030 миграцию выкатили раньше кода, и за окно между ними
выдача завела 96 новых кривых строк. В шапке 031 это записано прямо: «СНАЧАЛА
выкатить код, ПОТОМ миграцию».
**Ещё грабля.** Схема склейки должна быть «оставить ровно одного выжившего в
группе», а не «удалить коллизию с победителем»: у YM в группе до 12 копий, и в
одну подписку могли попасть **два дубля без победителя**.

### 3. Партиция Kafka замерзает при живом консьюмере — дважды

**Симптом.** Лаг растёт на **одной** партиции. Реплика жива, ошибок нет,
`inflight = 0`. Лечилось только рестартом — который обнулял трекер.
**Первый диагноз (14.07)** — «зависшая горутина обработчика». Лечение:
`SCRAPE_HANDLER_TIMEOUT` — жёсткий дедлайн 120 с на сообщение
(`cmd/scraper/main.go:268`). Помогло частично.
**Второй эпизод (31.07)** показал, что диагноз был неверен. Настоящая причина:
`offsetTracker` не переживал **ребаланс**. После ребаланса партиция приходит
заново, оффсета `cursor` из прошлой генерации больше не будет никогда, и
`complete` навсегда упирался в отсутствующий `done[cursor]`.
**Фикс.** `register` детектит разрыв последовательности (`offset != p.next`) и
пересинхронизирует курсор, осознанно бросая in-flight прошлой генерации
(`consumer.go:321-335`). At-least-once сохраняется: новый владелец перечитает.
**Плюс метрика.** `stuckSeconds` — сколько партиция копит завершённые оффсеты,
не в силах сдвинуть курсор, и алерт `KafkaPartitionStuck > 600s`. Ключевая
деталь: если ждущих оффсетов нет — метрика 0, чтобы простаивающая партиция не
светила фальшивое застревание.
**Мораль для рассказа:** первый правдоподобный диагноз продержался две недели и
был неверен; починил его не он, а метрика, которую завели вместе со вторым
фиксом.

### 4. Прод-порты торчали в интернет

**03.07.2026.** Деплой сделали без прод-оверлея → Redis, Postgres и Kafka
опубликовались на `0.0.0.0`. Redis заслейвили на чужой мастер, в Postgres
появился бэкдор-роль `pgg_superadmins`.
**Что сделали, кроме зачистки:**
- `ports: !reset []` в оверлее и `make check-ports` как гейт деплоя;
- в Redis переименованы в пустоту `REPLICAOF`/`SLAVEOF`/`MODULE`/`FLUSHALL`/
  `FLUSHDB`/`DEBUG` — **defense-in-depth поверх закрытых портов**, `CONFIG`
  оставлен, потому что его дёргает exporter;
- `requirepass` и разведение ролей Postgres (`tryberry_app` — только DML);
- Grafana сделана safe-by-default **в базовом файле**, а не только в оверлее;
- **security-алерты в Prometheus**: `redis_instance_info{role!="master"}`,
  `pg_security_superusers > 1`, `pg_security_login_roles != 3`;
- `make guard-clean-shell` — потому что экспортированные в шелл переменные
  перебивают `.env` при интерполяции compose, и на эту граблю наступили дважды.

**Побочный эффект, который пришлось решать архитектурно:** роль `tryberry_app`
стала строго DML, а `partition.Manager` должен создавать партиции. Дать ей
`CREATE ON SCHEMA` = дать и `DROP price_history`. Решение — `SECURITY DEFINER`-
функция, умеющая ровно одно (`migrations/028`), с фиксированным `search_path`
и `REVOKE ... FROM PUBLIC`.

### 5. Дедлок дорожки: пул стоит при `healthy = 4`

**29.07.2026, Ozon встал на 11 часов.** Метрика `healthy_lanes` показывала 4 —
всё в порядке. Реально: подвисший драйвер браузера держал `asyncio.Lock`
дорожки вечно. Запросы от Go копились на входе в лок (p95 = 30 с), а цикл
обслуживания **пропускал** залоченную дорожку, считая её занятой.
**Фикс.** Вся работа под локом обёрнута в `asyncio.wait_for(LANE_OP_TIMEOUT_S)`;
таймаут → дорожка помечается нездоровой, браузер на пересоздание, наружу 504
(«беда сайдкара», а не «FAB»). Плюс метрика **возраста последнего успеха**, а
не флага здоровья.
**Что выяснилось потом.** Та же дыра была во **всех трёх** сайдкарах. Закрыта
в `wb-search-miner` (там залипание нашли живьём) и в `ali-miner` 13.08, и у
каждого теперь есть `test_lane_deadlock.py`.
**Сопутствующее открытие.** `ali-miner` вообще не был в `scrape_configs`
Prometheus — то есть алерты на него, если бы их завели, были бы мёртвыми
правилами. Обнаружилось ровно в момент, когда их решили завести.

### 6. Единый анти-спам съедал минутный тариф

**Задача.** `below_target` на широкой выдаче (Ozon отдаёт ~8 ротирующихся
позиций) сыпал уведомления каждый скрейп.
**Первое решение.** Единая константа: не чаще раза в 6 ч
(`SEARCH_BELOW_TARGET_COOLDOWN_MINUTES`).
**Что выяснилось.** Она обнулила продукт перекупа: запрос скрейпился каждые
30 мин, подписка оценивалась, **11 из 12 уведомлений выбрасывались в кулдауне**.
Человек платит 1990 ₽ за скорость и не получает её.
**Что выбрали.** Зазор стал свойством тарифа: `Plan.SearchCooldown` — 6 ч у
free, 2 ч у lite, 1 ч у pro, **явно выключен** у reseller через
`CooldownOff = -1s` (нужно было отличать «выключено» от «не задано», потому что
ноль уже значил «фолбэк на env-ручку», `plan.go:57-59`).
**Цена.** Ещё одно поле в тарифе и трёхуровневый троттлинг, который надо
держать в голове целиком: каданс скрейпа → каданс оценки → кулдаун канала.

### 7. Кто врал в сверке — сервис или измеритель

**Задача.** Доказать, что Java-порт «честной цены» эквивалентен Go.
**Первый прогон.** 1906 расхождений вердикта из 4933. Выглядело как провал
портирования.
**Разбор.** Дефект оказался в **SQL-измерителе**: ограничив Go условием
`recorded_at >= observed_since`, автор выбросил «якорь» — сегмент, активный на
левой границе окна. При change-only хранении у стабильного товара внутри окна
строк может не быть вовсе, и Go выглядел так, будто истории нет совсем.
Появлялись пары, где **все четыре агрегата совпадали дословно, а вердикты
расходились**.
**После починки: 1906 → 32.**
**Дальше — ещё интереснее.** Из 32 остаточных две гипотезы: (а) рестарт Kafka
съел события, (б) разная семантика OOS. Гипотеза (а) отпала честно
(2 товара из 53). Гипотеза (б) **не проверялась вообще**, хотя автор считал,
что проверил: признаком взяли «большой разрыв между строками `price_history`»,
а он негоден **по построению** — при OOS scraper строку не пишет ВООБЩЕ, значит
разрывов между строками этот механизм не производит. Цифры вышли одинаковыми
(153.5 ч против 150.3 ч) и не значили ничего.
**Разобрали поштучно.** Товар `8199290`: нулевые события с 04.08 по 07.08, Go
якорем подставил цену 15 783 от 02.08 и дал ей **72 часа веса — ровно те
72 часа, когда товар нельзя было купить**.
**Вывод.** Права Java. «Минимум за всё время 15 783» про цену, по которой трое
суток нельзя было купить — ровно то враньё, против которого написан продукт.
**Мораль:** прежде чем объявлять расхождение дефектом сервиса, докажи, что
измеритель прав. Здесь измеритель был неправ в 98% случаев.

### 8. Java-сервис не заводился, и это было не видно

**D1.** `exactly_once_v2` требует служебный топик `__transaction_state`, а его
дефолты рассчитаны на кластер: RF=3, min.ISR=2. Брокер один → топик не
создаётся, и клиент **вечно висит на `InitProducerId`**, молча не обрабатывая
ничего. Никакой ошибки. Лечится
`KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1` + рестартом брокера.
**D2.** В проекции стоял guard «не затирать более свежий `computed_at`» —
казался очевидно правильным. Поймано на локальном прогоне: тик пунктуатора
отдал вердикт с `computed_at` «сегодня», следом приехало настоящее событие о
падении цены с `computed_at` «вчера», guard отбросил его **навсегда**, и в
таблице осталось `min_all=1000` вместо 700. Причина: `computed_at` — не версия
строки, у него **два разных источника времени**. Guard убран, порядок
обеспечивает Kafka.
**D7.** Readiness врал: без явного `include: kafkaStreams` в группе
`readiness` Spring отвечал UP по факту поднятого контекста — топология могла
быть DEAD.
**D9.** Тест был устроен так, что позеленел бы на второй прогон ложно.
**D3.** Стейт рос по числу **скрейпов**, а не смен цены (нет склейки сегментов) —
у reseller это ~130 000 сегментов на товар за 90 дней.
**Побочно:** миграция `032`, скормленная в psql целиком, выполняет и `Up`, и
`Down` — таблица создаётся и тут же удаляется, **без единой ошибки**.
**Цена рестарта Kafka на выкатке:** в логах scraper в этот момент
`send price event: kafka write ... server misbehaving` — строка в `price_history`
записалась, событие не доехало. Это видно в остаточных расхождениях сверки.

### 9. Фича, которую решили не делать после того, как её измерили

**product-match** — сопоставление одного товара между маркетплейсами.
Написали прототип на Lucene, собрали корпус смартфонов, сделали терминальный
разметчик, разметили золотой набор (110 спорных пар вместо 420 — размечали
только спор методов), построили контрольную группу на триграммах pg_trgm.
**Условие отказа сформулировали ДО замера.**
**Результат.** Lucene 0.55 против pg_trgm 0.53 — **не обогнал**. Условие
сработало, сервис не пишем. Причём узкое место оказалось не в поиске кандидатов
(recall@50 = 1.0), а **в решении** — а это не задача текстовой похожести.
**Что осталось полезного:** доменная нормализация (четыре разных написания
объёма памяти, включая «256+8 ГБ» задом наперёд у WB) и размеченный набор.
**Почему это хорошая история:** редко кто может показать фичу, которую **не**
сделали, с числом и заранее объявленным критерием.

### 10. `float64` пух базу тысячами одинаковых строк

WB отдаёт цену делением копеек на 100, а pgx конвертит `NUMERIC(12,2)` в
`float64` умножением на 10⁻². У дробных цен младшие биты расходятся, и строгое
`!=` считало цену «изменившейся» на **каждом** скрейпе. `price_history` WB пухла
тысячами идентичных точек. У Ozon и Я.Маркета цены целые — эффекта не было, и
это отлично маскировало баг.
Фикс — `pricesEqual` через `math.Round(x*100)` (`cmd/scraper/main.go:453`), и
**тот же критерий пришлось дословно повторить в Java** (`ProductState.samePrice`),
иначе стейт двух реализаций разъехался бы.

### 11. OOS-товар отдавал цену и фото чужого товара

Ozon при отсутствии товара показывает виджет `webOutOfStock` со **своим** sku,
фото и последней ценой, а рядом — блок рекомендаций. Жадные ярусы парсера
(«любой виджет с ₽») и рандомный фолбэк фото подставляли **чужой товар**.
Чинилось не только кодом: пришлось чистить историю (`ratio > 3`) и Redis-кэш
`price:<id>`. Отдельный SQL-скрипт `scripts/sql/ozon-oos-cleanup.sql`.
Из этого выросла целая подсистема: колонка `products.in_stock`, триггер
`back_in_stock`, и правило «при OOS в `price-events` кладём `new_price = 0`, а
не последнюю известную цену» — иначе ненулевая цена ложно пометила бы товар
«в наличии» и сломала бы триггер.

### 12. Нагрузочный тест, который доказал, что оптимизировать нечего

5 000 синтетических юзеров, 30k подписок, 26k товаров — живут в общей таблице
под флагом `is_synthetic`, чтобы конвейер видел их как настоящих, а notifier
редиректил доставку на тест-чаты (и то с сэмплированием 1 из 10, иначе 1000
синтетиков залили бы 3 чата при лимите Telegram ~1 msg/s на чат).
**Результат:** RAM 9 из 15.6 ГБ, CPU у scraper-реплик 4–9%. Единственное узкое
место — сам scraper, и он **latency-bound**: одна реплика держала лаг ~9500 при
CPU 15%, потому что ждала маркетплейс.
**Вывод, который важнее числа:** «занять» сервер этой нагрузкой нельзя, потолок
**внешний** — латентность МП, антибот-лимиты, одна дорожка сайдкара. Отсюда
3 реплики scraper как оптимум и отказ от Phase 2 масштабирования нотифаера.

### 13. Тесты были зелёные, пока их не запустили как надо

**Задача.** Проверить перед аудитом, что репозиторий в рабочем состоянии.
**Что было.** `go test ./...` — всё ок. Успокоился.
**Что выяснилось.** `make test` гоняет с `-race`, и с ним два теста
`internal/scraper` **падали**. Гонка — не в проде, а в **тестовом дубле**:
`tryBasket` тянет `price-history.json` и `card.json` двумя горутинами
параллельно, а фейковый RoundTripper писал счётчики в общую `map[string]int`
без синхронизации.
**Цена.** Мьютексы в двух дублях, 15 строк. Но настоящая цена была раньше:
красный `make test` жил в репозитории неизвестно сколько и обесценивал команду
как сигнал — если она красная по «неважной» причине, её перестают запускать.
**Что из этого следует.** `-race` поставлен обязательным шагом в CI. Именно он,
а не чтение кода, нашёл проблему — и он же единственный, кто поймал бы
настоящую гонку в конкурентном консьюмере, если бы она там появилась.

## 10. Что осталось непонятным мне после чтения

Это ровно те места, где автор поплывёт первым — потому что ответа в репозитории
нет.

1. **Почему scraper и notifier делят consumer group `price-tracker`?**
   Похоже на копипасту env, но подтверждения нет. Если это осознанно — нигде не
   написано зачем.
2. **Откуда «девять дней истории» при retention 72 ч** (§6, п.12). Моя версия
   про роллинг сегментов правдоподобна, но в репозитории её нет, и параметры
   `log.segment.bytes`/`log.roll.hours` нигде не заданы явно.
3. **Какой признак свежести вердикта планируется вместо `computed_at`.**
   В REVIEW §7 записано, что нужен «другой признак живости (например, heartbeat
   или сравнение с временем последнего события)», но выбора нет. Без него
   переключение notifier невозможно, а значит весь Java-сервис остаётся в
   подвешенном состоянии.
4. **Как именно должен выглядеть бутстрап стейта price-insight из
   `price_history`.** Есть только эскиз в одну строку («одноразовый producer»),
   и в нём же зашита проблема: гард `lastEventAt` отбросит синтетические
   события, если живой поток по товару уже прошёл. То есть эскиз не работает
   без остановки скрейпера или без изменения гарда.
5. **Почему выбран intervals-подход к оценке подписки, а не «событие с
   дедупликацией по цене».** Текущая модель требует публиковать `PriceEvent` на
   каждом скрейпе (193 тыс./сут) только ради того, чтобы у каждого тарифа была
   своя точка оценки. Альтернатива — событие только на изменение + периодический
   sweep по подпискам — нигде не рассматривалась.
6. **Что считается корректным поведением при отказе `search-events`.**
   В коде записано «на следующем скрейпе те же хиты сработают снова» — но это
   верно только пока `search_notifications` не записаны. Полностью эта
   инвариантность нигде не доказана и не покрыта тестом.
7. **Каков реальный потолок `evaluateSubscription`** (N+1, §7.8). Не замерялся
   вообще; в нагрузочном тесте акцент был на товарном пути.
8. **Планируется ли когда-нибудь второй брокер / реплика Postgres,** и если нет —
   какой RTO/RPO считается приемлемым. В доках про бэкапы есть, про целевые
   показатели восстановления — нет.
9. **Что делать, когда истечёт xray-подписка** (единственная точка отказа для
   Telegram-egress). Есть напоминание в трекере и скрипт перегенерации конфига,
   но нет ни мониторинга срока, ни второго провайдера.
10. **Зачем `ozon-miner` держит ~5 ГиБ.** Замерено, что память растёт от
    аптайма и выходит на плато, и что recycle не нужен. **Причина роста не
    установлена** — только наблюдение за поведением.
