ИНТЕГРАЦИИ С МНОЖЕСТВОМ ИСТОЧНИКОВ (главная тема, прямая параллель с устройствами)
Каждая площадка реализует интерфейс MarketplaceScraper: Marketplace(), Matches(url),
Scrape(ctx, url). Новый источник = новая реализация плюс регистрация в Registry,
остальной код не меняется. Общие доменные ошибки: ErrProductNotFound,
ErrMarketplaceBlocked, ErrAgeRestricted, поэтому верхний уровень не знает
специфики площадки.
Вокруг адаптеров: лимитер частоты на источник (x/time/rate), ретраи с
экспоненциальным бэкоффом, брейкер – 10 блокировок подряд гасят площадку до пробы
раз в 5–60 минут, чтобы не добивать источник, который нас уже режет.
Условный GET у WB: If-None-Match с ETag, при 304 цена не перекачивается.
Источники ломаются без предупреждения: Яндекс.Маркет убил старую форму ссылок,
пришлось переезжать на новую и чистить 1207 дублей в базе; WB отдавал цену из
архивного файла; Ozon режет по TLS-отпечатку, поэтому клиент на tls-client с
подменой отпечатка, а часть площадок ходит через браузерные сайдкары по HTTP.
Каналы: одна доменная логика за тремя транспортами. Telegram long-poll, MAX
вебхук → Kafka. Расхождение текста одного и того же отказа между каналами
считаю багом.

GO: ЧТО ГОВОРЮ КОНКРЕТИКОЙ
Конкурентный консьюмер Kafka: семафор на канале make(chan struct{}, N),
sync.WaitGroup, горутина-коммиттер по тикеру. Сообщения обрабатываются
параллельно, поэтому коммит нельзя делать по последнему обработанному: коммичу
вотермарк непрерывного префикса по каждой партиции. Ретраев внутри пула нет
намеренно: слот, занятый ретраем, стопорит вотермарк и режет пропускную;
задача всё равно приедет на следующем тике планировщика.
Контекст: таймаут на обработчик, SIGTERM отменяет корневой контекст, оффсеты
сбрасываются фоновым. Трейс-контекст переносится через заголовки Kafka.
Интерфейсы маленькие и на стороне потребителя, в тестах подменяются
(Provider, TokenProvider, репозитории). Тесты с -race, линтер и тесты на pre-push.
300 тестовых функций, SQL покрыт слабо.

ИНЦИДЕНТЫ
1) Замёрзшая партиция Kafka: лаг на одной партиции при живой реплике и нулевом
inflight. Первый диагноз неверный, думал зависла горутина. На деле трекер
оффсетов разошёлся после ребаланса. Фикс, метрика возраста застоя и алерт
KafkaPartitionStuck.
2) Архивная цена WB: success rate 100%, а цена врала в 97% случаев. Поймала
метрика происхождения данных. После переезда на живую ручку актуальных цен 90%
вместо 3%. Вывод: сервис без ошибок не значит верные данные.
3) Дедлок дорожки сайдкара: подвисший драйвер держал лок, пул стоял при
healthy>0, Ozon 11 часов. Теперь меряю возраст последнего успеха, а не только
число живых воркеров.
4) Утечка памяти в браузерном сайдкаре: рендерер раздувался до 3 ГБ за 20 секунд.
Две первые гипотезы неверные, нашёл, когда стал снимать память раз в 5 секунд.
5) Худший и мой промах: порты Redis и Postgres торчали в интернет из-за деплоя
без прод-оверрайда. Нашёл, вычистил, закрыл файрволом, сменил пароли.

МАСШТАБ И РОСТ
Нагрузочный тест: 5000 синтетических пользователей, 30 тыс. подписок, лаг 0, CPU
реплик 4–9%. Узкое место оказалось не в коде, а во внешних лимитах источников.
Пул консьюмера недогружен, inflight 2 из 8. Kafka 10 партиций, ключ product_id,
scraper в 3 репликах одной consumer group. Доставка уведомлений: durable outbox,
флашер с бэкоффом и бандлингом, лимитер 25 msg/s. План масштабирования доставки
написан, но не делал: вынести синглтоны из notifier и запустить N реплик в
consumer group, триггер – рост глубины outbox.

ВОПРОСЫ ПРО ИХ СТЕК (отвечать честно)
В: gRPC использовал? О: В своих сервисах нет, между ними Kafka и HTTP с JSON к
сайдкарам. gRPC у меня только как транспорт OTLP-экспортера трейсов. Понимаю
модель: контракт в proto, кодогенерация, дедлайн через context, статус-коды,
стриминг. Для внутренних вызовов между своими сервисами выбрал бы его ради
контракта и типизации, JSON мне пришлось держать руками.
В: resty? О: Нет, net/http и tls-client, ретраи и бэкофф написал сам. Resty это
обёртка над net/http с ретраями, middleware и удобной сборкой запросов, то есть
ровно то, что я делал руками.
В: YDB? О: Не работал. Знаю, что это распределённая SQL-база Яндекса с YQL,
шардированием таблиц по первичному ключу и serializable-транзакциями. Отсюда
главное отличие от Postgres: первичный ключ выбирают под распределение нагрузки,
монотонный ключ создаёт горячий шард. Мой опыт реляционный: Postgres,
партиционирование по месяцам, условный UPDATE как compare-and-set, FOR UPDATE,
уникальные индексы как идемпотентность.
В: Docker? О: Весь прод на Docker Compose, 12 сервисов плюс Kafka, Postgres,
Redis, мониторинг. Грабли знаю на своей шкуре: сборка вся из кэша при старой
ветке молча деплоит старый код; mem_limit не применяется без force-recreate;
OOM в cgroup контейнера не равен OOM хоста.

ГАРАНТИИ. At-least-once во всех Go-сервисах, идемпотентность на уникальных
индексах, ключ уведомления sub:price:recordedAt. Exactly-once только в Java-
сервисе на Kafka Streams, запись оттуда в Postgres идемпотентным апсертом, потому
что транзакция Kafka на базу не распространяется. Для устройств тот же принцип:
команда может прийти дважды, приёмник должен это переварить.

АЛГОРИТМЫ. Базовый уровень. Из практики: вотермарк непрерывного префикса, пул с
семафором, взвешенная медиана оконными функциями, дедуп по ключу.

СЛАБЫЕ МЕСТА (называю сам). gRPC, YDB и resty в проде не использовал. Единые точки
отказа: один брокер Kafka и один Postgres без реплики, RPO сутки. В api оффсет
Telegram двигается до публикации в Kafka, апдейты теряются при её сбое, задача
заведена. SQL покрыт тестами слабо. Горизонтально масштабировал только scraper,
доставка пока синглтон. Опыта командной разработки бэкенда нет, кроме
Android-стажировки с ревью.

ВОПРОСЫ КОМАНДЕ. Как устроена интеграция нового производителя: свой адаптер на
каждого или общий протокол. Как доставляется состояние устройств: push или
опрос. Что в YDB, а что в Postgres. Чем стажёр занят в первые месяцы и кто
ментор.
