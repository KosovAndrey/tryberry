## Журнал (2026-06-25, вечер) — WB-бэкфилл истории цен

- **WB отдаёт свою историю цен**, и наш скрейпер уже качал её, выбрасывая всё кроме
  последней точки. Probe реального `basket-XX.wbbasket.ru/.../price-history.json`:
  массив `{dt:unixSec, price:{RUB:копейки}}`, каданс ~недельный, охват в сэмпле 77д
  (12 точек), payload ~40 байт/точка (≈0.5КБ). Стоимость = **ноль** доп.запросов
  (файл и так скачиваем), выгода — график и «честная цена» сразу, ретроспективно.
- **Бэкфилл на первом скрейпе товара:** `parseWBHistory` (чистая, тест на реальном
  фикстуре `testdata/wb_price_history.json`) кладёт серию в `Result.History`
  (`scraper.PriceHistoryPoint`), cap `wbHistoryMaxAge=180д` (чтобы не плодить
  прошлые партиции). В `cmd/scraper` при `prevPrice<=0 && len(History)>0`:
  `partition.Manager.EnsureForTimes` (дедуп месяцев) → `PriceHistoryRepo.BackfillIfEmpty`
  (tx + `pg_advisory_xact_lock(product_id)` + повторная проверка пустоты → batch-insert).
  Best-effort: ошибка бэкфилла не валит обычную запись цены.
- **Идемпотентность/гонка:** гард «история уже есть» под advisory-lock; на втором
  скрейпе (prevPrice>0) бэкфилл даже не пробуется.
- Только WB. Ozon/Ali — нет нативной истории + антибот. Я.Маркет (виджет «как
  менялась цена») — отдельный probe, отложено.

## Журнал (2026-06-23, ещё позже) — промокод в платёжном флоу

- **Промокод на этапе оплаты (ветка `feat/checkout-promo`):** раньше скидочный код
  вводился только командой `/promo КОД` «в меню». Теперь на карточке тарифа есть
  кнопка **«🎟 У меня есть промокод»** → ввод кода прямо в оплате (FSM
  `checkout_promo` в Redis, по образцу email/порога). Discount-код запоминается как
  ожидающая скидка и карточка перерисовывается уже со скидкой в цене/кнопках
  (`pendingDiscountPct` + `discountedRub`); grant-код активируется сразу (как
  `/promo`). `sendPlanCard`/`sendSubConsent` получили `ctx`/`tgID` для preview.
  Тест `discountedRub`. *(Первая итерация — доработана ниже по репорту юзера.)*
- **Доработка промо-флоу (тот же бранч, по репорту юзера):** ввод кода «в меню» не
  реагировал (кнопка `menu:promo` была статичным текстом без FSM), скидка из меню
  не вела к оплате, нельзя было сменить уже применённый код, + нашёлся leak
  повторного применения discount (гейт `Redeemable` не проверял «юзер уже гасил» —
  а discount гасится только после оплаты). Сделано: единый ввод через один FSM

  переход к оплате (список тарифов или карточка); кнопка на карточке не прячется,
  становится «Сменить промокод»; `PromoRepo.Redeemable(code,user)` теперь с
  per-user UNIQUE-гейтом (закрыт leak на money-path для TG и VK). Лайфсайкл, грабли
  и проверка — `docs/CHECKOUT-PROMO.md`.

## TL;DR

Бот (Telegram @TryBerryBot, отслеживание цен/выдачи Wildberries) — рабочий, в проде,
микросервисы в Docker на RU-VM. За последние сессии закрыты три крупные темы из старого
бэклога: **свой egress-прокси (WireGuard+tinyproxy)**, **быстрая дорожка перекупов** и
**полная механика платных тарифов**.

**Главная развилка сейчас:** вся машинерия роста готова (тарифы + промокоды +
рефералка + меню), **оплаты ещё нет**. Заявка в ЮKassa подана 2026-06-11 (сайт
обновлён под модерацию: тарифы с ценами, оферта, политика, блок оплаты/возврата),
ответ ~через день. Как только одобрят — подключаем платёжный флоу к готовым крючкам
(discount-промокоды, реферальное событие `paid`, `SetPlan`).

## Что сделано с момента старого хэндофа (всё в `main`)

- **Egress-прокси свой.** Заменили арендованный lteboost на локальные `wg-proxy`
  (WireGuard, туннель wg0) + `tinyproxy` (HTTP CONNECT :8888). api/bot-worker/notifier
  ходят в Telegram через `HTTPS_PROXY=http://wg-proxy:8888`. Подводные камни деплоя —
  в memory `wg-egress-deploy-gotchas`.
- **Латентность приёма команд.** Polling (`WEBHOOK_ENABLED=false`) с узким таймаутом
  long-poll и свежим CONNECT-туннелем на каждый getUpdates (`DisableKeepAlives`).
  Команды доходят за ~2с. Остаточная нестабильность — на плече exit→Telegram (см. ниже).
- **Перекупы (была исходная бизнес-цель «ещё не начато»).** Быстрая дорожка: отдельный
  сервис `cmd/search-worker`, приоритетная очередь (~1-мин скрейп), свой пул токенов,
  реплики. Изоляция SLA от обычного поиска (20 мин).
- **Платные тарифы — полностью построены:**
  - Каталог планов: `free, trial, lite, pro, reseller_start, reseller_pro, unlimited`.
  - Строгий per-plan интервал проверки (миграция 010) — у дорогих планов чаще.
  - Грейс-период после истечения для поиск- и товарных подписок (reconciler).
  - Напоминания об истечении, мгновенное восстановление трекинга при покупке.
  - Тесты reconciler (`internal/domain/plan_test.go`).
  - Миграции 004–010 (`plans`, `plan_grace*`, `plan_reminded`, `search_tiers`,
    `per_plan_intervals`).
  - Выдача плана: **только** `/grant <telegram_id> <план> [дней]` (admin.go) — оплаты нет.

- **Фикс ложных уведомлений поиск-подписок (2026-06-11, задеплоено, f386f8c).**
  Новый товар в выдаче показывал зачёркнутую цену WB (`price.basic`) как «было X ₽» —
  выглядело как ложное «подешевело» (особенно `below_target`, срабатывающий сразу).
  Теперь в `SearchHitEvent` идёт `prev_price_kopecks` — опорная цена, от которой движок
  реально считал снижение (`last_notified` или baseline `first_seen_price`); для впервые
  увиденного товара она равна текущей и «было» не печатается. Сортировка топа в notifier —
  тоже по реальному снижению. Зачёркнутая цена в уведомлениях больше не участвует нигде.
  Хелпер `searchsub.RefKopecks` + тест. Пересобраны `search-worker`, `reseller-worker`,
  `notifier`.

- **Промокоды (2026-06-11, задеплоено, миграция 011).** Два типа: `grant`
  (N дней тарифа бесплатно — работает) и `discount` (скидка % — валидируется,
  применится при оплате ЮKassa). Погашение атомарное: лимит + UNIQUE(код,юзер) +
  выдача плана в одной транзакции. `/promo CODE`, deep-link `start=promo_XXX`,
  админка `/promo_create`, `/promo_off`, `/promo_list`. Правило наложения: free/триал
  → выдаём; тот же план → продлеваем; другой платный → отказ.

- **Реферальная система (2026-06-11, задеплоено, миграция 012).** Гибридная модель:
  приглашённому триал 7 дней вместо 3; рефереру +5 дней за «активного» друга
  (48ч + активная подписка, начисляет reconciler в notifier идемпотентно,
  потолок 90 дней/год; на free награда выдаёт Lite). Событие `paid` (+30 дней)
  в схеме — замкнётся на ЮKassa. Атрибуция `start=ref_<tgid>`: только свежим
  аккаунтам (окно 10 мин), один раз, не себе. `/ref` — ссылка + шеринг + статистика.
  Цифры — константы в `internal/domain/referral.go`.

- **UX меню (2026-06-11, задеплоено).** Навигация по меню живёт в одном сообщении
  (`showView`: колбэки правят сообщение, новые — только на команды). Главное меню
  2×5 с кнопками рефералки и промокода; «Мой тариф» с контекстными кнопками;
  приветствие приглашённого одним сообщением.

- **VK-интеграция, фазы 0–2 (2026-06-12, задеплоено, миграция 013).** Дизайн —
  `docs/VK-INTEGRATION-PLAN.md`. Юзер = `telegram_id?` + `vk_id?` (CHECK хотя бы
  один); привязка одноразовым кодом через Redis (`привязать КОД` в VK), пустой
  VK-аккаунт поглощается, непустой → ручной merge. Канал доставки
  `users.notify_channel` (auto/tg/vk/both, фолбэк на доступный) — роутинг в
  notifier (`cmd/notifier/delivery.go`), plain-text рендеры для VK. Сам VK-бот
  (`internal/vk`, консьюмер `vk-updates` в bot-worker, ingest в `cmd/api`
  `/vk/callback`): постоянная клавиатура + payload-роутинг, трекинг товаров по
  ссылке, поиск-подписки (FSM `vk_search_fsm` в Redis), списки с inline-отпиской,
  тарифы (заглушка оплаты), триал, профиль. Общие тексты/парсинг TG+VK — в
  `internal/domain/render.go`. Грабли VK: «Возможности ботов» в настройках
  сообщества обязательны для клавиатур (ошибка 912), событие «Входящее сообщение»
  включается отдельно, API 5.199, vk.com без прокси (NO_PROXY).

- **Витрина тарифов в TG (2026-06-12, задеплоено).** `/plans` + кнопка в меню:
  карточки с ценой/лимитами из `domain.Plans`, кнопка «Оплатить» — заглушка до
  ЮKassa (подписки не выдаются). Скрины ушли на модерацию ЮKassa. После запуска
  оплаты заменить обработчики `plan:buy:*` (TG) и `{"cmd":"buy"}` (VK) на
  создание платежа.

- **VK = полный паритет с TG (2026-06-12, задеплоено).** В VK добавлены:
  переключатель канала уведомлений в профиле, выдача кода привязки (vk2tg,
  TG принимает «привязать КОД», `LinkTG` зеркалит `LinkVK`), отвязка Telegram
  с подтверждением, счётчики лимитов, смена триггера товара (кнопки + FSM
  `vk_track_fsm`), промокоды («промокод КОД»), рефералка (код приглашения =
  `users.id`, «друг КОД» в окне атрибуции, `SetReferrerByID`). Симметрия
  строгая: из VK меняется только TG-привязка, из TG — только VK.
  Сервисные уведомления (пауза подписок, истечение тарифа, реферальная
  награда) идут через deliverer по `notify_channel` — доходят до VK-only
  юзеров; reconciler и `ListExpiringUnreminded`/`MarkReminded` на `users.id`.
  ФИКС латентного бага: NULL `telegram_id` VK-only юзера ронял сканы выборок
  алертов (COALESCE во всех JOIN users); алерты несут `UserID`
  (`SearchHitEvent.user_id`, ключ партиции = user id).

- **Слияние аккаунтов + анти-фарм триала/промокодов (2026-06-12, задеплоено,
  миграции 014–015).** Триал и погашение промокода привязаны к ИДЕНТИЧНОСТИ
  (вечные `trial_claims` / `promo_claims` по telegram_id/vk_id) — закрыт фарм
  «отвязал платформу → строка users пересоздалась → флаги чистые». При привязке
  кодом, когда оба аккаунта непустые, вместо отказа — слияние:
  `domain.ComputeMerge` (free/trial/paid; два разных платных → выбор из 2
  вариантов, остаток второго конвертируется по соотношению цен, ceil; затем
  подтверждение), `UserRepo.MergeAccounts` одной транзакцией переносит
  подписки/поиски/промо/рефералку (дубли по UNIQUE убираются), trial_used = OR.
  Аудит каждого слияния — таблица `account_merges` (планы до/после, итог,
  JSON с идентичностями и выбором) + slog «accounts merged». Отвязка тариф НЕ
  дублирует: план живёт на строке аккаунта, отвязанная сторона уходит на free.

Сервисы сейчас: `api` (ingestor), `bot-worker`, `notifier`, `scheduler`, `scraper`,
`search-worker`.

### B. Стабильность Telegram-плеча → VLESS (РАЗВЁРНУТО 2026-06-11)
- Симптом был: бот иногда отвечал 25с — флап на удерживаемых long-poll через WireGuard

- Решение в проде: основной egress на **VLESS+Reality** (TCP под HTTPS), 6 узлов
  подписки un1.pro (`vless-ger1..6`) + WG как авто-fallback. Контейнер `xray`
  (inbound :8888, observatory+balancer leastPing). Подтверждено логами
  `[in -> vless-ger1]`, exit-IP немецкий.
- Осталось: понаблюдать, что флап на 25с ушёл. Опц.: строгий приоритет/расширение
  пула узлов через тот же balancer.
