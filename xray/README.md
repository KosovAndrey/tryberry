# Xray (VLESS) — единственный egress в Telegram

На RU-хостинге РКН душит Telegram. Раньше весь egress шёл через WireGuard
(`wg-proxy` + `tinyproxy`), но WG — это UDP, и DPI его прицельно троттлит →
зависания long-poll на десятки секунд. VLESS идёт по TCP под видом обычного
HTTPS (особенно **VLESS+Reality** — маскируется под TLS к чужому сайту), и
почти не троттлится. WG-резерв выпилен 2026-07-11: handshake перестал
проходить совсем (при живом хосте — DPI), а unhealthy `wg-proxy` обрывал
каждый полный `up -d`. История: git log по `wireguard/`.

## Как это устроено

Один контейнер `xray` поднимает **два** локальных HTTP-прокси. Плечи выхода —
общие: outbound'ы `vless-*` (по умолчанию 16 узлов подписки, разложенных по
странам).

| Порт   | Кто ходит | Балансировка | Зачем именно так |
|--------|-----------|--------------|------------------|
| `:8888` | `api`/`bot-worker`/`notifier` (`HTTPS_PROXY`) | `leastPing` — одно лучшее живое плечо | long-poll к Telegram любит стабильный путь; скачки плеча его рвут |
| `:8889` | `search-worker`/`reseller-worker` (`SEARCH_PROXY_URLS`) | `random` — случайное плечо на соединение | поисковая ручка WB лимитирует по IP: с одного узла поиск упирается в 429, по числу узлов лимит делится. В бою с 01-09 (замер: 50% → 16% отказов) |

### Мёртвые плечи чистить, а не терпеть (01-09-2026)

`random` полезен ровно настолько, насколько чист пул: он честно попадает и в
мёртвые узлы, а каждое такое попадание стоит до 12с (таймаут клиента в
`NewProxyPool`) и жжёт одну из трёх попыток `fetchPage`. В ночь на 01-09 из 16
плеч были мертвы 6 — треть поисковых соединений уходила в никуда. Проверка и
чистка:

```bash
python3 scripts/wb-lane-test.py --lanes xray/config.json   # живость + вердикт WB по каждому адресу
python3 scripts/wb-lane-test.py --sub 'https://ПОДПИСКА/КОД'
```

Скрипт схлопывает узлы по резолвнутому IP (один адрес на разных портах — для WB
ОДИН адрес: в подписке таких дублей 19 на два адреса) и поднимает временный xray
на каждое плечо отдельно, потому что через общий inbound не видно, какое плечо
ответило. Из 88 узлов подписки живыми оказались 53 в 17 подсетях.

`observatory` каждые 30с пробит все плечи до `api.telegram.org`, `balancer`
(`leastPing`) держит трафик на **живом и самом быстром** узле. Узел отвалился —
автоматически уходим на следующий, без рестартов. Селектор балансировщика
матчит теги по префиксу, поэтому `["vless"]` охватывает все плечи сразу.

Поисковый балансировщик пробера не спрашивает: «умные» стратегии по определению
сходятся на лучшем узле, то есть ровно на том, чего мы здесь избегаем. Мёртвое
плечо ловит ретрай скрейпера (`fetchPage` перебирает попытки, каждая берёт новое
случайное плечо), а не observatory.

Порядок правил маршрутизации значим: `inboundTag: ["in-search"]` стоит **до**
общего правила, иначе поисковый трафик уедет на липкий `egress`.

## Конфиг собирается из подписки скриптом

Xray-core **не умеет подписочные ссылки** — их разворачивают клиенты
(v2rayN/Nekobox), ядро ест только статический `config.json`. Пока узлов было
шесть, их вписывали руками; на подписке в ~80 узлов это неподъёмно, поэтому
конфиг генерится:

```bash
python3 scripts/xray-config-from-sub.py 'https://ПОДПИСКА/КОД' -o xray/config.json
```

Скрипт разворачивает `vless://`-ссылки в outbound'ы, вешает на них общий
balancer и observatory — то же, что было руками, только воспроизводимо. Полезные
ключи:

| Ключ                 | Зачем                                                    |
|----------------------|----------------------------------------------------------|
| `--list`             | показать узлы подписки и выйти, ничего не записывая        |
| `-n 24`              | сколько плеч оставить (по умолчанию 16, `0` = все)         |
| `--include 'Финлян'` | оставить только узлы, чьё имя/хост совпали с regex         |
| `--exclude 'Турц'`   | выкинуть узлы по regex (матчит имя и хост, не транспорт)   |
| `--network tcp`      | только этот транспорт — под long-poll лучший `tcp`+vision  |
| `--prefer lt,ee,de`  | приоритет стран (см. ниже) — меняет стратегию балансировки  |

Все узлы брать не надо: observatory пробит **каждое** плечо раз в 30с, и сотня
лишних коннектов в минуту ради узлов в Канаде egress'у не помогает. Скрипт
набирает плечи round-robin по странам ближнего круга (FI, EE, LV, LT, SE, NL,
DE, PL), так что падение одной локации не выкашивает все плечи разом; дальние
страны идут только на добор.

Поддержаны reality поверх `tcp`, `grpc` и `xhttp`. `flow=xtls-rprx-vision`
проставляется только на `tcp` — на grpc/xhttp ядро с ним не стартует.

### Приоритет стран (`--prefer`)

По умолчанию стратегия — `leastPing`: трафик идёт на **самое быстрое живое**
плечо, и это обычно то, что нужно. `--prefer lt,ee,de` переключает на
`leastLoad` с весами: cost умножает измеренный RTT (1, 3, 9 по порядку;
остальные страны — 100), поэтому приоритет получается **мягкий** — плечо второй
страны перебьёт первую, только если реально втрое быстрее.

Жёсткого «всегда сначала Литва» в Xray нет и не будет: `fallbackTag` принимает
outbound, а не другой балансировщик, так что цепочку `lt → ee → de` им не
собрать, а `settings` есть только у `leastLoad`. Мягкий приоритет тут и лучше:
жёсткий удерживал бы трафик на живом, но перегруженном узле — ровно то, от чего
обычно и бегут.

Нужен просто «самый быстрый узел» — не ставь `--prefer` вовсе: `leastPing` меряет
пинг до Telegram через каждое плечо и держит трафик на лучшем. Это ровно то, что
обычно и требуется; `--prefer` нужен, только когда страна важнее скорости.

Два подвоха, о которых стоит помнить:

- `leastLoad` считает по `burstObservatory`, а не по `observatory` — скрипт
  ставит нужный пробер сам, но если правишь конфиг руками, не перепутай;
- в текущей подписке **вся Литва — gRPC** (а `lt6` — xhttp). gRPC в ядре помечен
  deprecated и по накладным расходам проигрывает TCP+Vision, так что «Литву
  первой» стоит сверять с замерами, а не считать очевидным выигрышем.

Даже с `--prefer` пара плеч резервируется за непредпочтёнными странами: 30-07
провайдер умер целиком, и пул из одних «любимых» стран умер бы вместе с ним.

> `xray/config.json` — **секрет** (внутри UUID и pbk), в `.gitignore`. В git
> лежит только `config.json.example` с плейсхолдерами. Сама ссылка подписки в
> репозиторий тоже не попадает.

**Перед рестартом конфиг надо проверить** — битый JSON или неизвестное ядру поле
означают, что xray не поднимется, а вместе с ним встанет весь egress:

```bash
docker exec pt_xray xray -test -c /etc/xray/config.json
```

Поднять и перецепить потребителей прокси:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d xray
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d api bot-worker notifier
```

Сменились узлы у провайдера — перегенерить тем же скриптом и `up -d xray`.

## Проверка

```bash
# Через какое плечо реально идёт трафик: ищем [in -> vless-XXX]:
docker compose logs --tail=30 xray

# Какой IP видит мир через xray (в образе busybox wget — прокси через env + -Y on):
docker compose exec xray sh -c "http_proxy=http://127.0.0.1:8888 wget -Y on -qO- http://api.ipify.org; echo"

# Доходит ли до Telegram (главное, ради чего всё):
docker compose exec xray sh -c "http_proxy=http://127.0.0.1:8888 wget -Y on -qO- -T 15 https://api.telegram.org/; echo RC=\$?"
```

> ⚠️ Последняя команда **в норме печатает `400 Bad Request` и `RC=1`** — это успех, а
> не поломка. busybox wget для `https://`-URL не делает CONNECT, а шлёт прокси GET
> в absolute-form; xray отправляет открытый HTTP на 443-й порт, и nginx Telegram
> отвечает 400. Важно, ЧЕЙ это ответ: `400` пришёл сквозь туннель (плечо живо), а
> `503` отдаёт сам xray, когда не смог никуда дозвониться (все плечи мертвы).
> Проверка `http://api.ipify.org` однозначнее — там нет TLS и ответ виден глазами.

Ещё одна строка, которую видно на старте и пугаться которой не надо:
`The feature gRPC transport ... is deprecated` — ядро ворчит на grpc-плечи
подписки. Они работают; если ворчание мешает, соберите конфиг с `--network tcp`.

Если все `vless-*` помечаются мёртвыми (Telegram перестал отвечать):
- `x509: certificate is valid for ... not <SNI>` → `serverName` не тот, что ждёт
  сервер: перегенерь конфиг из **свежей** подписки (провайдер сменил камуфляж);
- `REALITY: processed invalid connection` → `pbk`/`sid` разошлись с подпиской;
- `websocket: protocol "h2" was given but is not supported` + `malformed HTTP
  response "\x00\x00\x1e\x04..."` → эти байты HTTP/2-фрейма означают, что на том
  конце уже не VLESS-узел, а обычный веб-сервер: **подписка кончилась**, ноду
  перепрофилировали. Так лёг egress 2026-07-30 (провайдер joybang, ws+tls) — бот
  не принимал команды 5.5 часов. Лечится не правкой конфига, а новой подпиской;
- плечи живы, но long-poll всё равно висит → проблема не в xray, см. алерт
  `TelegramPollingStale` и `telegram_poll_errors_total`: если счётчик ошибок
  **не растёт**, а `last_success` стоит — висит соединение, лечится
  `restart api`, а не заменой узлов.

### Egress лёг, а узлы и конфиг «в порядке» (28-08-2026)

Отказ, который не попадает ни в один пункт выше: `xray -test` говорит
`Configuration OK`, узлы свежие из подписки, в логах ровные строки
`accepted ... [in >> vless-XXX]` **без единой ошибки**, — и при этом ничего не
возит: TLS-хендшейк к `api.telegram.org` и `search.wb.ru` висит до таймаута.
Признак, отличающий этот случай от мёртвой подписки: контейнеры при этом ходят
наружу нормально (прямой запрос из любого сайдкара получает ответ), не работает
именно связь xray → узел.

Причина оказалась в **порту узла**: всё, что слушает `:8443`, с нашего сервера
недоступно, а `:443` отвечает. В подписке на `:8443` сидели ровно те страны,
которыми мы фильтровали конфиг (`--include 'Латв|Финлян|Эстон'`), поэтому
перегенерация «свежих узлов» набирала те же недоступные плечи и ничего не
чинила.

Диагностика — TCP-проба узлов **с хоста**, до всяких конфигов:

```bash
for h in 93.123.39.49:8443 de001.fi1-cosmostechnology.ru:443 sw2.fi1-cosmostechnology.ru:443; do host=${h%:*}; port=${h#*:}; timeout 4 bash -c "</dev/tcp/$host/$port" 2>/dev/null && echo "OK   $h" || echo "FAIL $h"; done
```

Лечение — пересобрать конфиг на странах, чьи узлы отвечают:

```bash
python3 scripts/xray-config-from-sub.py '<URL подписки>' --network tcp --include 'Герман|Швеци|Польш' -o xray/config.json
```

Мораль на будущее: `--include` по странам — это фильтр не по географии, а по
доступности; при мёртвом egress первым делом пробуй TCP до узлов, а не меняй
подписку. И `Configuration OK` вместе с чистыми логами доступность плеч НЕ
подтверждает — `accepted` печатается на приёме от inbound, до всякой попытки
дозвониться наружу.

Отдельно стоит помнить, что через xray идёт **не только Telegram**: там же живёт
`u-card.wb.ru` (живая цена WB). Умер egress — вместе с ботом молча встаёт и
обновление цен WB, хотя алерт приходит только про getUpdates.

## Другой тип подписки (не Reality)

Скрипт пропускает всё, что не `security=reality`. Если провайдер отдаёт
`ws`+`tls`, outbound пишется руками:

```json
"streamSettings": {
  "network": "ws",
  "security": "tls",
  "tlsSettings": { "serverName": "<SNI>", "fingerprint": "chrome" },
  "wsSettings": { "path": "<PATH>", "headers": { "Host": "<HOST>" } }
}
```

и `flow` у пользователя оставить пустым (`""`).
